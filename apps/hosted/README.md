# The hosted app: samples

What the header's menu lists, what `?sample=<id>` does, and how to build and test the page are in [docs/MEASURING.md](../../docs/MEASURING.md), "The hosted app (local build)". This file holds how the sample files are made and read. The page loads the built `gantt-core` package, so run `pnpm build:lib` in `packages/gantt/` before `pnpm build`, `pnpm dev` or the specs here.

The menu lists four samples:

| id | What it is | Rows | Download |
|---|---|---|---|
| `office-fitout` | A small made-up office fit-out project: 9 phases (design, permits, procurement, demolition, framing and boards, MEP rough-in, inspections, finishes, handover) with 50 activities under them. It has links with lag, a calendar with four Monday holidays, a critical path and ten activities part-way done. Every activity but a milestone has one or two named crews, written as `Resources` and `Assignments`. | 59 | 3 KB (`office-fitout.xml.gz`) |
| `medium-5k` | A generated XER file of 5,000 activities | 5,201 | 327 KB (`medium-5k.xer.gz`) |
| `large-50k` | A generated XER file of 50,000 activities | 50,201 | 3.2 MB (`large-50k.xer.gz`) |
| `demo-50k` | The 50,000-task schedule the chart builds itself | 50,000 | none |

- `node scripts/build-samples.mjs` (needs `cargo` and Node 22.18 or later) writes the gzip files and `samples.json` (id, label, format, file, activities, rows, bytes, sha256) to `public/samples/`, which git ignores. It writes `office-fitout` itself, as MS Project XML, from the table in `samples/office-fitout.ts` (the 9 phases and 50 activities, typed; made-up names only), and asks the `xer` crate's `synth` example for the two generated XER files. It fails, naming the file, if one reaches 25 MiB (the per-file cap of a Pages deploy), if a generated file does not hold the activity count it was asked for, or if the office fit-out XML holds a different number of tasks than the table has rows. It stops at the first file over the cap, before it builds the rest, and leaves no `public/samples/` behind. `BUILD_SAMPLES_MAX_BYTES=<bytes>` can only lower the cap, which is how the test trips it: `BUILD_SAMPLES_MAX_BYTES=100 node scripts/build-samples.mjs` exits 1 with `build-samples: office-fitout.xml.gz is 2199 bytes, at or over the 100 byte cap`, and a value that is not a whole number from 1 to 26214400 (`0`, `abc`, or anything above 25 MiB) exits 1 saying it can lower the cap, not raise it.
- The Playwright specs read `public/samples/samples.json`. When it is missing, `pnpm exec playwright test` stops before any spec runs with ``the samples are not built: cannot read …/public/samples/samples.json (ENOENT: …). Run `node apps/hosted/scripts/build-samples.mjs` first.``. `tests/build-samples.spec.ts` covers that error and the cap, and runs with the other specs in `pnpm test:e2e`.
- The page fetches the file the catalog names (`samples/<file>`, for example `samples/office-fitout.xml.gz` or `samples/medium-5k.xer.gz`), undoes the gzip in the browser with `DecompressionStream` (it uses the bytes as they are when they do not start with `1f 8b`, as when a server such as `vite preview` has already undone the gzip), and gives the chart a `File` through `open`, the same path as "Open…", so the open timings in the status line are real. The chart picks the reader from the file's content, never its name: a file that starts with `ERMHDR` (after an optional byte order mark) is read as XER, any other file as MS Project XML.
- The menu shows activities; the chart's row count also counts summary rows. A generated file carries 201 WBS summary rows on top of its activities, so the chart's row count reads 5,201 and 50,201 rows. `office-fitout` has 9 summary rows on 50 activities, so it reads 59. `tests/samples.spec.ts` compares `#row-count` with the `rows` field of `samples.json`, and counts the office fit-out's leaf rows (50) and summary rows (9) from the page's own table against fixed numbers.
- The office fit-out opens with the "unsupported features" panel hidden and the data-date line on the chart, because the sample sets a `StatusDate` along with actual dates and progress (gs#859). The MS Project reader (`import::parse_mspdi`) reads a project's `StatusDate` as the data date (gs#563): an MS Project XML file that has one opens with the data-date line on the chart and "Data date YYYY-MM-DD HH:MM" in the toolbar, as a P6 XER file already does, and a file without one opens with no line. The date and time are used as written in the file, and a `StatusDate` that is not a date, or falls before the schedule's origin Monday, is left out and listed in the "unsupported features" panel. [docs/IMPORT.md](../../docs/IMPORT.md) lists the field.

## What the page looks like

- **Font.** The page uses a bundled font, not the machine's: `Gantt Sans` and `Gantt Mono` (Liberation 2.1.5, SIL Open Font License 1.1; files and notice in `packages/gantt/src/fonts/`). The task list and the toolbar hold the same text width on every machine, and the list text matches the chart's bar names and axis labels. The first load downloads about 295 KB of fonts: Gantt Sans Regular plus Bold. Gantt Mono (126 KB) loads only when one of the three diagnostic panels that use it (the metrics overlay, the unsupported-features panel and the result link) appears. The page holds text back until a font is in, so there is no flash of another font. The notice (`packages/gantt/src/fonts/NOTICE.md`) credits Arimo, Tinos and Cousine, the upstream fonts that Liberation builds on (Liberation Sans on Arimo, Liberation Mono on Cousine; Tinos is the serif, which the page does not ship). The demo page that `demos/50k/run.sh` serves (`packages/gantt/index.html`) sets its body text in Gantt Mono too, instead of the machine's monospace, and `packages/gantt/tests/font.spec.ts` checks it. This hosted page's own header and menu text use the system font.
- **The first-screen line.** One line over the chart's bottom edge (the chart keeps the whole window, and borders its bottom by the line's height while the line is open, so the line covers neither the legend row nor the baseline note) says it is a sample schedule and that "Open…" takes a P6 XER or MS Project XML file (from Microsoft Project, save as XML first). `✕` dismisses it, and `localStorage` key `gantt-first-screen-line-dismissed` keeps it dismissed on reload. Opening your own file (the chooser or a drop) or starting a New schedule removes it for that visit (a New schedule the unsaved-changes question cancels leaves it), and it never shows with the start-failure block. `index.html` holds the text and the chart's border rule; `src/first-screen-line.ts` puts the line on the page and sets `--first-screen-line-h` to its height.
- **Hidden columns are kept** (gantt#703). The Start, Finish and Float columns that the Columns menu hides stay hidden after a reload, in this browser: after each press on a row of the menu, `src/hidden-columns.ts` writes the hidden ones to the `localStorage` key `gantt-hidden-columns` (for example `start,float`), and sets `data-hide-<column>` on the chart's table when the page starts, and again after a switch to WebGL2. The menu reads the table's flags each time it opens, so it shows a restored column unticked. With storage blocked, every column shows on each load. The chart's package (`packages/gantt/`) writes nothing to storage, because it ships to npm and runs in other people's pages; `packages/gantt/tests/columns-menu.spec.ts` checks that, and `tests/hidden-columns.spec.ts` checks the reload.
- **The open schedule is kept** (gantt#2077). The standalone app keeps a copy of the open schedule in the browser after each edit and, when the page is opened again, asks once whether to bring the schedule back. `src/autosave.ts` writes `Gantt.toDocument()` to IndexedDB (database `gantt-autosave`) half a second after the last edit, and drops the copy when a save or a new file leaves no unsaved changes, or when you cancel the question; `tests/autosave.spec.ts` checks it. When you answer OK and the chart cannot load the copy right then, the copy is held: edits to the schedule on screen do not overwrite it, and the next page load asks again. A schedule brought back shows no unsaved mark, because `Gantt.load` opens it as a file.
- **Reduced motion.** With "reduce motion" on in the system, the "what moved" note at the top right of the chart stays fully visible for 4 seconds after an edit and then disappears at once, with no fade, and the dashed outlines of the old places go with it. With motion on, the note fades over 0.4 seconds. After a drag release the note and the outlines show, and the bars do not slide.
- **The note does not stop the wheel** (gs#549). The note (`#moved-note`) listens for the wheel with the same function as the canvas (`onWheel` in `packages/gantt/src/pointer.ts`). While the note shows (about 4.4 s, or while the pointer holds it), the wheel over it scrolls the rows and `Ctrl`+wheel or a pinch zooms, anchored where the pointer is, and the page behind does not scroll. `packages/gantt/tests/moved-note-wheel.spec.ts` checks it.
- **The screencast and the journey run on this page** (gs#541). `demos/screencast/record.mjs` opens `/?sample=demo-50k` on `apps/hosted/dist`; `tests/journey.spec.ts` plays every scene of `steps.mjs` and `steps-features.mjs` there, and `tests/j1-open.spec.ts` opens `office-fitout` from the menu, then your own file with the chooser (no network request), then a truncated file's error. `JOURNEY_SAMPLE=<id>` points the journey at another sample; `medium-5k` fails the first scene by name, because that scene checks for 50,000 tasks.
