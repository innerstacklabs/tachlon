# WASM API

The WASM module is the public surface of the engine and renderer, as set by [decision 0005](decisions/0005-users-first-component-later.md).
The shell in `packages/gantt/src/index.ts` (started by the developer page, `packages/gantt/src/main.ts`) uses only the Public exports.
Test-only exports are all named `test_*`. They are for the `packages/gantt/tests` specs, `demos/**`, and the measurement harness.
The snake_case export names are frozen. A later package maps them to camelCase.
To add an export, add its row to this page first. Then add the code with a `///` doc comment.
Coordinates are CSS pixels relative to the canvas's top-left corner.

## Public

### Setup and lifecycle

| Export | What it does | Notes |
|---|---|---|
| `App.create` | Set up the renderer for `schedule` on `canvas` (`css_width` x `css_height` at `dpr`). | Signature: `create(canvas, css_width, css_height, dpr, force_webgl, schedule)`. Width and height are CSS pixels. `dpr` is the device pixel ratio. `force_webgl` skips WebGPU. `schedule` comes from one of the `LoadedSchedule` constructors. Returns `Result` and throws `JsError` if renderer, surface, or schedule setup fails. |
| `LoadedSchedule.parse_bytes` | Parse the bytes of an MS Project XML or Primavera P6 XER file into a solved schedule. | Signature: `parse_bytes(bytes, selection)`, where `bytes` is a `Uint8Array` and `selection` is `undefined`, `"all"` or a P6 `proj_id` as a string. A file that starts with `ERMHDR`, after an optional UTF-8 byte order mark, is XER; any other file is MS Project XML, decoded as UTF-8, and `selection` does not apply to it. For XER, `"all"` opens every project, a `proj_id` opens that project, and `undefined` opens the only project of the file. For a file with several projects and no selection it throws an `Error` whose `name` is `"ChooseProject"` and which carries `projects`, an array of `{ id, name, activities }` in file order (`id` is the `proj_id` as a string, ready to pass back as `selection`; `name` is the project's short name, empty when it has none; `activities` is a number). Any other `selection` text throws. Every other failure throws a plain `Error` (the throw is a `JsValue`, not a `JsError`) if the file cannot be loaded or solved; the message is the importer's or the engine's text. An MS Project file whose tasks carry Baseline 0 (both a start and a finish) also brings that baseline, which `App.create` and `App.open` install with no undo step, as for `parse_document`; its entries hold no float. Copies `bytes` once into linear memory, keeps that copy as the file `App.save` writes, and runs on the calling thread. |
| `LoadedSchedule.format` | What the schedule came from. | Returns `"xer"`, `"mspdi"`, `"gantt"` (a schedule document), `"blank"`, `"demo"` or `"stress"`. The file's content decides between the first two, never its name. |
| `LoadedSchedule.timings` | How long `parse_bytes` spent in each Rust phase. | Returns JSON text, `{"parse":..,"build":..,"compute":..,"span":..}`, in milliseconds on the page's `performance.now()`. `parse` is format detection, the reader and the mapping into the engine schedule; `build` is the display data, the engine schedule and freeing the import's task list; `compute` is the solve, the row order, the outline and the check of in-progress file dates. The three windows are back to back, so they add up to the span between the first and the last clock read inside `load_bytes`. `span` is the whole of `load_bytes` timed by two reads outside it, an independent measure: it equals the sum of the three phases plus the cost of a clock call at each end (under 3 ms, measured), and a larger difference means a phase lost or double-counted time. The rest of the call (the copy of `bytes` into linear memory and building the result) is in none of them, and the page reports it as `copy`, the call minus the three phases. A value that is not a finite number is `null`; a negative value (a clock that went backwards) is written as it is. Nothing is clamped to zero. All zero for `demo` and `stress`. Call it before `App.open`, which consumes the object. |
| `LoadedSchedule.parse_document` | Read the text of a schedule document (decision 0010) into a solved schedule. | Signature: `parse_document(text)`, where `text` is the document's JSON text; the page gunzips the file first (`packages/gantt/src/document.ts`). Returns `Result` and throws `JsError` with the reader's message (`not a schedule document: ...`, `this document is version 2; this app reads version 1`, `bad schedule document: tasks[12].remaining ...`). It reads only `"format": "gantt"`; any other value is refused. `format()` is `"gantt"`. The schedule carries the document's `options` (decision 0018; an unknown member or value is refused by name) and its `must_finish_by` (minutes from `origin`; a value outside the engine's date range is refused by name, decision 0020), its baseline, its collapsed summaries and its original file, which `App.create` and `App.open` install. `timings()` holds the document read: `parse` is the JSON read, `build` and `compute` the rest. |
| `LoadedSchedule.conform` | Fit a schedule just read to what the host stores, before `App.open` or `App.create` takes it. | Signature: `conform(profile)`, where `profile` is the JSON of `App.set_capabilities`. A task's date limits past `perTask` are dropped, later in the order `snet`, `snlt`, `fnet`, `fnlt`, `mso`, `mfo`, `alap`, `so`, `fo` (a floor and a ceiling on one instant are one limit unless `kinds` leaves out `so` or `fo`); a duration goes to the nearest whole `durationStep` (half a step up, never none for some); a date with a time of day goes to the start of its day under `dates: "day"`. Summaries are skipped. `unsupported()` then ends with one line per kind of fit, with its count (`12 tasks had a second date limit, which this host does not store; the later ones were dropped`), and the schedule is solved again. `{}` changes nothing. A lag, and a limit of a kind `kinds` leaves out, are not fitted. Throws `JsError` for text that is not a profile. |
| `LoadedSchedule.demo` | Build the solved demo schedule with `n` tasks. | `n` is the task count. Returns `Result` and throws `JsError` if the outline cannot be built. |
| `LoadedSchedule.blank` | Build a solved schedule with no tasks, the start of a new plan. | Signature: `blank(start_day)`, where `start_day` is a whole number of days since 1970-01-01 (an `i32`). The origin is the Monday on or before `start_day`, so every date text starts there. The one calendar is Monday to Friday, 08:00-12:00 and 13:00-17:00, with no holidays: a day is 480 minutes. The outline is empty, so `App.open` and `App.create` accept it, and the first `App.insert_task` makes a top-level row named `New task` with activity ID `A1000` and a duration of 480 minutes. `format()` is `"blank"`; `timings()` is all zero, as for `demo`. |
| `LoadedSchedule.stress` | Build the solved stress fixture with `n` tasks. | `n` is the task count. This is the stress fixture with dense cross-phase links. |
| `LoadedSchedule.stress_grouped` | Build the solved stress fixture with `n` tasks under one root summary, each coded `Phase` with one of `groups` values. | `n` is the task count and `groups` the number of `Phase` values, at least 1. Returns `Result` and throws `JsError` if the outline cannot be built. The developer page's `?groups=` uses it. |
| `LoadedSchedule.unsupported` | Unsupported features reported while importing the schedule. | Returns an array of strings. For an XER file one line says how many in-progress activities have different dates in the file than the engine computed. |
| `App.open` | Replace the schedule on the page with `schedule`, in place. | Takes a `LoadedSchedule` (the object is consumed, as in `App.create`). The renderer, the canvas and its size stay; the colours stay. The new session has no selection, no filter, no collapsed summary and no undo history (`Status.revision` is 0), and its view is fitted to the dates of the rows on its first screen (the earliest early start to the latest early finish among them). The bars of the rows in the window then draw in (below, `App.set_reduced_motion`). `Status.epoch` goes up by one; a page that keeps state for the old schedule (rows drawn, a find query, an open cell editor) resets it when it sees that. Returns `Result` and throws `JsError` if the new outline cannot be built, and then the previous schedule is untouched. A schedule from `parse_document` also brings its baseline and its collapsed summaries, with no undo step (`Status.revision` is still 0). The session keeps the original file the schedule was read from (the bytes of an XER or MS Project file, or the document's own `source`), so `App.save` writes it. |
| `App.export_mspdi` | The session as an MS Project XML file, edits included, written by `export::export_mspdi` (gs#703). | Signature: `export_mspdi()`. Returns `{ bytes, left_out }`: `bytes` a `Uint8Array` of the UTF-8 file, `left_out` a `string[]` with one line for each thing the file cannot carry (an actual start, activity ids and codes, a baseline with no dates). The page downloads `bytes` as `<name>.xml` and lists `left_out` in its Export dialog. Reads the session and changes nothing, so it is no undo step. Throws `JsError` when a date or duration cannot be written in the file's form. |
| `App.export_xer` | The session as a P6 XER file, edits included, written by `export::export_xer`. | Signature: `export_xer()`. Returns `{ bytes, left_out }` as `App.export_mspdi` does: `bytes` a `Uint8Array` of the file, `left_out` a `string[]` naming what the file cannot carry. A session read from an XER file is written in that file's layout. Reads the session and changes nothing, so it is no undo step. Throws `JsError` when a date cannot be written in the file's form or a cell holds a character it cannot carry. |
| `App.export_xer_left_out` | What a Save as XER would leave out of this schedule, from `export::xer_left_out`. | Signature: `export_xer_left_out()`. Returns a `string[]`: one line for each of the activity codes, baselines and deadlines the schedule has (`the deadlines on 2 tasks are not written`), empty when it has none. Writes no file; reads the session and changes nothing. |
| `App.save` | The session as a schedule document: one JSON text (decision 0010), written by `document::write`. | Signature: `save(name)`, where `name` is the schedule's name (the opened file's name without its extension, `untitled` for a sample). Returns the text; the page gzips it (`CompressionStream`) and starts the download, so nothing leaves the page. Holds the edits, outline, each task's date limits (start no later than, finish no earlier or later than, must start or finish on, as late as possible), each task's bar `color` (`#rrggbb`) and `label` (the text its bar shows in place of the name; the table keeps the name), each only when set (the name in a colored bar reads at 4.5:1 on the bar and its progress for the tested palette only, `crates/timeline/src/scene/tests/bar_color.rs`; no other color is promised that), the schedule's `options` when a member is not on its default (decision 0018: `startedLateStart`, `unstartedRemaining`), its `must_finish_by` when a date is set, the opaque `key` of each task, link and calendar when set (the text a host gave it, such as a database id; the app never reads it, it is not empty and unique among the records of its kind, `read` refuses a repeat by name, and it stays through edit, delete and undo; a link or calendar the chart adds has none), baseline, collapsed summaries, the "unsupported features" lines and the original file when the schedule came from one. It reads the session and changes nothing, so it is no undo step and moves no `Status` field. Writing the same session twice gives the same text. It runs synchronously: the cost is one pass over the live tasks plus the base64 of the original file. |
| `App.backend` | Backend the page got: "WebGPU" or "WebGL2". | - |
| `App.set_locale` | Set the month and weekday names the app writes. | Takes JSON text, `{"months":[12 names],"weekdays":[7 names],"weekStart":0}`, January and Monday first; `weekStart` is the day the axis's weeks start on, 0 for Monday to 6 for Sunday (`packages/gantt/src/names.ts` writes it from `Intl` for the page's `locale`). An optional `texts`, an object from a key of `App.default_texts` to a sentence, gives the words this chart refuses an edit in (the `message` of a refusal, the text of a thrown `JsError`, the reason a link drag is refused with (`link.refusal` in the status), and the reason `App.set_task_fields` throws after the field's name, `Duration:`, which stays English) and the words of its printed pages (the header, the footer, the legend, the column heads, the filter line and the rows-not-printed note; copy, CSV and XLSX keep English heads), of the drag notes, of the what-moved note, of the hover card's calendar, float, deadline and `+ N more` text and of the compare lines (`lines`, the `and N more` that ends a long list, and the error for two files that share no ID); the on-screen legend is English still; a key it leaves out reads in English, an unknown key or a value that is not a string throws, and each chart keeps its own, so two charts on a page can refuse in two languages. The `kind` of a refusal does not change with the words. The names write the day in the toolbar's baseline date, the what-if finish dates, the off-screen note and the status range, and name the months on a printed page's axis (`12 Oct` becomes `12 Okt` with German names). The setting survives `App.open`, as `App.set_reduced_motion` does. Throws `JsError`, changing nothing, for text that is not JSON of that shape or a list of other than 12 or 7 strings or a `weekStart` outside 0 to 6. It is not an edit: it does not enter the undo history. |
| `App.set_fonts` | Add font faces and set the text engine's locale tag. | Takes TrueType or OpenType file bytes and reshapes cached labels; the setting survives `App.open`. Throws `JsError` when a face cannot be read, after keeping readable faces. |
| `App.default_texts` | The English sentences an edit is refused in and a printed page is worded in. | Static. Returns a JSON object from each key (`emptyName`) to its English text (`a name cannot be empty`), 164 in all; a `{name}`-style hole is filled by the app. A host translates the values and hands them to `App.set_locale` as `texts`. `refusal`, the answer the page gives for a cell edit it refuses itself (`busy`, `readOnly`, `badDataDate`), is not tied to a chart and stays English. |
| `App.task_count` | Number of live tasks. | A deleted task is not counted; `Status.n` is the same number. |
| `App.resize` | The canvas is now `css_width` x `css_height` at `dpr`. | Width and height are CSS pixels. `dpr` is the device pixel ratio. |
| `App.frame` | Draw a frame. False if the surface skipped it. | Returns `Result<bool, JsError>`. The Boolean is false if the surface skipped the frame. Throws `JsError` if rendering fails. |
| `last_panic` | The first panic's message, if the module has panicked. | Returns `Option` and gives `undefined` when the module has not panicked. |

### Headless (no canvas)

`openHeadless`, the package's `./headless` export (`packages/gantt/src/headless.ts`), gives a Node program `whatIf`, `whatIfLonger`, `explain`, `health` and `criticalPath` over a file, over plain `{ tasks, links }` as `fromTasks` reads it (plain data `validate` refuses throws a `PlainDataError`, whose `name` and `issues` the caller reads, as the data goes to `fromTasks` uncopied; the lines it leaves out are `leftOut`, empty for a file or a document; a third argument `capabilities` fits the schedule to what a host stores, as `LoadedSchedule.conform` does, and `leftOut` then ends with a line per kind of fit) or over `{ document }` (`tasks` is read before `document`, as `load` in `mount-load.ts` reads them), with the same result types as the chart's commands and no page (and `results()`, every task's early and late dates, total and free float and critical flag in one list, which the chart has no command for): it loads the engine with `initSync` and reads no `window` or `document`. `callTool` and `toolDefinitions` come from the same import and run over it, where `propose` answers `"unknownTool"`; `project` is for a file and any other source with it throws an `Error`; `free()` releases the session, after which `callTool` answers `{ ok: false, reason: "destroyed" }` and a method throws. How it works:

1. `packages/gantt/src/styles/tokens.css` (linked first on the page) defines every `--gantt-<token>` on the root with `:where(.gantt)` (zero specificity), the dark set inside `@media (prefers-color-scheme: dark)`. A host page overrides any token on the root element, for example `.my-host .gantt { --gantt-bar: #0a7; }` or an inline `style`; its rule wins regardless of order. `prefers-color-scheme` only selects the default set when the host sets nothing. `crates/timeline/tests/theme.rs` fails if these CSS blocks and `Theme::light()` / `Theme::dark()` differ.
2. The shell (`packages/gantt/src/theme.ts`) reads the computed `--gantt-*` values from the root, normalises any CSS colour to `#rrggbb` (or `#rrggbbaa`) through a canvas context, and calls `set_theme`. It does this at start, when the colour scheme changes, and when the root's `style` or `class` attribute changes. A host that changes a stylesheet the observer cannot see calls `window.gantt.syncTheme()`. The table is DOM and reads the same variables, so the table and the scene always agree.
3. `App::set_theme(json)` takes a flat JSON object of token name to `#rgb`, `#rrggbb` or `#rrggbbaa` strings. Keys left out keep their current value, so a partial theme is valid. An unknown key, a bad colour, a duplicate key or malformed JSON throws a `JsError` and leaves the theme unchanged; nothing falls back silently. `App::theme()` returns the complete current theme as the same JSON, and the static `App.theme_tokens()` returns the token names. A theme is not an edit: it does not enter the undo history or change `Session::revision`.
4. CSS is the source of truth in this app: a theme passed only through `set_theme` changes the scene but not the DOM table, and the next `syncTheme` overwrites it with the CSS values. Theme the chart in CSS; call `set_theme` directly only for a chart with no DOM table.

The message line (`#overlay`) takes its background from `surface`, its text from `text` and its border from `rule`; the measured run's download link (`#result-link`) takes its background from `sel-edge` and its text from `bar-text`. The hover card (`#hover-card`) takes its background from `surface`, its text from `text`, its labels from `muted` and a critical value from `crit-text`; it is DOM and CSS colour only, not drawn per frame. `#unsupported` (the list behind the toolbar's "N import notes" button) uses the theme's tokens. `#overlay` is now only the chart's message line (loading, errors and a measured run's progress).

The toolbar (`#toolbar`) and the status line (`#status-line`) are inside the root and use the tokens above (`surface`, `rule`, `text`, `muted`, `sel`, `sel-edge`, `hov`, `crit-text`). They are the app's chrome: `packages/gantt/src/index.ts` wires them with the Public exports only and looks each one up as optional, so a page without them keeps a working chart. The toolbar's `#toolbar-file` group holds the Open button, the hidden file input `#open-input` and the line that names the open file (gs#87 PR 2); `#open-error` is the line that says why a file did not open. `<dialog id="picker">` is the project list for a file with several projects (gs#87 PR 3); it sits inside the chart root (its styles are under the root class and it inherits the tokens), and the root's key listener ignores a key whose target is inside a dialog, so the chart's keys never act on it; a page without it shows an error line for such a file. `index.ts` and `open.ts` look each one up as optional.

## Dates

The engine counts minutes from an origin Monday. For a file the origin is the Monday on or before its plan start (XER `plan_start_date`, MSPDI `StartDate`), or Monday 2000-01-03 when the file has none. The demo and the stress fixture use Monday 2026-01-05. `LoadedSchedule` carries the origin from the import (`Loaded::origin`, from `Imported::origin_day`) into `App.create` and `App.open`, and every date text the app writes or reads goes through `Origin::date_of` in `crates/app/src/dates.rs`: `table_rows` and `task_details` (`start`, `finish`, `lateStart`, `lateFinish`), `data_date_text`, `Status.lookahead.start`, and the `YYYY-MM-DD` that `set_lookahead` takes. The `from` and `to` texts in `Status` follow it too. A file planned in 2024 therefore shows 2024 dates everywhere, and a lookahead start the box shows is a start the box takes back.

The canvas axis follows the same origin: the year, month and day labels and where the month and year ticks fall come from it (`timeline::axis::Origin`, passed in `timeline::scene::Backdrop::origin`), so a 2024 file's axis reads 2024 and the table and the chart never disagree on the year.

The month in a day label the app writes (`14 Oct`: the baseline's date, the what-if finish dates, the off-screen note, the `from` and `to` of the status) is a name from `App.set_locale`, English until the host sets others, and so are the month names on a printed page's axis; `App.open` keeps them. The table's dates and the screen's axis keep their own forms; the axis's weeks start on the `weekStart` day (Monday until the host sets another).

## JSON shapes

`App.status` returns a JSON string that parses as the TypeScript `Status` interface in `packages/gantt/src/api.ts`.
It contains backend, task and row counts, filter state (`filter` is `off`, `critical`, `near`, `longest`, `slipped`, `float`, `joined`, `left`, `moved`, `status`, `check`, `code` or `resource`), visible row and time ranges, viewport values, scene counts (including `shaded`, the non-working-day columns drawn, and `dataDate` and `dataDateX`, the file's data date and the x of its line),
revision and frame counters, surface size, the row the canvas draws as hovered (`hoverRow`, or `null`), and current hover, drag, and selection state.
`range` is `[first, last, extent]`, the range selection as table rows (`first` to `last` inclusive, `extent` the end that moves), or `null` when there is no range; a collapsed end stands on its summary's row.
`link` is `{ selected, drag, refusal, note }`: the selected link's id (or `null`), the link drag in progress as `{ pred, target, refused }` (`target` is the task under the pointer, and `refused` is the message a release there would be refused with; each is `null` when there is none), and the message the last link drag was refused with (cleared by the next press).
`gesture` names what the pointer is doing, one of `idle`, `bar-pressed`, `bar-dragging`, `link-pressed`, `link-dragging`, `finished-pressed` (a press on a finished task's bar, which cannot move), `resize-pressed` or `resize-dragging` (a press on a leaf bar's right edge, which sets its duration). It is derived from the press state (`Session::gesture`), so it is never stale. While it is not `idle`, the chart's keys, the hover card and the cell, row and link editors stay shut: an arrow key, Home, End, PageUp and PageDown are taken and do not scroll the host page, `CellEdit.begin` refuses, and a second `pointer_down` (a second finger) is ignored until the first press ends.
`note` is the calm line a bar drag on a finished or a started task leaves, `<name> is finished: its dates are its actuals. Change Actual finish in the table to move it.` or `<name> has started: its start is its actual start. Change Remaining or % complete in the table to move its finish.` (a drag of its bar's right edge says `<name> has started: change Remaining or % complete in the table to move its finish.`; each reads in the words of `App.set_locale`'s `texts`, `dragFinished`, `dragMoveStarted`, `dragResizeStarted` and `dragPutBack`, English where it sets none), or `null` (cleared by the next press);
the page shows it in a chip at the chart's bottom right for about 6 seconds, not in the red alert line.
`lookahead` is `{ on, start, weeks }`: the window that is set, or the one a reader would get (the data date's day for 3 weeks, or the project origin's day when the file has no data date), with `start` written `YYYY-MM-DD`.
`epoch` counts the files opened in place with `App.open`; it starts at 0.
`moved` is `null` or the report of the last edit, undo, redo or drag release that moved tasks besides the edited one: `{ seq, text, others, finish_days, alpha, slide }`.
`seq` counts reports, so a page can tell a new one from the one it shows;
`text` reads like `8 tasks moved · finish +7 days` (the finish clause appears when the project finish moved by a calendar day or more);
`others` is the count, the edited task left out;
`finish_days` is signed;
`alpha` is 1 for 4 seconds after the report, then falls to 0 over 0.4 seconds (with reduced motion on, `App.set_reduced_motion`, it drops from 1 to 0 at 4 seconds with no ramp), and is 1 while the pointer holds the note (`App.set_moved_hold`);
`slide` is true for an edit and false for a drag release, whose bars are already where the pointer left them.
Any other change clears it.
`moved` adds 13 bytes to the status string when it is `null` and 113 for the example above when set (`crates/app/tests/moved.rs` asserts both).
`baseline` is `null` with no baseline set, else `{ slipped, finish_days, joined, left, added, removed }`, how the schedule differs from the baseline of `App.set_baseline`.
`slipped` counts tasks whose early finish is later than the baseline has it;
`finish_days` is the calendar days the project finish moved, signed;
`joined` counts tasks that are critical now (zero float and not finished) and had float then, and `left` the tasks that had zero float then and are not critical now, except a task that is finished now: finished work is never critical, so a task finished after the baseline was set is not counted as leaving;
`added` counts live tasks the baseline has no entry for and `removed` the tasks it holds that are deleted now.
The first four count only tasks that are live now and were live then.
The app computes the object once per solution (keyed on the revision and the stamp) and reads the kept result on every other frame, and with no baseline it computes nothing.
During a bar drag it computes at most once every 150 ms and the frames between report the last value; the first read after the release is exact.
`baseline` adds 16 bytes to the status string when it is `null` and 83 when it is set with nothing changed; the widest it can be is 147 (`crates/app/tests/baseline.rs` asserts the sizes).
`slide` is `{ active, copyMs }`: `active` is true while a slide runs (a session that has reduced motion on never has one), and `copyMs` is how long the copy of the last slide took in milliseconds, or `null` before the first slide; it stays after the slide ends.
`slide` adds 39 bytes to the status string while `copyMs` is `null` (`crates/app/tests/moved.rs` asserts it).
`offscreen` is `null`, or `{ b, a }` when none of the rows the window shows has a bar in the window's time span: `b` is the day of the latest finish before the window and `a` the day of the earliest start after it, among those rows, written like `12 Jan`, and either is `null` when that side has no work (never both).
The app scans only the visible rows each time the status is read and keeps nothing between frames.
`offscreen` adds 17 bytes to the status string when it is `null` and at most 40 when set (`crates/app/tests/offscreen.rs` asserts the field stays under 60); the shell's edge note shows it as `Work on these rows: earlier, 12 Jan`, `Work on these rows: later, 2 Aug` or `no work 6 Jul to 2 Aug`.

`App.table_rows` returns a JSON string that parses as `TableRow[]`, where `TableRow` is the TypeScript tuple in `packages/gantt/src/api.ts`. Each tuple contains task id, start, finish, float in minutes or `null`, critical state, and row kind. Row kind is 0 for a leaf, 1 for an expanded summary, 2 for a collapsed summary, and 3 for a group header while the rows are grouped by an activity code type (decision 0015): `[null, value or null for no value, leaf count, null, false, 3, null, null, null, null]`, with 4 in place of 3 while its group is collapsed (`Session::toggle_group`); a header has no task, no schedule entry and no bar. Three cells follow, at positions 6 to 8: the start, finish and float variance against the baseline, each the signed change in working days of the task's own calendar as text (`+5d`, `-2d`, `0`; a fraction rounds as the Float column does), or `null`. Start and finish are positive when later, float is positive when there is more of it. A summary row reads its rolled-up span against the rolled-up span of the baseline's own dates, over the outline as it is now (a task the baseline has no entry for, or that is deleted, is left out of the baseline's span); its Float cell is always `null`. So is the float (position 3) of a finished task, one with an actual finish: the table's Float cell is empty for it, not `0d`, though the engine's float for it stays 0 (decision 0008). All three are `null` for a task the baseline has no entry for, in a session with no baseline, and (the Float one only) when the baseline came from a file that states dates but no float, (the Start or Finish one only) when the baseline's date is before the origin, and while a bar is being dragged (a drag redraws every row every frame, so the page holds the columns then and the release brings them back). Position 9 is the free float: how long the task can run late before the next task has to wait, as text in working days of the task's own calendar (`1d`, `2.5d`; `0d` for a task with none), and `null` for a summary, a group header, a finished task and a task whose free float the engine cannot work out. It is worked per row from that task's successors (`Schedule::free_float`), also while a bar is dragged, and only while the column is shown (`App.set_free_float_shown`): while it is hidden, the start state, every row has `null` there. Positions 0 to 8 are as they were.

`App.task_details` returns a plain object described by the TypeScript `TaskDetails` interface in `packages/gantt/src/api.ts`. It contains the task identity and names, the activity ID (`activityId`, empty when the task has none), the progress status (`status`: `Not started`, `In progress` or `Complete`) with `actualStart`, `actualFinish` and `percentComplete` (each an empty string until set, text from the table's progress columns), date and float display values, critical or summary state, and predecessor and successor counts and lines. A line is the neighbour's outline path and its link in the link editor's text, such as `Level 3 / Concrete / Pour slab (SS+2d)`; the first three neighbours are listed. `resources` lists the names of the task's resources from an MS Project file, in the file's order (empty for a task with none, and for a task of a saved document or added after the open). A leaf with a baseline entry also has `baselineStart` and `baselineFinish` (date texts, left out when the baseline's date is before the origin) and `baselineVariance`, the start and finish variance in working days of the task's calendar as the table's variance cells write them (`+5d`, `-2d`, `0`; each `null` when that date is left out). A summary, a task with no entry and a session with no baseline have none of the three.

`packages/gantt/src/api.ts` is where these shapes live; `Status` (with `Hover`, `Drag`, `Selected`, `Link`, `LinkDrag` and the inline `lookahead` object), `TaskDetails` and `TableRow` are declared there and nowhere else. `App.status`, `App.table_rows` and `App.task_details` are one-line delegations to `Session::status_json`, `Session::table_rows_json` and `Session::task_details_json` (`crates/app/src/json.rs`, native, no `wasm_bindgen`); `App.task_details` parses the string with `JSON.parse`. `crates/app/tests/json_contract/` builds real sessions (hover off, on a leaf and on a summary; drag, selection, link drag and window off and on; a leaf and a summary row of the table and the hover card), captures the keys of the JSON they write, and compares them with `api.ts`: the keys of each object, both ways, and whether each key is optional (a key counts as always written when every capture has it); and, for a `TableRow`, the number of cells and the JSON kinds each cell takes. Renaming a key on either side fails `cargo test -p app --test it json_contract::`. A string in these shapes is escaped the way `serde_json` writes it.

## Page entry

`packages/gantt/src/index.ts` is the entry a host page imports: it starts the chart and returns what the page may call, and it is the only file of `packages/gantt/src` that a host needs to name. The developer page, `packages/gantt/src/main.ts`, calls it like any host and adds the URL knobs (`?n`, `?stress`, `?schedule`, `?backend=webgl`, `?fallback`, `?measure`, `?panic=init`). It hands the ones `mount` needs (`params`, `fallback`, `measure`, `measured`, and `restart`, its reload for a panic and the frame banner's Reload button) through `packages/gantt/src/page-knobs.ts`, which the entry does not export, so no type of them is in `MountOptions` or any other export. One row per export, and the `entry` architecture check keeps this list equal to the exports of `index.ts` (see "How it is enforced"). The chart's elements are found by their ids, so the page holds one chart; `root` is the element that holds them. The page gives only the root: the chart's markup (`packages/gantt/src/chart.html`) and stylesheets come with `index.ts`, and `mount` inserts the markup in `root`.

<a id="mount"></a>`options.schedule` is a `File` (XER, MS Project XML or a `.gantt` document, which the page gunzips; every project of an XER is opened), `{ demo: n }` or `{ stress: n }`.
`options.document` is a saved schedule document, the JSON `toDocument` returns, for a chart that starts on it with no `load` after; `options.schedule` wins over it and it wins over `options.tasks`. With none of the three the chart starts with no tasks and waits for `load` or `open`.
`options.forceWebgl` draws with WebGL2 and never tries WebGPU.
`options.wasmUrl` (a string or a `URL`) is where the engine file is fetched from; without it the engine is the file `app_bg.wasm` beside the script, and a string reads against the page's address.
`options.locale` (a BCP 47 tag such as `"de"`) is written as the root's `lang` and decides the chart's number format (`1.234,5` for `"de"`); a right-to-left language (`ar`, `he`, `fa`, `ur`, `ps`, `sd`, `yi`, `ckb`, `dv`, `ug`) also sets `dir="rtl"` on the root, so the table, toolbar and panels read from the right while the timeline stays left to right; it also sets the month names the app writes (`App.set_locale`: `de` writes March as `Mär`) and the day the axis's weeks start on (Monday for `de`, Sunday for `en`); without it the numbers read as `en-US`, the names are English, the weeks start on Monday and the root's `lang` and `dir` are not touched. A tag that is not a language tag rejects `mount` with a `RangeError` before the root is touched. The React, Vue and Angular components take it, and `texts`, as a prop or input and mount again when it changes.
`options.texts` (an object from a key to a text) gives the words of the chart's markup, `packages/gantt/src/chart.html`: each element names its key in `data-t` (its text), `data-t-title`, `data-t-aria-label` or `data-t-placeholder`, and `applyTexts` (`packages/gantt/src/locale.ts`) writes the text of that key into it as the chart starts, from `TEXTS_EN` (`packages/gantt/src/texts-en.ts`) with the host's texts laid over it. The names of the columns and fields the script writes while the chart runs (the ID, WBS and progress heads, the variance heads, the hover card's row names, the cell editor's name for a field) come from the same texts by `nameOf` (`packages/gantt/src/field-names.ts`), the English in `FIELDS_EN` and `TEXTS_EN`; a column is told apart by its class, never by its text. The sentences the script writes while it runs (a file that cannot be opened or loaded, the saved note, the selection count, the row position, the baseline's confirmation, a failed frame's banner) are templates with `{name}` holes in `MESSAGES_EN` (`packages/gantt/src/texts-en.ts`), written by `say` (`packages/gantt/src/messages.ts`); a number in a hole is written in the chart's number format. A sentence that depends on a count has one key per plural category of `locale`, after a dot (`bytes.one`, `bytes.few`, `bytes.many`, `bytes.other`), chosen by `Intl.PluralRules`; the host gives the forms its language uses, and a count with no form of its own falls to `.other`, then to the bare key. A key the host leaves out stays English and an unknown key is ignored. With `locale`, the keys of `App.default_texts` among them (`alreadyLinked`, `durationInvalid`) also go to `App.set_locale` at mount, so the chart's refusals read in them; without `locale` they are not handed over. The object is frozen, and `state()` gives the same object back while nothing in it changed.
`state()` parses the status JSON on each call: read it when a host needs it or in a `change` handler, not in an animation loop.
The `change` event's detail is built by the loop's own reader, so it has the same fields as `state()` but is not the same object; a `state()` call between frames never moves what the next event is compared with, so each event differs from the one before it.
`change` does not fire for the first frame: read `state()` after `load`.

## Mount error codes

A `MountError`'s `code` is the product name in capitals, an underscore and one of these causes (`packages/gantt/src/errors.ts`). The engine causes
come from fetching the engine file again after the load failed and reading its status and first four bytes.

| Cause | `stage` | When | What to do (`fix`) |
|---|---|---|---|
| `DATA_INVALID` | `"schedule"` | `validate` refuses the plain task data. | Correct the fields `message` lists; `validate(data)` checks the same rules. |
| `ENGINE_FETCH` | `"engine"` | The engine file (`app_bg.wasm`) could not be requested, or answered with a status outside 200 to 299. | Serve it from the address the page asks for, with status 200. |
| `ENGINE_NOT_WASM` | `"engine"` | The address answers 200 with bytes that do not start with `\0asm` (often the page's own HTML) | Serve the file itself as `application/wasm`; make a single-page fallback skip `.wasm` files. |
| `ENGINE_LOAD_FAILED` | `"engine"` | The address answers 200 with real WebAssembly, but the engine did not start (a stale `app_bg.wasm`, an import mismatch, a failure in its start function). | Rebuild so `app.js` and `app_bg.wasm` come from the same build; read the console and `cause`. |
| `ENGINE_CSP` | `"engine"` | The browser refused to compile the engine under the page's Content-Security-Policy. | Add `'wasm-unsafe-eval'` to `script-src`. |
| `GPU_NONE` | `"render"` | The start failed in a browser with no WebGPU adapter (`navigator.gpu` missing, or `requestAdapter()` gives `null`) and no WebGL2. | Use a current browser with hardware acceleration on. |
| `FILE_UNREADABLE` | `"schedule"` | The browser could not read the `File` given as `schedule` (moved, deleted or locked). | Pick the file again and call `mount` again. |
| `SCHEDULE_UNREADABLE` | `"schedule"` | The `File` or `document` given as `schedule` cannot be read as a schedule (not XER, Microsoft Project XML or a schedule document). | Open it in the app it came from, or export it again as XER or XML. |

## How it is enforced

The test `the_public_surface_matches_the_page` in `crates/app/tests/architecture/main.rs` runs in `cargo test` (the `rust` CI job). It needs no wasm build and no node. It parses every `.rs` file of the wasm module, `crates/app/src/web/`, with `syn` (a `[dev-dependencies]` entry of `app`) and reads the other files as text: this page, `packages/gantt/index.html`, `packages/gantt/src/chart.html`, `crates/timeline/src/theme.rs`, every `.ts`, `.tsx`, `.mts`, `.js` and `.mjs` file under `packages/gantt/src/` and every `.css` file under `packages/gantt/src/`, except the generated `packages/gantt/src/wasm/`. Each failure names the file and line and says what to change. A failure from this test means one of these (the numbers are this page's; see the note after the list for the module doc's):

1. An export in the wasm module (`crates/app/src/web/`) has no row under "Public" or "Test-only", or a row has no export. An export is a `pub fn` (or `pub async fn`) in a `#[wasm_bindgen] impl`, a free fn with `#[wasm_bindgen]`, or a `pub` field of a `#[wasm_bindgen]` struct (named `Struct.field`, because wasm-bindgen exports it as an accessor). Fix this page, or the code.
2. An export has no `///` doc comment. Add one above it.
3. A "Test-only" name does not start `test_`, or a "Public" name does. Rename it, or move the row.
4. `wasm_bindgen` appears in another `crates/*/src` file, or a file of the wasm module has a `#[wasm_bindgen]` with arguments or a path, or a `use` that renames `wasm_bindgen` with `as` (which would hide exports behind the alias). Move the export into `crates/app/src/web/`, write the bare `#[wasm_bindgen]`, drop the alias, or extend the test. In the wasm module the check reads the syntax tree, so a doc string or string literal that names `wasm_bindgen` and a wrapped `use wasm_bindgen::{..}` pass.
5. A file under `packages/gantt/src/` outside "Test-side files" uses a `test_*` identifier, or a file other than `packages/gantt/src/test-hook.ts` names `window.gantt`, `GanttHook` or `gantt.app`. Use a Public export instead, or move the code into a Test-side file.
6. The test found no exports, no rows, no TypeScript files or no tokens. A path moved; fix the path in the test, because an empty parse would pass.
7. A `--gantt-` token used in the CSS (`packages/gantt/index.html`, `packages/gantt/src/chart.html`, `packages/gantt/src`) or in the scene's token list (`crates/timeline/src/theme.rs`) is missing from the "Theming" section, or a token listed there is used by neither. Add or remove the row.
8. `packages/gantt/src/**` (except `measure.ts`, which records the window's size in its report), the page's CSS, `packages/gantt/index.html` or `packages/gantt/src/chart.html` reads the window's size (`innerWidth`, `innerHeight`, `outerWidth`, `outerHeight`, or a `vw`, `vh`, `vmin`, `vmax` unit with its small, large and dynamic forms), or a `keydown`, `keyup` or `keypress` listener (`addEventListener` or an `on…` property) is on `window`, `document`, `document.body` or `document.documentElement`, or the `<html>` or `<body>` tag has such an attribute. The chart takes its size from its container and its keys from its own root; use the root's size or a percentage, or put the listener on the root (see "Embedding" in `docs/ARCHITECTURE.md`).
9. A selector in a `<style>` block of `packages/gantt/index.html` or `packages/gantt/src/chart.html`, or in a `packages/gantt/src/**/*.css` file does not start with `.gantt` or `:where(.gantt)`. Prefix it with the root class; the page's own reset is a `style` attribute on `<html>` and `<body>`. `@media`, `@supports`, `@container` and `@layer` blocks are read through, and `@keyframes` and `@font-face` blocks are skipped.
10. (check `entry`) An export of `packages/gantt/src/index.ts` has no row under "Page entry", or a row has no export. The failure names `packages/gantt/src/index.ts` and the line of the export, or this page and the line of the row. A form that hides its names (`export *`, `export default`, a destructuring `export const`) fails too: name each export. Add or remove the row, or the export. The same check fails when an exported declaration of `index.ts` names a type that `index.ts` imports from `./measure.js` or `./page-knobs.js` (the developer page's knobs and the measured run), directly, through an `interface` or `type` of the file, or by re-export; the failure names the line of the export and the way to the type. Pass such a value through `packages/gantt/src/page-knobs.ts`.

The module doc of `crates/app/tests/architecture/main.rs` numbers thirteen checks; this page lists the ten that `the_public_surface_matches_the_page` runs. Items 1 to 9 here are its checks 1 to 9, and item 10 here (`entry`) is its check 11. The other three are separate tests in the same crate, and they check the source tree, not the public surface, so they have no item here: its check 10 (`size.rs`, `the_tree_is_inside_its_size_budget`), its check 12 (`hosting.rs`, `the_component_and_the_hosted_app_stay_apart`) and its check 13 (`name.rs`, `the_old_name_stays_out_of_the_repository`).

The test reads the syntax tree, so the layout of the wasm module's files does not matter: comments, wrapped lines, `where` clauses, a multi-line string whose lines start at column 0, and an export in an inline `mod` or a fn body are all read as the compiler reads them. It fails closed. A `#[wasm_bindgen]` on anything but an `impl`, a fn or a struct (a `pub enum`, a `const`, a trait, a field) fails with file and line. So does the name `wasm_bindgen` inside a macro body or another attribute (a `cfg_attr`), a macro inside an exported `impl`, and a module file that does not parse. Fn bodies are not searched for anything but nested items. Each failure says to extend the test.

The test crate also has unit tests on small synthetic inputs for each of these messages, so each failure path is shown to fire.

It does not catch a name built at run time (`app["test_" + n]`, `window["gantt"]`) or a `--gantt-` token built at run time. The threat model is a good-faith author who forgets.

`pnpm typecheck` (the `web` CI job) is a second layer. `packages/gantt/src/api.ts` defines `PublicApp`, which is `App` without its `test_*` members (a `Pick` over `Exclude<keyof App, ...>`), and every file outside the Test-side files types its `app` as `PublicApp`. So `app.test_x()` there fails with `Property 'test_x' does not exist on type 'PublicApp'` and the file and line. This also catches `app['test_x']` and a renamed alias, which the text test does not. `index.ts` holds the `PublicApp` type only; `installTestHook` and `Metrics` take it and widen it to `App`, which is safe because it is the same object. A cast to `App` in any other file defeats the fence, and the text test does not catch that.

The `packages/gantt/tests` specs run every Test-only export, directly or through the scripted measurement (`?measure=1`, `measure.spec.ts`) and the `?panic=init` checks (`startup.spec.ts`), so a rename that misses a caller fails the `web` CI job.
