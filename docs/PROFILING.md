# Profiling: where the time and memory go

One command, run from the hub, builds the profile build, copies the bundle to the mini, serves it there on 127.0.0.1, and opens one benchmark cell in Chromium on the Mac mini (`ssh mini`) n times. It writes one folder. Run it before a change and after it (or with `--compare`) to see what the change did. For the benches, frame times and open-time runs, see [MEASURING.md](MEASURING.md).

```sh
node demos/bench/profile.ts --cell chain-10000 --holder <lock name> --runs 3 --out profile-out
node demos/bench/profile.ts --cell tree4-10000 --holder <lock name> --compare origin/main
node demos/bench/profile.ts --cell tree4-10000 --holder <lock name> --compare origin/main --drag --runs 10
```

Before the first run, `pnpm install --frozen-lockfile` in `apps/hosted` of this checkout (the build runs it again in its own worktree, which needs the pnpm store that install fills). The mini needs only Chrome (or Chromium) and `python3`.

## Options

- `--cell <shape>-<size>`: the benchmark schedule to open (`chain`, `tree4`, `stress`, and `tree4seq` and `tree4long`, which give `tree4`'s tasks host keys; sizes 1,000 to 100,000, see "The benchmark schedule" in MEASURING.md). Required.
- `--holder <name>`: the name this task took the maintainers' lock on the mini under. The lock is a maintainers' tool (`mini-lock.ts` in their `lifeos` checkout, which the command calls with `who`; it exits 2, naming the holder it found, unless that is `<name>`; nothing is copied to the mini first). Required, except with `--build-only`. Without that lock and the mini, run `--build-only` to build the bundles and measure them with the benches in [MEASURING.md](MEASURING.md) on your own machine.
- `--runs <n>`: how many times to open it; default 3. Each run is a fresh Chromium.
- `--compare <ref>`: run the same cell at `<ref>` and at this checkout, interleaved (ref, this, ref, this, ...), and print a before/after table: each side's median with its min to max over the runs, and the change between the medians. `<ref>` must already contain the bench page (`demos/bench/sides/ours-page.ts`) and this command's build switch. The command resolves `<ref>` to a commit sha once, before it builds anything, prints `baseline: <ref> = <sha>` (to stderr first, and at the top of `summary.md`) and builds that sha. A second cell is a second command, so pass the printed sha as `<ref>` to measure it against the same code: `origin/main` may have moved. When the runs fall in two clusters (see "Two clusters"), a second table gives the open time by cluster.
- `--out <dir>`: the folder to write; default `profile-out`.
- `--host <name>`: the ssh host with the browser; default `mini`. `--chrome <path>` is the browser's path on that host (default: Google Chrome in `/Applications`). Both sides of a compare run on this one host. The lock is read on this host too (`MINI_LOCK_HOST=<name>` for `mini-lock.ts`), so `--host dell --chrome /usr/bin/chromium` needs the Dell's own lock. A Linux host (the Dell) must have its Wayland session logged in (`wayland-1`): each run opens a window there, started with the flags and NVIDIA offload variables of MEASURING.md's GPU rows (headless over ssh gives SwiftShader), and the GPU process row is PSS from `/proc`, not the footprint `vmmap` gives, so read it against runs on that host only. The Dell's load is high while its CI runners work: read `uptime` before and after. When the host is asleep or ssh fails, the lock read fails and nothing runs: run on the mini under its lock instead.
- `--seed <u64>`: the schedule's seed; default 20261020.
- `--drag`: also run the developer page's scripted run (`?measure=1`, the one `demos/50k/measure.mjs` drives, shortened to 4 s drags, 3 repeats and no edit phase) on the stress fixture, once with the head task dragged and once with the first critical task dragged (`dragTarget=critical`), `--runs` times per side, interleaved, each side in a fresh Chromium. Without `--compare` it runs on this checkout alone and prints one set of columns. The command builds that page into `measure/` beside the bench page (the first build of a ref takes the extra Vite build) and prints one more table after the open tables: for each drag, the median over the runs of the p50 and p95 frame interval and of the drag response (pointer event to the frame that shows its recompute), the p95's min to max over the runs, and whether this checkout's median p95 lies within the ref's spread. The page uses the profile build's wasm, so its counting allocator is in both sides' frames: read the change between the sides, not the absolute frame time, and take a frame result for a per-frame row from the same machine as before and after (MEASURING.md, "Measuring frame times").
- `--ghosts <n>`: hold a proposal that moves at least `n` tasks, so the chart draws ghost outlines while it is measured (default 0: none). The command holds it through `window.gantt.app` right after the ready frame of each open run (`run.json` gets `ghosts`, the tasks it moves; the open time is the open before the proposal) and on the first frame of each `--drag` page, so it works on any `--compare` ref. The proposal is a week-late start for the first row that moves, then for rows whose slip moves enough more tasks, up to the 10 changes the app holds; it stops with an error when they move fewer than `n`. A chain's first task moves every task after it, so `n` is a floor: `tree4-50000 --ghosts 500` moves 500 (five chains of 100), and on the `--drag` page (the stress fixture), where a slip of one of the first 120 rows moves at most 187 tasks and the head task's moves 49,967, it holds the head's 49,967.
- `--before-edit` (with `--drag`): the drag page gets `?beforeEdit=1`, a before-edit function that allows every change. A `--compare` ref that does not know it measures the page without one.
- `--groups <k>` (with `--drag`; default 0: the plain fixture): the drag page groups its stress fixture by a `Phase` activity code with `k` values, about the same number of leaves each, and the drag table is headed by a line that names the count. A `--compare` ref that does not know `?groups=` measures its plain fixture.
- `--memory-infra`: also print the GPU and renderer processes' memory by allocator (see "The folder").
- `node demos/bench/profile.ts --cell <shape>-<size> --build-only` builds the bundles, prints where they are and exits.
- Progress and stalls: the command prints one line to stderr for each finished session (`before session 3/10 done`; with `--drag`, also one after each drag of a session). When no session finishes for 15 minutes, or the process has not ended 2 minutes after its last session, it closes the session on the mini (for at most 20 s, as Ctrl-C does), prints `no session finished for <n> minutes; last: <the last line>` and exits 3, so the task that holds the lock sees a non-zero exit with a reason and releases the lock itself. A drag page that gives no result in 2 minutes ends the command with a line that names the page address, its message line (the measured run's progress, or why it failed to start; `(unavailable)` when the page does not answer within 5 seconds), its console errors, its page errors and its failed requests.

## Two clusters

On the mini, `mount to ready frame` of one bundle lands in a fast cluster (about 260 to 410 ms) or a slow one (about 520 to 710 ms), and a run's cluster changes in streaks of several runs, so a whole-run median moves with the mix of runs and not with the code (gantt#2120). In a slow run the renderer's main thread is idle until the first commit, which comes about 435 ms after the mount mark (about 230 ms in a fast run), and the time is in the renderer's thread-pool workers, which run the same tasks about 1.5 times slower. Ruled out on `chain-10000`: a display refresh (frames come as soon as the first commit exists), a cold GPU process (opening a WebGPU device first made 12 of 12 runs slow), and a slow main thread (a fixed loop before the page loads took 46 to 72 ms in 16 runs, all slow). Not found: why the workers run slower. So the command does not remove it. With `--compare`, when the open times of both sides together have a gap of at least 6% of their median with 3 or more runs on each side, it prints `mount to ready frame by cluster`: one split point for both sides (the middle of the largest gap), the runs of each side in each cluster, and the change inside each. Read the engine rows first, then the slow cluster's change with its run counts. A cluster with runs of one side only shows no change: that is a different mix, not a result. The Dell shows the same streaks as a slow drift between about 320 and 770 ms, with no gap, so its table has no cluster rows. The line below the table, `mount to ready frame in pairs`, is the median over the runs of the second side's time divided by the first side's of the run taken next to it, which a streak shared by both sides leaves out.

## The build

`scripts/build-web.sh --keep-names` builds `wasm-release` with the wasm `name` section kept (function names) and the app's `alloc-stats` feature on, a counting allocator. The shipped `wasm-release` build is still stripped and has no allocator; this build is for profiling only. The command runs it for you, with `CARGO_TARGET_DIR` under `~/.cache/cargo-target/gantt/profile` unless you set it, then builds the bench page with the hosted app's Vite settings and writes the cell's data into it. It is always built in a git worktree under `~/.cache/gantt-profile/<commit>-<cell>`, so this checkout's `packages/gantt/src/wasm` (the shipped build's output) is never overwritten. A clean commit's build is reused; this checkout with uncommitted changes to tracked files is applied to a fresh worktree and built again each time (untracked files are not carried over). `build-web.sh` fails if the wasm has the allocator's export without `--keep-names`, or lacks it with it.

## The folder

`<out>/summary.md` is the table printed at the end (the median of each number over the runs). `<out>/run-<k>/` (`<out>/before/run-<k>/` and `<out>/after/run-<k>/` with `--compare`) holds, for each run:

- `run.json`: the numbers below.
- `trace.json`: the Chrome trace (load it in `chrome://tracing` or Perfetto), with the CPU profile on.
- `flame.svg` and `flame.folded`: a flame graph of the renderer main thread with Rust function names, and the folded stacks it was drawn from.

The numbers, all from one page load:

- **Phase table**, in ms from the navigation, from the page's own marks (`library-ready`, `data-start`, `mount-start`, the first mark of each name, as the bench's load phase reads them) and the first ready frame (the frame after the chart holds the cell's rows): navigation to library ready, library ready to data start, data start to mount (the fetch), mount to ready frame (the open, parse, schedule and first draw), and the total. The page is served from the mini itself, so the library row has no hub-to-mini transfer in it.
- **Engine allocation counts**: peak live bytes and the number of allocations, from the counting allocator (`App.test_alloc_stats`).
- **`memory.buffer`**: the size of the wasm memory.
- **GPU process memory** at 20 s after the ready frame: the physical footprint (`vmmap --summary` on the mini) of the browser's GPU process.

With `--memory-infra` the command also turns on Chrome's own `disabled-by-default-memory-infra` trace category and asks for one memory dump (`Tracing.requestMemoryDump`) at the same moment as the GPU footprint read, 20 s after the ready frame. The dump is found in the trace by the guid Chrome returned for the request, so no other dump in the trace is read, and the command stops with an error when the dump is missing. It prints a second table after the first: the GPU process and the renderer process, each broken down by the dump's top-level allocator names (`malloc`, `skia`, `gpu`, `v8`, `shared_memory`, ...) in MB, largest first, the median over the runs; with `--compare` the table has one column per side. `run.json` holds each run's bytes under `allocators`. The allocators overlap (`shared_memory` and `malloc` hold bytes that others also count), so the rows do not add up to the process, and an allocator the dump gives no size for is left out. Where several renderers exist (a spare one), the one with the most bytes is shown. The category adds its own tracing cost, so compare phase times only between runs that both used the flag or both did not. Without the flag the output is unchanged.

## Where the mini is used

Every step that touches the mini is in `demos/bench/profile-mini.ts`. Per run it copies the bundle to a scratch directory there and serves it with `python3 -m http.server` on 127.0.0.1 (a free port, so no phase includes a transfer from the hub), starts a fresh Chromium with `--remote-debugging-port=0` and a temporary profile (it reads the port Chrome chose from `DevToolsActivePort`, so no port is assumed and no other browser is attached to), forwards that port to the hub, where Playwright drives it, and reads `vmmap`. When the run ends it stops the two processes it started, by pid (TERM, a wait of up to 5 s, then KILL), and removes the two temporary directories. Ctrl-C (or SIGTERM, SIGHUP) on the hub, even during the open, runs that same close (for at most 20 s) and exits 130. Everything made on the mini carries a marker, a temp directory named `gantt-profile.<id>` (Chrome's profile and the page server's folder are in them); a run that was stopped hard leaves them, so each run first stops any process whose command line holds such a path and removes such directories, and touches nothing without the marker. Run one profile command per mini at a time: a second one's start sweeps the first's. The build worktree is removed when the build ends; the bundle stays in the cache.
