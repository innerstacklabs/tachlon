# The demo page

How the demo page is built and served, what it shows, its URL options, how the Playwright specs check it, and how the screencast is recorded. The keys table is in [KEYS.md](KEYS.md); the measurements are in [MEASURING.md](MEASURING.md).

## Running it

Building from source is the developer route. A scheduler who wants to open a file uses the hosted app, which the README links to as the live demo; it needs no install and no sign-in.

The 50k demo needs the `wasm32-unknown-unknown` Rust target, `wasm-bindgen-cli` at the version in `Cargo.lock` (0.2.129; `cargo install wasm-bindgen-cli --version 0.2.129 --locked`) and pnpm.

```sh
demos/50k/run.sh                          # builds the wasm and the bundle, serves http://127.0.0.1:4173/
demos/50k/run.sh --schedule <file.xer>    # starts with your own P6 XER or MS Project XML file
```

The browser tab reads the product name, then ": 50k timeline".

The print demo, `demos/print/run.sh [--out <dir>]`, opens the same page at `?n=5000`, turns on the Longest path filter and a 26-week lookahead window, and saves the printed pages as `print.pdf`: US Letter landscape, two pages of 40 rows. The whole longest path is 333 rows on 14 pages. It needs Playwright's Chromium and builds the page when `packages/gantt/dist` is missing. The script adds the paper rule (`@page { size: letter landscape; margin: 0 }`) itself. `demos/print/test-print.mjs` runs it and counts the pages (`/Type /Page` objects, not `/Pages`); the `checks` leg of the `web` job runs that test after the Chromium install.

## What you see

- Zoom: Ctrl+wheel or a trackpad pinch zooms at the cursor, from years down to hours.
- Pan: drag pans both axes.
- Scroll: the plain wheel scrolls rows.
- Status line: `s` shows it under the chart (this page only; the hosted app shows a shorter speed line).
- Fit and Find: they ease the view over 300 ms, and any wheel, pinch, drag or key stops the flight.

What you see: 50,000 generated tasks, one per row in outline order (each summary above its children, drawn as a thin dark bracket with an end tick at each end), critical tasks in red, the only color besides the selection, and 2 px taller than a normal bar (ordinary bars are the linework blue and the summaries, links and grid stay quiet, so only the critical path is red; a normal bar is half the 24 px row, 12 px high with 2 px corners, `--gantt-bar-h` and `--gantt-bar-r`). The axis is two tiers (months over weeks, weeks over days) in the 48 px head band (`--gantt-axis-h`, two tiers of 24 px); once a day is wider than 3 px the non-working days of the schedule's calendar are shaded as columns under the bars, and a file's data date is a line with a tag on the axis. Ctrl+wheel or a trackpad pinch zooms at the cursor (years down to hours), drag pans both axes, the plain wheel scrolls rows. Press `s` to show the status line under the chart: it names the backend, the visible rows, the task under the pointer, the frame interval (p50, p95 and missed frames over the last 120 frames) and the CPU time of `App.frame()`. A legend strip, 22 px tall, is the last row under the chart (and under the status line when that is shown): a swatch and a label for each entry of the printed legend (Task, Critical, Deadline, Start constraint, Finish constraint, Summary, Dependency, Data date, Non-working day, Proposal ghost, Just-moved outline), each swatch the color of its theme token (`--gantt-bar`, `--gantt-crit` for Critical and for Deadline, the missed-deadline tick, `--gantt-text` for Start constraint and Finish constraint, the cap on a held bar, `--gantt-sum`, `--gantt-link`, `--gantt-today`, `--gantt-nonwork`, `--gantt-sel-edge` for the two outlines), so it follows the theme; it is not drawn in print. Above the chart is the toolbar strip: Open… and, once a file has notes the importer did not apply, an import-notes button; a Filters menu (below); Baseline (Set, Add new, Clear) and Variance; Progress; Insert and Delete; Collapse to level (1, 2, All); zoom out and in and Fit; the data date; the row count and Find. The Filters menu and Find are the app's chrome (`apps/chrome`), built only on the chart's public API (`commands`, `state()`, `filterInputs()`, `busy()` and its events); the chart works without them, with an empty place in the toolbar for each. The status line is this page's own: in the hosted app `s` shows a shorter speed line (the open time and the frame p50 and p95) instead. The controls and the keys ([KEYS.md](KEYS.md)) do the same things. Fit and Find ease the view to their target over 300 ms; a wheel, a pinch, a drag or a key stops the flight where it is, and with reduced motion the view jumps.

Click a bar (press and release within 4 px and 300 ms) to select it. A click on a summary bar selects the summary and highlights it and all its descendants; its driving path is empty. A dependency drives its successor when it alone sets the successor's early start (`Schedule::driving_predecessors` and `driven_successors`). The selection highlights the chain of driving predecessors back to a task with no driving predecessor, and the driven successors forward, in an accent color; every other bar and arrow dims to 40%. Each direction holds at most 2,000 tasks; the status line says when a chain is capped. The chain is computed once per click and again after the next recompute. A new selection lights the path over 300 ms instead of at once: the selected task first, then its driving predecessors one after another, nearest first, on an ease-out curve; the driven successors light with the last frame. With the page's reduced-motion setting on, the whole path shows at once. Selecting a different task restarts the reveal; an edit that rebuilds the same task's path does not replay it. The reveal adds no rectangles; while it runs, each frame does one pass over at most 2,000 ranks. Escape or a click on empty space clears the selection, and the table scrolls to the selected row and marks it.

Press Ctrl+F (Cmd+F on macOS) with the chart focused to go to the find box in the toolbar and find a task by name. The browser's own find does not reach the canvas, so the chart takes the key while focus is inside it; with focus elsewhere on the page the key is the browser's. Typing in the box selects the first task whose name contains the text (case-insensitive, matched against the full outline path, which the table shows as a row's tooltip, computed in Rust), and the table and the timeline scroll to it; a match inside a collapsed summary expands the summary. With a row filter on, find searches only the rows the filter shows: a task hidden by the filter is neither counted nor selected, and changing the filter re-runs the query. Enter goes to the next match and Shift+Enter to the previous one, both wrapping around; the box shows "3 of 41" or "no matches", and, when a row filter or Lookahead is on and nothing matches, the note keeps "no matches" and its tooltip reads "no matches in the shown rows", so an empty result is read as a search of the shown rows only. Escape clears the box, returns focus to the chart and keeps the selection. A query that is a whole real date written `YYYY-MM-DD` (gs#391) goes to that day on Enter instead of stepping through names: the keystroke that completes the date does not jump to a task whose name holds it (the keystrokes before it search names as usual), and Enter pans so 00:00 on the day sits a fifth of the way in from the left, keeps the zoom, and scrolls so the first row whose bar starts on or after the day is the top row (a day after every bar only pans). It selects no task, and an existing selection stays; the box shows "went to date". Text that is not a real date (`2026-02-30`, `2026-02`) searches names exactly as before, Shift+Enter included. A bad date or a bar drag leaves the view as it was (`App.go_to_date`).

Zoomed in far enough, each visible bar shows its task name (the last outline segment, as in the table): inside the bar, in the theme's `bar-text` color (white in the light theme), when the text plus 8 px fits; otherwise just right of the bar, in the theme's `text` color, when the free space up to the canvas edge fits it; otherwise nothing. A name right of a task bar starts past the bar's link terminal (`terminal-gap + terminal-size`, 11 px by default, gs#440), so the dot of the hovered bar is never under its name, and that stretch counts against the free space; a summary bar has no terminal and its name starts at the bar's end. A row shorter than 16 CSS px, a bar narrower than 8 px (a year across the canvas leaves only milestones and summary spans wide enough) and a bar cut by the axis band or the bottom edge get no label. A summary bar is thinner than the text, so its name goes beside it. At most one label per row. The names are drawn with glyphon like the axis; `crates/timeline/src/labels.rs` places them and `Renderer::measure_bar_label` shapes a name once per task and keeps the buffer while the task is in view, so a pan or zoom reshapes nothing. The text colors are the theme's `bar-text` (inside) and `text` (outside) tokens, defined once in `crates/timeline/src/theme.rs`. `App::test_bar_labels()` exports the placed labels for the specs.

Left of the canvas is the task table (it opens at half of the chart's box, between 420 and 800 px, `--gantt-table-w`: 640 px of a 1280 px chart, leaving a name column of about 300 px, enough for the office fit-out's longest name; a progress column joins the pane only while Task keeps 280 px, so at 1280 px the fit-out shows every name whole and its progress columns sit off to the right, reached by scrolling the table, gs#703; Start and Finish are 100 px each, `--gantt-date-col`; gs#411, gs#821): name, duration, start, finish and float, as DOM rows (the Progress button adds the Actual start, Actual finish, Remaining and % columns, and with a baseline, the Start, Finish and Float variance columns appear, which the Variance button hides or shows; the Columns button opens a panel that hides or shows Start, Finish and Float, by `data-hide-start`, `data-hide-finish` and `data-hide-float` on `#table`, `packages/gantt/src/columns-menu.ts`, and moves Dur, Start, Finish and Float up or down its list, which puts the column left or right in the head and every row and in the cell cursor's walk, by `data-column-order` and the `--order-<column>` and `--track-<n>` properties on `#table`, `packages/gantt/src/column-order.ts` (a drag of one of the four head cells onto another puts it in the other's place, and the target shows a bar on the side it will land on, `data-drop`, `packages/gantt/src/column-drag.ts`, `column-order.spec.ts`); the order lasts until the page is reloaded and nothing is stored) (a file with P6 activity IDs adds a first "ID" column, 92 px, and a file with WBS codes a "WBS" column after it, gs#703; the cell cursor walks both; a file without IDs, such as MS Project XML or the demo, has no such column; the toolbar shows the data date of a file that states one: a P6 file's last recalculation date or an MS Project file's status date, gs#563), styled in the Ledger design (gs#110 PR 2). The name column shows each task's leaf name (`Pour slab`; its tooltip is the generated construction path, `Level 3 / Concrete / Pour slab`), indented 14 px per outline level, with a 14 px gap on a leaf where a summary has its chevron. A summary row is a tinted band in semibold. A critical task has a filled red diamond in the left gutter and a semibold red float. Float is in working days of the task's calendar (`3d`, `2.5d`, `0d`; `App.task_float`; no decimal from 100 days up; the cell of a finished task is empty, not `0d`), and its heading says so when hovered: `Total float, in working days of each task's own calendar`. Selection is a full-row tint and a 3 px accent edge, hover a pale fill; the canvas fills the same row with the same `--gantt-sel` and `--gantt-hov` tokens, and a pointer on a table row hovers that row on the canvas too (`App.set_hover_row`). The column grid is one token, `--gantt-cols`; the ID column puts one more track in front of it (`--gantt-id-col`). The divider between the table and the canvas is a 6 px strip over the table's right edge (`#split`, `packages/gantt/src/split.ts`, gs#412): drag it to set `--gantt-table-w` in px on the chart's root, at least 420 px and at most the chart's width less 320 px (so the canvas keeps 320 px); a double-click puts the default back (or the value the host's page has set inline by then); with focus on the strip, `Left` and `Right` move it 16 px. The canvas follows through its resize observer, and nothing is saved, so a reload opens at the default. Every rule sits under the chart's root class. Names and the outline are app-owned in `crates/app/src/names.rs` and `meta.rs`, not in the engine. Only the visible rows plus six above and below exist in the DOM (about 47 at 800 px; the rows are redrawn when the view leaves them or the dates change), inside a spacer as tall as all the visible rows (`rowCount`), so the browser scrolls it natively. The table's `scrollTop` and the canvas's vertical scroll are one value: scrolling either moves the other. Dependency arrows are drawn between bars for the links in view: a link is drawn when one of the five segments of its path (out of the predecessor by a stub, along the boundary between rows, down to the successor's row a stub short of its bar, in) crosses the canvas and the visible rows. They are found through an index of the links by row (`timeline::scene::LinkIndex`): a binary search for the links of up to 256 rows, a scan of the few longer ones, never a scan of all. Bars draw over the arrows.

While the task list scrolls, a small label at its right edge says `Row N of M` (N is the row at the top of the list, M the row count) and hides one second after the last scroll (`packages/gantt/src/row-position.ts`); it is a DOM element the table's scroll handler writes, so a scroll adds one text write and the frame loop does no work for it. `packages/gantt/tests/row-position.spec.ts` checks it on `?n=2000`.

The hosted office fit-out sample (`apps/hosted/samples/office-fitout.ts`) assigns one or two named crews to each of its 47 activities that is not a milestone, as `Resources` and `Assignments` in its MS Project file, which the reader keeps on `ImportedTask.resource_names`; nothing on the page shows the names yet, and the reader's note "47 tasks have resource assignments; only the resource names were read, and no dates are affected." is marked expected in `samples.json`, so the toolbar has no notice (`apps/hosted/tests/sample-notes.spec.ts`, gantt#703).

A leaf's Start cell that holds a real start constraint (a bar drag, a typed Start or a P6 `CS_MSOA` above the task's import floor, `App.task_constraint_text` is not empty) carries `data-constrained="true"`, a small triangle in its top right corner (`table-cells.css`) and a `title` of `Start no earlier than <date>`; a task that holds only its import floor, and a summary, has none (gs#703 K7; `tests/start-mark.spec.ts`).

A summary row has a disclosure chevron in its name cell, a button with `aria-expanded`. Click it to hide or show the rows beneath it; every summary is expanded on load, and a child summary that was collapsed stays collapsed when its parent expands. A summary row shows its rolled-up start and finish and no float. Double-clicking the chevron edits nothing. The task count in the status line is the number of live tasks (a deleted task is not counted); the table and the `rows` line count the visible rows.

Press `1` to `9` to collapse every summary to that outline level (`1` shows only top-level rows), or `0` to expand all. Alt+Left collapses the selected summary; on any other row it selects the parent. Alt+Right expands the selected summary. While the rows are grouped (Filters, Group), Alt+Left closes the focused header's own group, or else the selected task's group, and Alt+Right opens it. These keys do nothing while a text box has focus. Collapsing to a level keeps the active row filter on, and none of these actions is an undo step, just like clicking a disclosure triangle.

Keys act only while focus is inside the chart (`docs/ARCHITECTURE.md`, Embedding, rule 2): the listener is on the chart's root element, and nothing listens on the window or the document. The page starts with focus on the chart, and a click anywhere in it takes focus back. Click outside the chart and the keys stop; click the chart again to resume.

The chart is a component that fits in any box (gs#100 PR 4). It is as big as the element that holds it, it follows that element when it resizes, and its style rules all start with the `.gantt` class, so it does not restyle the page around it. The page that holds it gives it a height; the demo page does so with `style` attributes on `<html>` and `<body>`. A page may hold several charts, each in its own root (gs#1083): each has its own ids, selection, view and frame errors, and a frame that fails in one leaves the others drawing. They share one WASM module, so a panic in one stops every chart on the page, and each shows the panic in its banner and reports it once through `on("error")`; only a reload recovers. The three rules and the tests that keep them are in `docs/ARCHITECTURE.md`, "Embedding".

The "Critical only" button in the Filters panel of the toolbar (or the `C` key, Shift+c) hides every row whose task is not critical, meaning zero total float and not finished (decision 0008). Each critical task's summaries stay as context rows, so the outline still reads. The header then shows "Critical only" pressed and the count of the activities it keeps (the summaries above them are rows, not activities), for example `Critical only · 21 of 50,000 activities`. It combines with collapse: a collapsed summary that holds a critical task stays, and its children stay hidden. Turning it off restores the previous view, collapse state included. After a drag, an edit, an undo or a redo changes which tasks are critical, the rows follow the new schedule; during a bar drag the rows hold still, so the dragged bar does not vanish under the pointer, and they refresh on release. The `c` key still jumps to the next critical task among the visible rows. The stress fixture has no outline, and the toggle does nothing there.

The "Longest path" button beside "Critical only" (or the `L` key, Shift+l) shows the tasks on the longest path. It starts from every task that finishes when the project finishes and walks back along the driving relationships. These are the dependencies that alone set a task's early start, the same relationships used for the driving path of a clicked bar. When two predecessors set the same start, both chains stay. This differs from "Critical only," which means zero total float and not finished. A zero-float task can fail to drive anything. For example, a predecessor on a weekday calendar can have zero float when its successor is pinned by a start-no-earlier-than date on a 24/7 calendar, but it is not on the longest path. Summaries that hold a longest-path task stay as context rows, as they do for "Critical only." The row filter is one setting with seven values, one at a time: Off, Critical only, Near critical (at most ten working days of float), Longest path, Slipped (tasks that finish later than the baseline; its button shows only when a baseline is set), Show moved (the tasks the last edit or drag moved; its button is disabled until there is a move report) an activity code (the code-type and value boxes, for a file with P6 activity codes) and Start constraint (the tasks whose start-no-earlier-than is above their import floor, the ones the hover card gives a "Start no earlier than" row) and Check (the tasks one link check counts, Missing logic, Open starts or Open ends, as the Checks window does: a choice under Status) and Resource (the tasks that name one resource: a choice under Status that lists the file's resource names, shown only for a file that names some). Choosing one value replaces the previous one, and each button is pressed while its filter is on. The header shows the active filter and, for Critical only, Near critical and Longest path, the activities it keeps, for example `Longest path · 109 of 50,000 activities` (the other filters show the visible row count); with Longest path on, a line at the chart's bottom left names the path, for example `Longest path: Excavate to Handover · 14 activities · 212 days` (the first and last activity, how many activities it holds, and the calendar days from the first start to the project finish); every filter is named there, so `Near critical`, `Float lost`, `Joined critical`, `Left critical`, `Start constraint` and the Status, Check and Resource choices (`Status = In progress`, `Check = Open starts`, `Resource = Crew A`) read the same way. It combines with collapse, and find searches only the shown rows. After a drag, edit, undo or redo, the rows follow the new schedule. During a bar drag they hold still and refresh on release. The stress fixture has no outline, so the button does nothing there. The key does nothing while a text box has focus.

The "Lookahead" button in the Filters panel, with its date box and weeks box (gs#96), keeps only the activities that are active in a date window. The boxes start at the file's data date and 3 weeks, or at the project's first Monday (5 January 2026 in the app's calendar) when the file has no data date. The window runs from 00:00 on the date for the number of weeks (1 to 520). An activity is in it when its computed early dates intersect it: it starts before the window ends and finishes after the window starts, so one that finishes exactly at the window's start is out, one that starts on the window's last day is in, and one that starts exactly when the window ends is out. A milestone is in when its date is in the window. Summaries that hold an activity in the window stay as context rows, as they do for "Critical only", and a collapsed summary that holds one stays with its children hidden. Unlike the row filters above, the window is not one of their values: it is a second limit that combines with them, so with "Critical only" on and a window set the table shows the critical activities that are active in the window, and turning either off leaves the other. It combines with collapse, and find searches only the shown rows. Change the date or the weeks while the window is on and the rows follow; a value the app refuses (no date, 0 or more than 520 weeks) leaves the last window and marks the boxes invalid. The header shows the active limits and the visible row count, for example `Lookahead · 54 of 50,000 rows`; with Critical only, Near critical or Longest path as well, the count is of activities, as it is without the window. After a drag, edit, undo or redo the rows follow the new schedule, and during a bar drag they hold still and refresh on release. Opening another file removes the window and resets the boxes to the new file's defaults. The stress fixture has no outline, so the button does nothing there. The chart's keys do nothing while a box has focus.

Hovering a bar shows a card next to the pointer with the task's name and outline path, start and finish, late start and finish, total float in working days and hours (`task_details` in `crates/app/src/lib.rs`, with a day being the task's calendar's working day; a negative float has one minus sign, `-1 d 2 h`) followed, when it is a day or more, by the same float in calendar days (`App.task_float_calendar_text`: `5 d 0 h (7 calendar days)`, the whole days from early finish to late finish), the task's Calendar (`App.task_calendar_text`: `5 days a week, 8 h a day`), critical yes or no, `Driven by` (`App.task_driven_by`: the predecessors whose links set the task's start, up to three outline paths, one a line; a task that starts at the project start or at its constraint has no such row), and the predecessor and successor counts with the first three names of each, each with its outline path and its link's type and lag (`Level 3 / Concrete / Pour slab (SS+2d)`). The title carries the activity ID when the file has one. A task that is not a summary and has a start-no-earlier-than above its import floor (from a bar drag, a typed Start or a P6 `CS_MSOA`; a task that holds only the floor an import gave it has none) also shows `Start no earlier than` after Finish (`App.task_constraint_text`: `2024-01-15 08:00`); a task without one shows no such row. A task that is not a summary and has an MS Project `Deadline` also shows `Deadline` after it (`App.task_deadline_text`: `2026-01-12 16:00 (missed by 2d)`, the days its finish falls after it, or the date alone when it finishes in time); a file with none, the sample included, has no such row. The canvas marks the same task: a bar whose early finish falls after its deadline has a 2 px tick in `--gantt-crit` at the deadline, 2 px taller than the bar at each end (`timeline::scene::Backdrop::deadlines`); a task that meets its deadline or has none has no tick. The canvas also marks a task held by a real start constraint, the one the card's `Start no earlier than` row shows and the Start cell's mark flags: a 3 px cap in `--gantt-text` on the bar's left edge, over the body (`timeline::scene::Backdrop::start_constraints`, answered per drawn bar by `Session`, so a frame costs the rows in view). A task that only holds its import floor has none, a task with actuals has none (its own start-no-earlier-than no longer binds, decision 0008, so the card names none either), a summary has none, and a bar that starts off the left of the canvas, or is under 6 px wide, has none; a bar drag that leaves a start above the floor puts the cap on, and a drag back to the floor, or an undo, takes it off. A task with a start-no-later-than or a start pin and no actual start has the same cap on its left edge, and a task with a finish limit or a finish pin and no actual finish has it on its right edge (`StartConstraints::holds_finish`), under the same size and off-canvas rules; the card, the Start cell and the Start constraint filter still mean start-no-earlier-than only. A task that is not a summary also shows Status, and Actual start, Actual finish and % complete once it has them, and, when the file has a baseline, Baseline start and Baseline finish with how far each moved from the baseline. The card is DOM (`#hover-card`), rebuilt at most once per frame and only when the hovered task changes, and hides when the pointer leaves the bar or a drag starts. For a summary the card shows the rolled-up start and finish and the link counts, and leaves out late start and finish, float, calendar, critical and driven by.

Double-click a task's name or duration cell to edit it in place (or edit from the cell cursor, below): Enter commits and moves the cell cursor down, Tab and Shift+Tab commit and move across, Escape (or clicking away) cancels. A duration is typed in working days (`3d`), hours (`4h`), minutes (`30m`) or a combination (`1d 4h`), on the task's calendar, where a day is that calendar's working day; a number with no unit is days (`5` is `5d`, and a link's lag follows: `FS+2` is `FS+2d`), and `0` makes a milestone. A result below zero or unparseable input is refused: the cell shows the error and nothing changes. A duration with a sign adds to or takes from the task's current duration (`+3d` on a 5d task makes `8d`, `-1d` makes `4d`). A rename replaces the last segment of the outline path (and the same prefix in the task's descendants) and recomputes nothing. A duration change recomputes through the duration cone (`Schedule::recompute_duration_cone_moved`, gs#58; gs#380 wires it into `Edit::SetDuration`): it redoes the task's own late dates and its predecessors' float even when the finish does not move, rolls up only the summaries above the tasks whose early dates moved (`Outline::rollup` rebuilds every summary instead when more than half the tasks moved), and falls back to a full `compute` when the cone is wide, when the project finish moves, or when an early start lands past its late start. The cone is exact only when the solution equals `compute()` before the edit, which holds because moves and duration edits preserve that equality, insert, delete, restore and link edits full-compute, and a rename leaves the schedule unchanged. `crates/app/tests/duration_cone.rs` checks the solution and every summary against a full `compute()` on a clone after each step of link-then-duration-then-undo sequences and a random mix. A link is added, removed and restored through `Session::edit` too (`Edit::AddLink`, `RemoveLink`, `RestoreLink`; the chart gesture is an Alt-drag from a leaf bar, or a drag from the dot beside the finish end of the hovered or selected bar, onto another bar: the release adds a finish-to-start link as one undo step, selects it, and the preview line and the cursor turn to the refused look (red line, `not-allowed`) while the drop would be refused; a refused release shows the app's message in the alert line over the chart, like a refused row edit, and the next press clears it; Escape during the drag, and a release on empty canvas or on the dragged bar, add nothing; a click on an arrow selects the link and `Delete` or `Mod+Backspace` removes it, ahead of any selected row): the app refuses a link to a summary, a repeat of a live link, and a loop (the message names the loop), re-solves with a full `compute`, and undo and redo bring back the same link. A duration edit, a bar drag, an undo or a redo that moves other tasks leaves a move report (`Session::move_report`, `status.moved`): `8 tasks moved · finish +7 days`, the count leaving out the edited task, the finish clause present when the project finish moved by a calendar day or more. A drag makes one report at the release, with the positions the tasks had at the press; a cancel, or a drag back to its start, makes none. A drag of a leaf bar's right end (the last 6 px, `Timeline::hit_edge`) sets the task's duration to the working time from its start to the end of the day under the pointer, as typing that day in the Finish cell does; it is one undo step, a started task says why in the chip above, and `Status.gesture` reads `resize-pressed` then `resize-dragging` (`crates/app/src/press/resize.rs`). Any other change clears it. A drag on a finished task does not move it and leaves a calm note, `<name> is finished: its dates are its actuals. Change Actual finish in the table to move it.`, in a chip for about 6 seconds, until the next press clears it. The chart draws a dashed outline at the old place of each moved task that has a visible bar (a plain bar, not a summary), under the bars, for about 4 seconds and then fades it over 0.4 seconds; a drag release shows the press-time places. It draws at most 400 outlines, the ones nearest the center of the canvas; the text and the count still cover every moved task. The page tells the app whether it asked for no motion: `packages/gantt/src/motion.ts` reads `prefers-reduced-motion: reduce`, and `index.ts` sends it to `App.set_reduced_motion` after `App.create` and on every change (gs#485, story S3.5 of gs#427). `status.slide` is `{ active, copyMs }`: `active` is true while a slide runs, and `copyMs` is how long the copy of the last slide took, or `null` before the first one. With reduced motion off, the frame (`Session::advance_motion`, then `Session::display_dates` for every drawn position) slides the tasks an edit, undo or redo moved from their old places to the new ones, so bars, arrows, bar labels and the link dot move as one picture; with it on they jump (gs#487); opening a file draws the bars of the first screen in the same way, each growing from its start to its finish in turn over 360 ms (gs#309), and a scroll, a zoom or an edit ends it at once; `packages/gantt/tests/reduced-motion.spec.ts` checks `status.slide` under `page.emulateMedia`. Every person's edit goes through `Session::edit`, which applies it and records its inverse; a whole bar drag is one edit (`crates/app/src/history.rs`, `Session::edit` and `Session::commit_drag`). A dragged bar lands on a working-day start of its task's calendar (08:00 on the office fit-out; `Calendar::day_start_at`, gs#863): the start the pointer asks for is the first working minute of the working day that the engine would put it on, so a task, its successors and the summaries above keep whole working days, and the table and the bar show that start while the pointer is still down. A drag that ends back at the press leaves the start the file gave, even mid-day, and a milestone keeps the pointer's minute (it may also sit at a working-period end). `crates/app/tests/drag_day_start.rs` and `apps/hosted/tests/drag-day-start.spec.ts` check it. Ctrl+Z undoes; Ctrl+Shift+Z or Ctrl+Y redoes (use Cmd instead of Ctrl on macOS). History keeps 200 steps, and undo and redo are off while dragging a bar or editing a cell. While a cell is edited the hover card is hidden and a press on the canvas starts no drag. While a bar or a link is pressed or dragged, the keys, the editors and a second press (a second finger) do nothing, and an arrow key, Home, End, PageUp and PageDown are taken and do not scroll the host page (`Status.gesture`, gantt#1152).

What moved (gs#489, story S5a of #429): after an edit, an undo, a redo or a drag release that moved other tasks, the chart shows the report as one line of text at the top right of the canvas (`#moved-note`), for example `8 tasks moved · finish +7 days`. It shows at full opacity for 4 seconds and then fades out over 0.4 seconds, the same clock as the dashed outlines (with reduced motion on, it stays at full opacity for 4 seconds and then goes at once, with no fade, and the outlines go with it); the app computes the opacity (`status.moved.alpha`) and the page only sets it. A new report replaces the text at once; any other change (a rename, an insert, a delete), and opening a file, hides it. The page writes to the note only when something changed, so an idle frame costs nothing. While the pointer is over the note it stays at full opacity (`App.set_moved_hold`); when the pointer leaves it keeps the time it had left, and at least 1 second more, before it fades, and hiding the note or opening a file ends the hold. The note takes the pointer only while it shows text, so the chart under it gets no hover or drag there, and it takes no focus, and it sits inside the chart root in the canvas's grid cell, so it follows the canvas when the task list divider moves and when the chart is embedded in a host box. `packages/gantt/tests/moved-note.spec.ts` runs the 3.9 s and 4.5 s checks on Playwright's fake clock (`page.clock`) and the hold by the pointer; `packages/gantt/tests/moved-note-reduced.spec.ts` runs the 3.9 s and 4.05 s checks with reduced motion, and the note and outlines after a drag release.

Insert and delete rows (gs#50): `Insert`, or the toolbar's Insert button, adds a task named `New task` of 1 working day as a sibling after the selected row's whole subtree, at its level (with nothing selected, the last top-level row), and selects it; the `Insert` and `Mod+Enter` keys also put the cell cursor on its name, so typing names it (the button does not move the cursor). `Delete` or `Mod+Backspace`, or the toolbar's Delete button, deletes the selected row and selects the next visible row's task, else the previous, else none; the successors are re-solved. `Mod+Enter` is the same command as `Insert`, and `Mod+Backspace` the same as `Delete`, for a Mac keyboard (gs#418): `Mod` is `Ctrl` or `Cmd` with no `Alt` and no `Shift`, so `Alt+Enter` and `Shift+Enter` insert no row (`Alt+Enter` pins the card, `Shift+Enter` opens the task dialog), and a refusal shows in the same alert line. Plain `Backspace` deletes no row (it opens the cell editor empty while the cell cursor is in the list, gs#421); like `Delete`, `Mod+Backspace` deletes a selected link before any row (`rows.remove()`). Both are one undo step each, and undo restores the row, its dates and the selection. A refusal shows in the alert line over the chart and changes nothing: deleting a summary ("Delete or move its sub-tasks first."), deleting with nothing selected, inserting while "Critical only", "Longest path" or "Lookahead" is on ("Clear the row filter or window to insert a row."), or acting during a bar drag. The line clears on the next successful edit or when dismissed. The keys do nothing while a cell or the find box has focus. A new bar starts at the project's left edge until it is linked. A search in the find box runs again after an insert or delete.

Cell cursor (gs#416, story S1 of #300): a click on a cell in the task list selects its row (the timeline already mirrors the selection) and puts the cursor on that column, drawn as an outline in `--gantt-sel-edge` (no new token). The row is the app's selection, so it survives edits and undo; `Session::move_selection(delta)` moves it over the table's own rows, so a collapsed summary's children and the rows a filter hides are skipped, it stops at the first and last row, and a selection hidden under a collapsed summary moves from that summary's row. The column is `packages/gantt/src/cursor.ts`, kept as a name because the ID column comes and goes. The wasm exports are `App.select_task` and `App.move_selection` (`docs/WASM_API.md`). `Escape` clears the selection and the cursor. The keys do nothing while a cell or the find box has focus. The Rust tests are `crates/app/tests/nav.rs`, and `packages/gantt/tests/cursor.spec.ts` clicks, presses the arrows, collapses a summary and undoes an edit.

More cell-cursor keys: `Home` and `End` put the cursor on the first and last column, `Ctrl+Home` and `Ctrl+End` on the first and last row, and `PageUp` and `PageDown` move it a page of rows. `Ctrl+A` makes the visible rows a range, `Ctrl+C` copies the range (or the selected row) as tab-separated text (the hosted file menu's "Export the list as CSV" writes the same columns for every visible row, and says `Exported 41 rows to <name>.csv`; "Copy the list", under it, puts the same rows on the clipboard as tab-separated text and says `Copied 41 rows`), and `Ctrl+P` prints the chart as pages (see Printing, below). Typing on an Actual start, Actual finish or Remaining cell opens its editor, as on the other editable cells.

Printing (gs#703): `Ctrl+P`, or "Print..." in the file menu of the hosted demo (under "Save image (PNG)"), prints the chart as landscape US Letter pages of 25 rows each, whatever the window size. On `beforeprint` the page fills `.gantt-print-pages` with one SVG per page (`App.print_pages`) and print media shows only those; `afterprint` empties them. Each page has a header with the page title, the data date, the filter when one is on (with its value for a code or a status filter), the Lookahead window when one is on, "Page i of n" and "Printed" with the print date, and a legend of the bar colors at the foot (the legend names the two outlines too, though print draws neither). The pages hold the selected range's rows if a range is selected, else every visible row, in order, in the columns the table shows: the Columns menu's order and hides and the Progress and Variance buttons' state. At most 100 pages print: the last page then says "N rows not printed. Select a range to print them." If no pages were filled, the text sheet prints instead: a header line and one line per visible row, with the toolbar, the canvas and the table hidden. The specs `print-pages.spec.ts`, `print-sheet.spec.ts` and `journey-j5.spec.ts` (in `packages/gantt/tests/`) and `print.spec.ts` and `print-menu.spec.ts` (in `apps/hosted/tests/`) check the pages, the text sheet, the sheet size and the Print item; `crates/app/tests/print_pages.rs`, `print_lookahead.rs` and `print_legend.rs` check the page count, the header, the left-out line, the range and the legend.

"Save image (PNG)" in the same menu (under "Copy the list") downloads a picture of the first printed page as `<name>.png` (`untitled.png` for a sample): `App.print_pages` page 1 drawn on white at twice its `viewBox` (2112 by 1632 pixels for Letter), through an `Image` from an SVG blob URL and a 2D canvas, so it reads no GPU canvas. The spec `export-image.spec.ts` (in `apps/hosted/tests/`) checks the file name, the PNG signature and the size.

Range selection (gs#423, story S2 of #300): `Session` holds a range as two tasks, the anchor (always the selected task) and the extent (`crates/app/src/range.rs`). `Shift+Up` and `Shift+Down` call `Session::extend_selection(delta)`, `Shift`+click calls `Session::extend_to(task)` and `Shift+Space` calls `Session::select_row_range()`; the wasm exports are `App.extend_selection`, `App.extend_to` and `App.select_row_range` (`docs/WASM_API.md`). The rows between the ends are read from the table's visible order each time, so a collapsed summary's children and the rows a filter hides are never in a range, and a collapse needs no special case: a hidden end stands on its summary's row, and the range keeps the same two tasks. A range ends when the selection changes (a click, an arrow, a search hit) or clears, when an end has no row at all (a filter), and when an end is deleted (an undo of its insert). `Status.range` is `[first, last, extent]` rows or `null`; `packages/gantt/src/range.ts` sets `data-range` on the table rows of the drawn window only, and the table scrolls to the extent as it moves. The timeline fills the range rows in view with the selection band (gs#425, story S2b: `RowMarks.range`, passed from `Session::scene`); the scene count follows the window, not the range, and `crates/timeline/src/scene/tests/bars.rs` and `crates/app/tests/range.rs` count the fills. The Rust tests are `crates/app/tests/range.rs`, and `packages/gantt/tests/range.spec.ts` presses the keys, clicks with Shift, collapses a summary under a range and undoes an edit.

Edit from the cursor (gs#421, story S3 of #300, with ruling R2): `Enter` and `F2` open the editor on the cursor's name or duration cell with the old text; a printable key opens it holding that key (so typing `5d` on a duration and pressing `Tab` sets 5 days, one undo step); `Backspace` opens it empty and `Escape` restores the old value. `Enter` commits and moves the cursor down in the same column, `Tab` and `Shift+Tab` commit and move (name, duration, the next row's name, and back); `Escape` discards. A refused commit keeps the editor open, as for a double-click. The cursor is "in the list" from a click on a cell or an arrow key until `Escape`, a press on the timeline, focus leaving the chart, the end of the selection, or its row being hidden under a collapsed summary or by a filter (`packages/gantt/src/cursor.ts`, the mode in `mode.ts`); while it is, the chart's letter keys are suspended and the keys typed before the selected row is drawn (printable keys, `Backspace`, `Enter`, `Tab`, `Shift+Tab`) wait for it in order and are replayed into the editor once it opens, so `x`, `Backspace`, `y` leaves `y` and `Enter` commits. A focused toolbar button keeps `Enter` and `Space`; the other keys, `c` included, reach the cursor. When the selection ends (`Escape`, a schedule opened, the row deleted) the cursor leaves the list, and only a click on a cell or an arrow brings it back. The editor is `packages/gantt/src/cell-edit.ts`; `packages/gantt/tests/cell-grid.spec.ts` types, tabs, refuses, backspaces and presses `c` in the list, and `packages/gantt/tests/mode.spec.ts` hides the selected row and moves focus out of the chart.

Indent and outdent (gs#417, gs#422): `Alt+Shift+Right` indents and `Alt+Shift+Left` outdents (`Option+Shift` on a Mac), through `Session::indent_selected` and `outdent_selected` and the wasm exports `App.indent_selected` and `outdent_selected`; the keys do nothing while a cell or the find box has focus, and `Alt+Left` and `Alt+Right` still collapse and expand. Indent makes the selected row the last child of its previous sibling, opening that row if it was collapsed; outdent moves the row to just after its parent and adopts the siblings below it as its last children (MS Project's rule). A row's whole subtree moves with it and no task's dates change. Each is one undo step, and undo restores the exact parent, outline level and position, the adopted siblings included. A refusal changes nothing and carries a message: no sibling above to indent under, already at the top level, a leaf with a link that would become a summary (the link rule of gs#47), a row filter or lookahead window on, or a bar drag in progress. A refusal shows in the same alert line over the chart as a refused row edit, and the next successful edit clears it. There is no toolbar button. `packages/gantt/tests/indent.spec.ts` presses the keys on Linux: indent, outdent with the adopted siblings, undo and redo, the refusal on the first row, and `Alt+Shift+Left` not collapsing. The Rust tests are `crates/app/tests/reparent.rs`: 200 random indents and outdents on 2,000 tasks keep the solution equal to a full `compute()` with every date unchanged, and undoing them all restores every task's parent, level and preorder position.

Move a row (gs#703): `Alt+Shift+Up` moves the selected row, with its subtree, above the sibling before it, and `Alt+Shift+Down` below the sibling after it (`Option+Shift` on a Mac), through `Session::move_selected_up` and `move_selected_down` and the wasm exports `App.move_selected_up` and `move_selected_down`. Each is one `Reparent` under the row's own parent, so no task's dates or links change and every row keeps its parent. The moved row takes its parent's level plus one (1 at the top), so in a file whose levels skip (an MS Project task at level 3 under a level 1 summary) it drops to level 2 and its subtree moves by the same step; the selection follows the row, and one undo step puts back the order and the levels. The first and last of the siblings are refused with "This row has no sibling above it." or "...below it.", and so are a row filter or lookahead window and a bar drag in progress; the refusal shows in the same alert line as indent's. There is no toolbar button. `packages/gantt/tests/move-row.spec.ts` presses the keys on Linux: a summary moves with its subtree, Ctrl+Z restores the order, and the first row shows the refusal. The Rust tests are `crates/app/tests/move_row.rs`.

Links (gs#49, gs#347): hold `Alt` and drag from a leaf bar onto another bar, or press the dot that appears just beyond the finish end of the hovered or selected bar and drag from it; releasing over a bar adds a finish-to-start link (the successor moves to the predecessor's finish, and the whole schedule is re-solved). While you drag, a line follows the pointer from the predecessor, the cursor is a crosshair, and both turn to the refused look (red line, `not-allowed` cursor) over a target the app would refuse: a summary ("Link its sub-tasks instead."), a task already linked to the same successor in the same direction, or a task that would make a loop (the message names the loop, `"B" to "A" would make a loop: A → B → A.`). Releasing on a refused target shows that message in the same alert line over the chart as a refused row edit and changes nothing; the next press clears it. `Escape` during the drag, and a release on empty canvas, add nothing. A new link is selected. A click on an arrow selects the link (a click on a bar or on empty canvas clears it), and `Delete` or `Mod+Backspace` removes the selected link instead of a row; `Ctrl+Z` brings it back with the same identity, `Ctrl+Shift+Z` removes it again. With a task selected, `]` and `[` select its next and previous link (the ones that start or end at it, in the order they were added, wrapping at the ends; a removed link is never reached; `Session::step_link`), so `]`, `Delete`, `Ctrl+Z` removes and restores a link without the pointer. The link keys do nothing while a cell or the find box has focus. There is no key to add a link yet (the predecessor column of a later story will give one).

## URL options

URL options:

- `?n=1000` or `?n=10000`: a smaller schedule (default 50,000, at most 200,000).
- `?backend=webgl`: skip WebGPU and render on WebGL2.
- `?schedule=1`: load `schedule.dat` (an MS Project XML or P6 XER file, served by `run.sh --schedule`) instead of the generated demo; not with `?stress`. With `?measure=1` the measurement runs on the file.
- `?stress=1`: the stress fixture (dense cross-phase links, a head task every stream depends on, and two in five bars colored from six colors) instead of the demo schedule.
- `?groups=<k>` (with `?stress=1` or `?measure=1`): the stress fixture under one root summary, each task coded `Phase` with one of `k` values, and the rows are grouped by `Phase` from the first frame.
- `?beforeEdit=1`: hand the chart a before-edit function that allows every change, so a measured drag pays for the call the chart makes when it starts.
- `?measure=1`: the scripted measurement ([MEASURING.md](MEASURING.md), "Measuring frame times"); without `?schedule` it turns on `stress=1`; with `?schedule` it runs on the file. When the run ends without an error, the page shows a "Download the measurement (JSON)" link that saves `gantt-measurement.json`.
- `?panic=init`: panic on purpose during init (a test hook). On auto the page reloads on WebGL2; with `?backend=webgl` it shows `render error: <reason>`.

If WebGPU starts but then fails (an uncaptured GPU error or a lost device), the chart switches to WebGL2 in place, with no reload, and the status line's backend segment gives the reason, for example `WebGL2 (WebGPU failed: GPU device lost (Destroyed): Device was destroyed.)`. Headless Chromium with the SwiftShader software adapter does this: its WebGPU device is lost after the first frame even for a bare clear loop. A WebGPU panic leaves the module unusable, so for one the page itself reloads on WebGL2 (`?backend=webgl&fallback=<reason>`), as it does for `?panic=init`. The frame banner's Reload button reloads the page.

## Checking the page in headless Chromium

Check the page in headless Chromium with the `@playwright/test` specs in `packages/gantt/tests/` (needs Playwright's Chromium: `pnpm exec playwright install chromium`, or `CHROME=<path>`):

```sh
cd packages/gantt && pnpm test:e2e            # GANTT_URL, CHROME, BACKEND=webgl, DPR=2, N=10000 to vary
```

There is one spec per journey (`startup`, `zoom-pan`, `table-sync`, `hover-drag`, `outline`, `find`, `filters`, `selection`, `table-edit`, `schedule-route`, `measure` and the others in the directory; the open-a-schedule journey `j1-open` and the `journey` spec run on the hosted app, below). Between them they zoom from years to hours at a bar and pan, and fail if the zoom anchor drifts more than 1 px, the pan does not follow the pointer, a view lacks bars, critical bars, axis labels or dependency arrows, the hours view does not place each task's name once, the table's DOM rows do not follow the canvas's visible rows, or a collapse, "Critical only", "Longest path", find, undo or redo, table edit, selection or driving-path journey does not behave as its spec says; they also fail if a schedule file does not open or a malformed one does not show its error. Every test that opens the page also fails on a page error. The specs read the app through `GanttHook` and keep the check messages the old `verify.mjs` printed. The config starts `pnpm preview` itself and never reuses a server already on its port, so a run cannot test another checkout's build (gs#378). The port is `GANTT_PORT`; without it a local run takes a port from 4400 to 4899 derived from the checkout's path (each worktree gets its own, printed in the `vite preview ... --port` line at the start of the run), and CI without `GANTT_PORT` takes 4173. If the port is busy, the run stops with "already used": set `GANTT_PORT` to a free port, or stop that server. `GANTT_URL` skips the server and tests whatever answers there. The HTML report goes to `packages/gantt/playwright-report/` and CI uploads it as the `playwright-report` artifact, with the screenshots and data a test attaches.

The `web` job in CI runs them: it first runs the browserless unit tests of the demos (`demos/screencast/test-caption.mjs`, `test-ctx.mjs`, `test-frame.mjs`, `test-label.mjs`, `test-mac-copy.mjs`, `test-story.mjs` and `demos/50k/test-measure-open.mjs`; not `test-measure-cleanup.mjs`, which needs a built `packages/gantt/dist`, Chromium and bwrap), then it installs Playwright's Chromium (`pnpm exec playwright install chromium`; CI runs on the self-hosted `gantt-ci` runners on hub, whose system libraries are installed already), sets `GANTT_PORT` from the runner name (4174 on `hubgantt2`, 4173 on every other runner, so the two hub runners can run the job at the same time) and runs `pnpm exec playwright test` on the runner's software GL (no GPU), where the page renders on WebGL2. The `hosted-browser` job runs `apps/hosted/tests/journey.spec.ts`, which plays every scene of the README screencast and of the feature clips on the hosted build at `?sample=demo-50k` (about 2 minutes on the CI runner, gs#396, moved by gs#541), and `apps/hosted/tests/j1-open.spec.ts`, which opens a sample from the menu and your own file with the chooser; `JOURNEY_SAMPLE=medium-5k` points the journey at another sample, and its first scene, `open`, then fails by name. The developer page's `?schedule=1` error texts stay checked in `packages/gantt/tests/schedule-route.spec.ts`. The scripted measurement runs once inside it (`measure.spec.ts`), short (5,000 tasks, one repeat, no warm-up); the job fails if it does not complete, writes a result without one of its fields, or does not judge all seven thresholds, and asserts no timing. The same job bundles and typechecks the shell, and the `wasm` job builds and lints the wasm.

**The eight chapter stills are one script.** `node demos/screencast/stills.mjs --out <scratch dir>` takes all of them in one run, and `--dry` lists them with no browser. `--only <still>` writes one (the scenes before it still play). Each sample opens in a new browser context, so a zoom an earlier scene left cannot reach the next still, and a still is taken once the zoom level has held for 30 frames. Into `book/src/media` itself the script applies the WebGPU check of `clip.mjs`, so on the hub it writes to a scratch folder (see "Where to record").

**The README video does not carry the open-file caption.** The caption "Open a P6 or MS Project file" belongs to the `open-file` scene of `steps-features.mjs`. That scene is not in `steps.mjs` (the story opens with its own `open` scene, captioned "50,000 tasks open: bars, names and the critical path in red") and sets no `clip: true`, so `run.sh` neither shows the caption in the README video nor cuts a clip of it. Only `clip.mjs` makes the open-a-schedule clip. To change what the clip shows (the caption, the scene, the fixture), re-run `clip.mjs` with the command in the table; re-recording the README video does not touch it.
**Where to record.** Anything that shows motion or frame rate is recorded on the MacBook Pro: the README story, the feature list and any clip that shows them. The guard is in `run.sh`: it copies nothing unless `screencast.json` and `features/clips.json` both say `backend: "WebGPU"` and `fps` 50 or more (`copy-clips.mjs guard`). A still or near-still book clip with no animation or frame-rate claim, such as open-a-schedule, may be recorded on the hub, but not into `book/src/media`: `clip.mjs` applies the same check when `--out` is `book/src/media` or a folder inside it, so it refuses a hub recording there. On the hub, record into a scratch folder; an agent copies the still into the book by hand after checking that it shows no motion or frame rate (the gs#633 rule, applied as a deliberate copy). The commands and the reasons are in `demos/screencast/README.md`, "Where to record".

The screencast at the top of the README is recorded by a script: `demos/screencast/run.sh` builds the hosted app (`apps/hosted/dist`: the wasm, the samples and the bundle), copies it to the recording machine (the maintainers' MacBook Pro, an ssh host named `mbp` in the maintainer's ssh config, which `run.sh` calls; without one, use `--local`), records `demos/screencast/steps.mjs` headless there, on `?sample=demo-50k` (WebGPU on its Apple GPU, no window), and writes `docs/media/screencast.gif`, `docs/media/screencast.mp4` and `docs/media/screencast.json`, then rewrites the block at the top of the README (machine, date and the `main` commit). Before the video starts, a pre-roll (the `setup` export of `steps.mjs`) runs once after the frame-rate check and sets the opening view (day zoom, the first bar a fifth in from the left, the top rows) and, for the story, `criticalView` (`demos/screencast/steps/story.mjs`) then puts the first critical task on the chart (the fixture's critical path is in its last rows); the cut is stamped after it, so the first frame of the story video is a readable schedule with bars, names and the critical path in red, and the fast scroll is not first (gs#508). Each step waits on `GanttHook` state, never on a sleep, and draws its caption over the page: a rounded dark label, 30 px semibold, centered in the lower third of the timeline, with a 150 ms fade between captions (`demos/screencast/record/overlay.mjs`). A step may give `captionEnd(ctx, result)`, which returns text appended to its caption once the step has run (the measured time of a drag, for one), and `ctx.ring(selector)` circles a page element for a moment (the "50,000 rows" count, `#row-count`). The context and the scene runner are in `demos/screencast/ctx.mjs`, with a `mode`: in `record` mode (the recorder) `ctx.hold(s)` is `s` seconds counted in frames and the caption overlay is drawn; in `test` mode (the e2e spec) a hold is one frame and the caption calls draw nothing, but a function caption is still called and every caption must come out as non-empty text. A scene is a step plus three optional fields: `journey` (the book chapter that owns it, `J1` to `J9`), `clip` (true when it is cut into a per-scene clip, gs#152) and `pre` (an expression run in the page before the scene; if it is false the scene fails with its name and the page state, so a reordered list fails at once and not after a 15 s wait). There is no `requires` and no skip: every scene is on `main`, so a missing method fails the scene. `apps/hosted/tests/journey.spec.ts` runs the scenes of `steps.mjs` and of `steps-features.mjs` in `test` mode, one test per list with a `test.step` per scene, in the `hosted-browser` job; a screencast scene is therefore also a test. `node demos/screencast/test-ctx.mjs` checks the two modes, the function caption and the `pre` check with no browser. `node demos/screencast/test-clips.mjs` cuts an ffmpeg `testsrc` video with three known windows (one noisy, so it falls down the ladder) and checks that each clip starts and ends within 0.3 s of its window and is under the cap, that an unchanged scene hash copies nothing, and that the WebGPU and 50 fps guard and the size check copy nothing; it needs ffmpeg and takes about 45 s, so it is not in the `web` job (the CI runner has no ffmpeg). `node demos/screencast/test-frame.mjs` checks the pre-roll order, the caption ending and `zoomTo` with no browser. `node demos/screencast/test-story.mjs` checks the story's step order, the scene fields, the caption endings and that the P6 file the story opens holds what its steps name, the same way. `node demos/screencast/test-caption.mjs` checks that the `open-file` caption names both P6 and MS Project and does not say the file stays in the browser, the same way. `demos/screencast/run.sh --local` makes a software-GL draft on hub in `demos/screencast/draft/` (git-ignored): the story as `screencast.gif`, `.mp4` and `.json`, and the feature clips in `draft/features/`. `--local` also runs from a detached HEAD (`git worktree add --detach`); the draft is labeled "from detached HEAD based on <commit>". `demos/screencast/run.sh --upload` is the maintainers' step: it uploads `docs/media/screencast.mp4` as a GitHub attachment and rewrites the README video URL. Its scripts (`demos/screencast/upload/`) are not in the public repository, so `--upload` stops there with exit 2, after the detached-HEAD check. The script exits non-zero if the GIF is 5 MB or more. The `links` feature clip names its two tasks by id (`PLAN` in `demos/screencast/steps-links.mjs`) and fails the recording if the link added is not that one, so a task id change in the fixture means editing `PLAN`. `record.mjs` writes each step's window into `screencast.json` as `stepWindows` (`name`, `startSeconds`, `endSeconds`, in seconds from the cut, the same clock as `durationSeconds`; `steps` still lists the names), and fails a story recording longer than 45 s: it writes the JSON, deletes the GIF and MP4 and exits 3 with the length (gs#384; `test-frame.mjs` checks both with a fake list of windows and a fake duration). `steps.mjs` is the README story and stays fixed: four steps, meant to run 30 to 45 s (open, drag, fling, close; the recording of 2026-10-29 in `docs/media/screencast.json` still has the four P6 steps and ran 48.6 s; the next recording will be shorter). All four run on the 50,000-task schedule, so the story shows the first idea of the README (fast in a browser); the P6 steps (open-p6, code-filter, edit-link, show-moved) are in `steps-features.mjs`, which the journey spec still runs, so what a scheduler works with is shown by the feature clips and not by the README video. The drag moves the first critical task, the one the pre-roll put on the chart, and its caption gains what the release moved (the page's "what moved" line) and the measured re-solve time; after the release the view glides to the first critical task of the re-solved schedule (the release moves the critical path to other rows, which can be off the screen; the glide takes about 0.5 s) and holds there for 1.5 s, and the step fails if no critical bar is then on screen. The fling follows the drag on the whole schedule: it zooms out and sweeps the rows once, top to bottom, and its caption gains the slowest gap between animation frames that it measured. The last steps (`demos/screencast/steps/p6.mjs`) open `demos/screencast/fixtures/fit-out.xer` through the page's Open button: a made-up office fit-out of 26 activities five weeks in, with actual dates, a data date, links of three kinds and one activity code, "Trade". The hosted samples have no actuals and no codes, so the story brings its own file; `fixtures/build-fit-out.mjs` writes it, and the Mac copy of `demos/screencast/` carries it. The `open-p6` step fits the project on the chart, then scrolls the table sideways under the frozen ID, WBS and Task to the progress columns (#810) and back; `code-filter` picks the code type and one value, then Clear (#771); `edit-link` clicks the arrow of one link, presses Enter, types the new type and lag in the link editor (#788) and reads the page's note, which says when the critical path changed (#780); its caption gains the finish and critical-path part of that note. `show-moved` then presses the Show moved button (#795) and the task list keeps the tasks the edit moved with their summaries; its caption gains the row count. It follows the link edit and not the 50,000-task drag because on that schedule the press changed nothing a viewer could see: the drag's view is the bottom of the list, where every visible row had moved. A caption ending is added while the state it describes is on screen (`ctx.extendCaption`), and the code filter takes its ending off before Clear, so no ending sits over a state that has gone. The steps check part of what their captions claim (the file's data date and progress columns, the link's text before the edit, that a filter keeps fewer rows, the task names they aim at) and fail the recording if it does not hold; the page's own labels carry the rest. The feature steps that are not in the story live in `demos/screencast/steps-features.mjs`, which has the same shape (a `setup` and `steps`), is never published as its own video, and is the source of the per-feature clips for the book. A recording is two runs of `record.mjs`: the story, and `--list features`, which makes no GIF or MP4 of its own and cuts one GIF per scene that sets `clip: true` out of the one recorded video, from the scene's start to its end (`runScenes` returns each scene's window; a scene's name is its file name, a slug of lowercase letters, digits and `-`). A clip is a GIF under 600,000 bytes, at most 12 s: `makeClip` (`record/media.mjs`) tries 640 px at 8 fps, then 560 and 480 px at 8 fps, then 480, 400 and 320 px at 6 fps, and writes the first that fits; a scene that fits no rung, or runs over 12 s, fails the run (exit 3) with the scene's name and the sizes tried. Next to the GIFs the run writes `features/clips.json`: the recording's `backend` and `fps` and, for each clip, the hash of the scene and the size written. The hash covers the scene's name, journey, `pre`, caption, caption ending and actions as source text, and the source text of the module that defines the scene and of every file that module imports, transitively (`sceneModuleDigests`), so an edit to a helper or a constant a scene reads recuts the scenes of every module that imports it: more clips are copied, never a stale one. The state the earlier scenes leave in the page and the `setup` pre-roll are not in the hash: bump `lookEpoch` when a scene's starting state changes. `run.sh` copies a clip into `book/src/media/features/` only when its scene's hash differs from the one in the committed `clips.json`, or it was cut under an older `lookEpoch` (a number at the top of that file; bump it by hand when the chart looks different or a scene's starting state changed, and every clip is recut), or it is not committed yet; ffmpeg output is not byte-stable, so an unchanged clip would otherwise be a new blob in history each time. `demos/screencast/copy-clips.mjs` does the copy and checks every clip's size on disk before it copies any; a clip at or over the cap stops the run. It also refuses a recording: `run.sh` copies nothing, not the story media either, unless `screencast.json` and `features/clips.json` both say `backend: "WebGPU"` and `fps` 50 or more (the MacBook measured 120), so a draft from a machine without a GPU never reaches the repo. A PR that adds a user-visible feature adds its step to `steps-features.mjs` in the same diff, and the wrap of a sprint that merged one re-runs the script and commits the new media.
