# Measuring: tests, benches, frame times and open time

Speed is the claim, so it is measured. This page holds how the tests, the benches, the scripted frame-time run and the open-time run work, and the results taken so far. How to run the demo page is in [DEMOS.md](DEMOS.md).

No comparison with P6 or MS Project has been measured. The frame-time and open-time rows below are this chart alone, on the machines named, and the benchmark compares it with another browser Gantt chart (DHTMLX) and quotes Syncfusion's published benchmark, not with a desktop program.

## Why it is fast: Rust, WebAssembly and the GPU

Most browser Gantt charts are JavaScript libraries that draw with the page's DOM or a 2D canvas. This one is not:

- **Rust** is a compiled systems language: native-code speed, no garbage-collection pauses, and memory safety checked by the compiler. The scheduling engine (`crates/engine`) and the timeline renderer (`crates/timeline`) are both Rust.
- **WebAssembly (WASM)** is a compact binary instruction format that every modern browser runs at close to native speed, next to JavaScript and inside the same sandbox. The Rust code is compiled to one WASM module, so the engine runs in the page.
- **The GPU draws the timeline** (wgpu: WebGPU where the browser has it, WebGL2 otherwise), and only the visible part of a 50,000-row chart is drawn each frame.
- **Engine and renderer share memory in that one module**: a drag changes the schedule, recomputes the critical path and redraws without copying the schedule between JavaScript and WASM. TypeScript is a thin shell for browser events.

Measured on the 50,000-task stress fixture, release build ("Results" below):

| | MacBook Pro M3 Pro, 120 Hz | Dell, Intel Iris Xe, 60 Hz |
|---|---|---|
| Critical-path recompute per drag step, p95 | 1.4 ms | 1.2 to 1.4 ms |
| Zoom and pan frame time, p95 | 9.1 ms | 16.8 ms |
| Missed frames | 0 of 8,655 | 0 |

These two machines and the Mac mini (the duration edit under "Results") are the only machines measured so far. The aim is the same feel on any recent laptop in any current browser; Windows, tablets and phones are not measured yet.

For scale: Syncfusion's own October 2026 benchmark of JavaScript Gantt libraries reports a critical-path calculation at 50,000 tasks of 47.5 s for Syncfusion and 84.7 s for DHTMLX ([Syncfusion](https://www.syncfusion.com/blogs/post/react-gantt-chart-performance-benchmark.md)). That is a full calculation, while the 1.4 ms above recomputes only what one drag step changed; a full computation here is 20.3 ms natively ("Tests and benches" below). A like-for-like browser measurement (full compute and open time on the same file) is planned.

## Tests and benches

M1 is the engine: `crates/engine`, pure Rust with no WebAssembly dependencies. It has the task and dependency model (FS/SS/FF/SF, lags counted in the successor's, the predecessor's, a 24-hour or a named calendar, start-no-earlier-than), working calendars with holidays, a forward and backward critical-path pass that finds every date by search, and a deterministic schedule generator.

M2 is the timeline: `crates/timeline` (viewport, time axis and scene, unit-tested natively, plus a wgpu renderer), `crates/app` (the wasm-bindgen module that owns the schedule and the timeline) and `packages/gantt/` (a thin TypeScript shell: DOM events and the frame loop). The page renders on WebGPU where the browser offers it and on WebGL2 otherwise. M3 adds the measurement: a metrics overlay and a scripted run (see "Measuring frame times"); its first GPU results (the Dell, 2026-10-22) are in "Results".

Run the tests (the brute-force comparison included):

```sh
cargo test
GS_SEEDS=20000 cargo test --test brute_force   # a wider fuzz sweep
GS_SEED=123 cargo test --test brute_force      # one seed
```

A browser test that fails on `main` with no change to it or to the code it drives is set aside, not left to turn pull requests red (gantt#1163). Tag it `{ tag: "@quarantine" }` and put its issue number in a comment above it. Both Playwright configs (`packages/gantt/` and `apps/hosted/`) skip the tag in every CI run except the nightly one, so the nightly run still shows whether it passes; a run on your machine keeps it. The fix removes the tag, and the pull request that fixes it shows 10 reruns green: `pnpm exec playwright test --retries=0 --repeat-each=10 <spec>`. The usual cause so far is a WebGPU device lost just after the page is ready, which reloads the page onto WebGL2 under the test. A file that checks keys, files or timing, not the GPU, starts its pages on WebGL2 with `test.use({ webgl: true })`, and then has no device to lose.

Run the benches (criterion, native, 10k/50k/100k tasks):

```sh
cargo bench -p engine
scripts/profile-drag.sh   # where a finish-moving drag spends its time (callgrind; needs valgrind)
```

A link solve (bench `links`, 50,000 tasks, native): adding a link that closes no loop and re-solving takes 31 ms (`add_link`, graph rebuild, full `compute`, and the removal that undoes it); the loop check alone walks the head of the stress fixture's whole cone in 2.3 ms. This is the solve only: it does not include the report of what moved, the copy of the old and new dates, or the slide, which the page starts for a link edit as for a duration edit (gs#724). The page-side cost of a link edit is the `linkEdit` block of the measured run ("Measuring frame times", the **link edit** phase). This file does not record when or on what machine the 31 ms was measured; `cargo bench -p engine --bench links` replaces it with a dated figure.

A duration edit (gs#58): `Schedule::recompute_duration_cone_moved` updates the solution from one task's new duration and reports the tasks whose early dates moved and where they were (a `Moved` list: the task with its old early start and finish); the app's `Edit::SetDuration` calls it. It returns a `DurationCone` saying how the edit was solved: `Cone`, `Fallback(FallbackReason)` when the cone gave up for that reason and a full compute solved the edit, or `Replaced` when the solution had the wrong length. Benches `duration_full` and `duration_cone` grow a pinned task by 60 working minutes and shrink it back on `stress(20261020, n)`, with the project finish fixed (the pinned task is chosen by `benches/cpm/duration.rs`), with a full `compute` and with the cone; `duration_cone` checks both directions against a full `compute`, and that each took the cone (`DurationCone::Cone`), before it times anything. The engine's `test-hooks` feature (off by default; only the engine's own dev-dependency on itself turns it on, so no shipped build has it) exposes `engine::test_hooks`: a limit override of the cone's two numbers (admitted tasks and dependency inspections), a seam that leaves one predecessor out of the backward pass, and the seams that make a fallback fail. `crates/engine/tests/duration_sweep.rs` (gs#518) runs `fuzz::schedule` seeds 0 to 399 with 64 duration edits each, every edit checked against a full `compute`, at two limits and reads the returned `DurationCone`: at 1,000 admitted tasks the cone solves at least 65% of the edits that change a duration (73.2% measured, 2026-10-27) and runs on each of the four lag calendars, and the finish moves in some; at 3 admitted tasks and 8 inspections `ForwardLimit`, `BackwardLimit` and `EdgeLimit` each occur (`EsAfterLs` does not occur in the sweep; a unit test covers it). Run it with `cargo test -p engine --test duration_sweep -- --nocapture` to print the tally. Mac mini (Apple M4, macOS 26.7, rustc 1.99.1), from a fresh clone at the bench head, medians of 20 samples, one run (2026-11-07, mini load 3.33 before the run and 2.74 after it, so not an idle machine): `duration_cone/50000` 0.070 ms, under the 1 ms finish line of gs#58, against `duration_full/50000` 11.2 ms; at 10,000 tasks 0.070 ms against 2.18 ms, at 100,000 tasks 0.012 ms against 25.7 ms. The cone's cost follows the pinned target's cone, which differs per size, so the three sizes do not form a curve. How often the cone gives up on 200 drawn edits (2 of 200), what a fallback costs and the groups `duration_finish`, `duration_large` and `duration_backward` (a finish-moving edit, a large cone and a backward-only edit) are in `docs/duration-measurement.md`; the table of the run, with the mini load before and after each run, is in the description of gantt#1564. The three hub runs of 2026-10-26 (`docs/bench/duration-2026-10-26.out`, `duration_cone/50000` 0.161 to 0.216 ms against `duration_full/50000` 62 to 107 ms, hub load 2.3 to 27.4 at the start) ran on a loaded hub and are not figures; the `duration_dist` run and the three groups are not on the MacBook yet (gs#519, ruling Q1).

A bar drag changes one task's start-no-earlier-than, and `Schedule::recompute_cone` updates the solution from there: it recomputes the dragged task and the tasks downstream of it whose predecessors moved, and the backward pass again only when the project finish moves. `cargo test --test cone` checks it against a full `compute` on fuzzed, generated and stress schedules (`GS_SEEDS=<count>` widens the sweep, `GS_SEED=<n>` replays the equivalence checks for one seed; the check that the sweeps reach finish-moving, float-only and wide cones is a sweep-level test, `the_sweeps_reach_the_cases_they_name`). Native, 50,000 generated tasks, one drag step (benches `drag_step_full` and `drag_step_cone`, same steps): 20.3 ms with a full compute, 0.33 ms with the cone, mean over the steps of five drag targets. A drag that moves the project finish (a critical task dragged later) still runs the whole backward pass, so it saves only the part of the forward pass the cone skips: a finish-moving drag is 4.2 ms per step with the cone against 8.0 ms with a full compute (the first critical task dragged 20 days per step; medians of three runs on the Mac mini after gs#41 PR 3, 2026-11-07, raw figures in the description of PR #1566; PR #24 measured 17.3 ms against 21.1 ms, with 17,840 tasks moved, on another machine before gs#41). Benches `drag_finish_full` and `drag_finish_cone` toggle that task 20 days later and back, so every iteration moves the finish; absolute times vary with the machine, so compare the pair. What remains, from `scripts/profile-drag.sh` (callgrind, instructions inside `recompute_cone` on that drag, 50,000 tasks): the backward pass is 64% and the forward cone 12%, at 99.1 M instructions per call (0.70x of the 141.8 M before gs#41 PR 1, which computes each candidate start's finish once per probe and reuses it for the late finish; the backward pass was 74% and the forward cone 10%). ## The hosted app (local build)

`apps/hosted/` is a Vite project of its own, the page a person opens to use the chart (gs#511, story S3): one box that holds the chart, the whole window, with no row of its own above it. The page does not print which backend is drawing: it is the toolbar's tooltip ("Drawing with WebGPU" or "Drawing with WebGL2") and a screen-reader-only label, `#backend-label`. It loads the chart as a customer does, the built package: `gantt-core` is a `link:` dependency on `packages/gantt/` in `apps/hosted/package.json` (and in `apps/chrome/package.json`, whose toolbar files import it), so `pnpm build:lib` in `packages/gantt/` runs first and no alias names the chart; it is not a pnpm workspace, so `packages/gantt/` keeps its own lockfile and build, and `apps/hosted/` and `apps/chrome/` have their own `package.json` and `pnpm-lock.yaml`. It opens the office fit-out at once (the chart mounts with a generated 200-task schedule, and the sample opens over it). The toolbar's one "Open…" button opens a menu with "Open a file…" first, then four samples: `office-fitout` (a small made-up office fit-out project, 50 activities under 9 phases, 59 rows in all, written as an MS Project XML file at build time and 3.3 KB to download (3,341 bytes gzipped)), `medium-5k` and `large-50k` (generated XER files of 5,000 and 50,000 activities, fetched from `samples/` next to the page) and `demo-50k` (the 50,000-task schedule the chart builds itself, no download). `office-fitout` has links with lag, a calendar with four Monday holidays, a critical path and ten activities part-way done; the "unsupported features" panel stays hidden for it, and it opens with the data-date line, because the sample sets a `StatusDate` (2027-02-05 17:00) along with actual dates and progress (gs#859); the MS Project reader (`import::parse_mspdi`) reads a project's `StatusDate` as the data date (gs#563), so a file that has one opens with the data-date line and "Data date YYYY-MM-DD HH:MM" in the toolbar. The page's text uses a bundled font, not the machine's: `Gantt Sans` and `Gantt Mono` (Liberation 2.1.5, SIL Open Font License 1.1, files and notice in `packages/gantt/src/fonts/`; the notice credits Arimo, Tinos and Cousine, the upstream fonts Liberation builds on), so the task list and toolbar hold the same text width on every machine, and the demo page's body text (`packages/gantt/index.html`) is in `Gantt Mono` too; the chart's own text (bar names, axis labels) already used Liberation Sans. The chart's specs in `packages/gantt/tests/` rely on it: `waitReady` in `packages/gantt/tests/support/gantt.ts` waits for the fonts and throws if `Gantt Sans` did not load. A file chosen with "Open…" is read in the browser with no network request. The page takes two URL options: `?sample=<id>` opens one sample straight away (an unknown id shows its reason in the status line under the "Open…" button and opens nothing; with no `?sample=` the page opens the office fit-out, gs#821), and `?backend=webgl` skips WebGPU; the page adds that one itself, with `?restarted=1`, when it reloads after the chart reports a `fatal` error (a panic, at the start or in a frame); a page that has already started again shows the reason instead of reloading, so a start that always fails cannot reload forever. Any other WebGPU failure switches the chart to WebGL2 in its box with no reload, edits and all; the page puts its menu back into the chart's new toolbar and names the new backend (`apps/hosted/tests/webgl-switch.spec.ts`). How the sample files are made, fetched and counted is in [apps/hosted/README.md](../apps/hosted/README.md). The `hosting` architecture check (`crates/app/tests/architecture/hosting.rs`, decision 0007, runs in `cargo test`) keeps the two apart: the chart's files name nothing about hosting, and `apps/hosted/` imports only `@gantt/chart`, its own files and the packages its `package.json` declares.

Build and check it on a machine with the Rust tools of "Demos" and pnpm:

```sh
bash scripts/build-web.sh --no-bundle   # the wasm, into packages/gantt/src/wasm/
(cd packages/gantt && pnpm install --frozen-lockfile && pnpm build:lib)   # the package the app loads, into packages/gantt/dist-lib/
(cd apps/chrome && pnpm install --frozen-lockfile)
cd apps/hosted
pnpm install --frozen-lockfile
node scripts/build-samples.mjs          # the sample files, into apps/hosted/public/samples/ (needs cargo and Node 22.18 or later)
pnpm build                              # apps/hosted/dist/, with the samples
pnpm typecheck
pnpm exec playwright install chromium   # once; or set CHROME=<path>
pnpm test:e2e                           # GANTT_PORT, GANTT_URL, CHROME to vary
```

`pnpm dev` serves the page with hot reload (it needs the same `packages/gantt/dist-lib/`: rebuild it with `pnpm build:lib` after a change to the chart), and `pnpm preview` serves `dist/`. Run `node scripts/build-samples.mjs` before `pnpm build` and `pnpm test:e2e`: `tests/samples.spec.ts` reads `public/samples/samples.json` when Playwright loads it, and without that file the run stops before any spec runs, with an error that says ``Run `node apps/hosted/scripts/build-samples.mjs` first.`` (measured 2026-10-27 with `pnpm exec playwright test --list`: exit 1, no test listed, not even the ones in `hosted.spec.ts`). The script took 9.5 seconds on the hub (2026-10-27, load average 18) and wrote 3.5 MB. It stops, naming the file, at the first sample that reaches 25 MiB (the per-file cap of a Pages deploy); `BUILD_SAMPLES_MAX_BYTES=<bytes>` lowers that cap for a test and cannot raise it, and `tests/build-samples.spec.ts` covers the cap and the missing-file error ([apps/hosted/README.md](../apps/hosted/README.md)). `tests/hosted.spec.ts` opens the build, waits for the chart to be ready, reads the backend label and checks it equals the chart's backend (WebGPU or WebGL2), checks the chart's box is the whole window, and opens `packages/gantt/tests/fixtures/two-projects.xer` to see the project chooser with no network request made for it. `tests/samples.spec.ts` checks that the "Open…" menu lists "Open a file…" and the four samples with their activity counts and download sizes, opens each of them from the menu and checks the chart's row count against `samples.json`, opens `medium-5k` with `?sample=` from a server that has already undone the gzip, checks that `?sample=nope` shows its reason and opens nothing, and opens `?sample=office-fitout` to count its leaf rows (50) and summary rows (9) from the page's own table, find a critical path, and read the one line in the unsupported-features panel. The `hosted` and `hosted-browser` jobs in CI do the same on the self-hosted `gantt-ci` runners after the `wasm` job, side by side (`hosted` also typechecks and runs the Node tests and, on the batch, nightly and deploy runs but never on a PR push, the benchmark driver test (it is two tests of 60 to 98 s each); `hosted-browser` runs the browser specs): each downloads the `wasm-bindings` artifact, installs the Rust toolchain (`dtolnay/rust-toolchain@stable`, with `Swatinem/rust-cache@v2`), runs `node scripts/build-samples.mjs` and builds. Then `hosted-browser` runs every spec in `apps/hosted/tests/` on the software GL (no GPU, so WebGL2); on the fast tier it runs the `@smoke` tests, plus the hosted specs the diff reaches when it changes a file under `apps/hosted/` (a changed spec, the specs that share a changed `src` module's name, or every spec for any other file there, except a type declaration, a markdown file and a file in `tests-node/`, which add none: the typecheck and the Node step cover them; and every spec when the diff changes `packages/gantt/src/chart.html` or a file under `packages/gantt/src/styles/`, which every hosted page loads, gantt#1614), prints the journey spec's time (below). `hosted` uploads `apps/hosted/dist/` as the `hosted-dist` artifact. Neither job reads a secret or deploys anything. Two more specs run in `hosted-browser`, and in `pnpm test:e2e`: `tests/j1-open.spec.ts` opens `office-fitout` from the "Open…" menu, opens your own file with the chooser (no network request) and checks a truncated file's error; `tests/journey.spec.ts` plays every scene of the README screencast (`demos/screencast/steps.mjs`) and of the feature clips (`steps-features.mjs`) on `?sample=demo-50k`, the same page and URL that `demos/screencast/run.sh` records on (gs#541), so a screencast scene is also a test. `JOURNEY_SAMPLE=<id>` points the journey at another sample; `medium-5k` fails its first scene, `open`, by name, because that scene checks for 50,000 tasks.

The `hosted-browser` job reports the journey spec's time against its budget of 180 s (gs#495). The Playwright step adds the `json` reporter, and the step after it, `journey time`, runs `node tests/journey-time.mjs test-results/results.json`: it adds the two journey tests' durations (the story list and the features list) and appends a block such as `Time: 160.3 s of the 180 s budget (89%).` to the job summary, with each test's time under it. If the result is missing, empty or holds no timed journey test, the block says `Time: unknown (...)`, never `0 s`; if a journey test did not run or did not pass, it says that the time is not a full run. A result with any count of journey tests other than two adds a line `Expected 2 journey.spec.ts tests and found N`, and a skipped journey test counts as not run; if the job summary cannot be written, the block stays on stdout and the step still exits 0. The step reports and does not fail the job; the spec's own timeout, 240 s a test in `playwright.config.ts`, does. To read the time on your machine, from `apps/hosted` after the build above:

```sh
PLAYWRIGHT_JSON_OUTPUT_NAME=test-results/results.json pnpm exec playwright test tests/journey.spec.ts --reporter=list,json
node tests/journey-time.mjs test-results/results.json
```

The time depends on the machine and its load: the figure in the example, 160.3 s, is from the hub (software GL) with its load average between 25 and 42 (2026-10-27), not from CI.

The status line's frame numbers are for watching, not results: results come from the scripted run, on a machine with a real GPU. The hosted app's speed line (click the chart, press `s`; `apps/hosted/src/speed-line.ts`) is the same kind of reading: it shows `Gantt.speed()`, the last open's total and the last 120 frames' p50, p95 and missed count, so a scheduler checks smoothness on her own machine in the hosted app alone. It floats over the chart's edge, so it does not change the chart's box, and `apps/hosted/tests/speed-line.spec.ts` checks it.

## Measuring frame times

```sh
demos/50k/run.sh --measure --param refreshHz=<display Hz>   # on the machine with the GPU; opens Chrome, leave the window alone
demos/50k/run.sh --measure --machine "Dell XPS 15, RTX 4060" --viewport 1920x1080
demos/50k/run.sh --measure --headless      # a smoke run on a machine without a GPU: not a result
```

`run.sh --measure` builds the release bundle, serves it on a free port, opens Chrome (`--channel chrome` by default; `--chrome <path>` for another binary), runs the page's `?measure=1` script and writes `demos/50k/results/measure-<time>-<machine>.json` (git-ignored). Other options are in the header of `demos/50k/measure.mjs`. You can also open `http://127.0.0.1:4173/?measure=1` in a browser that you start yourself; the page then offers the same JSON as a download when it finishes. Page options: `n`, `repeats` (5), `warmup` (1), `dragMs` (10000), `panMs` (3000), `dragDays` (30), `editRepeats` (5; 0 skips the edit phase), `baseline` (0; 1 sets a baseline before the warm-up, because the variance and comparison-bar costs are measured only with one, and the result's `config.baseline` says which), `refreshHz`, `machine`, `backend=webgl`. The CI smoke run in `measure.spec.ts` records `machine: "playwright-ci"` (it was `verify.mjs` until gs#287, which deleted that script), so a result file's machine name tells a CI smoke run from a real measurement.

To read the drag frames of two refs on the Mac mini without a hand-built pair, run `node demos/bench/profile.ts --cell <cell> --holder <lock name> --compare <ref> --drag --runs <n>` (docs/PROFILING.md, `--drag`). Each run's frame-interval p95 per drag is in its run folder (`drag.json`), and `--critical-only` skips the open measurement and the head-task drag. Before it builds or reads the lock holder it checks that `wasm-bindgen` is on PATH and that `@playwright/test` resolves from the checkout (`pnpm install` in `apps/hosted` or `packages/gantt`); when either is missing it exits 2 and prints the fix in one line.

The script runs on the stress fixture (generator seed 20261020, 50,000 tasks, two in five of them colored from six colors, gantt#1875). It runs the whole script once as a warm-up and discards it, then 5 repeats. Each repeat records three phases, and after the repeats an `edit` phase and a `link edit` phase record `editRepeats` edits each (below):

- **zoom**: ctrl+wheel steps, one per frame, anchored at the cursor, from 5 years to 2 hours across the canvas and back (the viewport's limits), over rows that start in the middle of the project;
- **pan**: a pointer drag in the axis band, sweeping both axes, at 0.1 px per minute;
- **drag**: 10 s of continuous drag of the stress fixture's head task, sweeping 30 days (`dragDays`, the range of the engine's `stress_drag` benches) back and forth; `dragTarget=critical` drags the first critical leaf task instead, which moves the project finish. The drag is cancelled at the end, so every repeat starts from the same schedule.
- **edit** (after the repeats; `editRepeats` edits, one unrecorded first when `warmup` is above 0): the script picks a task whose cone is wide, sets its duration through the public `App.set_duration` (to `200d`, longer than the fixture's tasks), records two windows of frames (`slide`, 0 to 400 ms after the edit: the 360 ms slide of the bars plus a 40 ms margin; `afterEdit`, 400 to 600 ms; before gs#486, `afterEdit` covered 0 to 600 ms and there was no `slide` window, so such results are not comparable), counts the rows whose start moved, reads the slide's copy time, undoes the edit, waits until `status.slide.active` is false (at most 1 s, then the phase fails with an error) and records 600 ms of frames with no edit. It chooses the task by trying the same edit, undone, on up to 32 leaf tasks, spread from the earliest start (from `App.table_rows`), and keeping the one that moves the most rows; the stress fixture's head task has about 267,600 minutes of float, which absorbs a longer duration, so the script chooses by trial and not by name. The result's `edit` block holds the chosen `task` and `row`, `text` (the duration set), `moved` (the fewest rows moved by any recorded edit; each edit reads every row's start before and after, so a phase that did not make the edit reads 0 and the smoke spec fails), `movedPerRepeat`, the `candidates` tried and the rows each moved, `setMs` (the time of the `set_duration` call, which blocks the page), `copyMs` (the page's copy of the old and new dates for the edit, `status.slide.copyMs`, as p50 and p95 over the edits; `null` while the page reports no slide), and `slide`, `afterEdit` and `noEdit`, each with the same p50, p95, missed frames and `encodeMs` as a phase. There is no threshold. A frame interval measured here includes the `set_duration` recompute, since that call runs in the frame that starts the `slide` window.
- **link edit** (after the edit phase; same `editRepeats`, one unrecorded first when `warmup` is above 0; gs#725): the same three steps for the edit a person makes most often after a drag, adding and removing a link. There is no wasm method that adds a link, so the script takes the pointer path: it presses with Alt on a leaf bar (`App.pointer_down` with `alt` true), moves onto another leaf bar and releases (`App.pointer_up` adds the link and selects it). It chooses the pair by trial: on the leaf bars on screen it tries a late-starting bar as the predecessor of each of the 8 earliest-starting ones (the 8 latest as predecessors, up to 64 pairs), counts the rows whose start moved, undoes the trial and keeps the pair that moves the most rows; a pair the engine refuses (a loop or a duplicate) leaves the revision as it was and is skipped. Each repeat then (1) adds the link and records the `slide` and `afterEdit` windows, with the windows defined as in the edit phase, and reads `status.slide.copyMs`; (2) removes it with `App.remove_selected_link` and records a second pair of windows (`remove`); (3) undoes the removal, which puts the link back, and redoes it, and records a third (`undoRedo`: `slide` pools the 400 ms after the undo and the 400 ms after the redo, `afterEdit` is the 200 ms after the redo); it then waits for the slide to end and records 600 ms with no edit. The result's `linkEdit` block holds the pair (`pred`, `predRow`, `task`, `row`: the link runs from `pred` to `task`), `moved`, `movedPerRepeat`, the `candidates` tried (a refused pair reads 0) and `refused`, `setMs` (the time of the release that adds the link, which blocks the page), `copyMs`, `slide`, `afterEdit`, `noEdit`, and `remove` and `undoRedo` (each with `slide` and `afterEdit`). A result written before gs#725 has no `linkEdit` key; read it as absent. A frame interval measured here includes the recompute, since the release runs in the frame that starts the `slide` window. There is no threshold. TODO(measure): the 50,000-task `linkEdit` rows on a GPU machine, from `bash demos/50k/run.sh --measure --param refreshHz=120` on the MacBook; none has been taken yet.
- **select and Fit** (after the link-edit phase; same `editRepeats`, one unrecorded first when `warmup` is above 0; gs#309): the frames after the two view changes a person makes most. The script chooses a task with a long driving chain by trial: it selects up to 32 leaf tasks spread from the earliest start with the public `App.select_task`, reads `status.selected.backCount` (the driving predecessors behind the task), clears the selection with `App.clear_selection`, and keeps the task with the longest chain. Each repeat then (1) selects that task and records 400 ms of frames (`select`, the same window length as the edit phase's `slide`); (2) clears the selection, zooms in to 0.1 px per minute and calls `App.fit_project`, and records 400 ms (`fit`). The phase fails if no candidate has a chain, if `select_task` or `fit_project` returns false, or if Fit leaves the scale where it was. The result's `select` block holds the chosen `task` and `row`, `back` (its chain length), the `candidates` tried, and the phase's p50, p95, missed frames and `encodeMs`; the `fit` block holds the same figures and `pxPerMinuteBefore` and `pxPerMinuteAfter`, one value per recorded repeat. A result written before gs#309 has no `select` or `fit` key; read it as absent. There is no threshold, and no GPU-machine row has been taken yet. TODO(measure): the 50,000-task `select` and `fit` rows from `bash demos/50k/run.sh --measure --param refreshHz=120` on the MacBook.
- **open draw-in** (after the select and Fit phase; same `editRepeats`, one unrecorded first when `warmup` is above 0; gs#309): the frames after a file opens, when the bars of the rows in the window grow from their start to their finish over 360 ms. The script writes the loaded schedule out once with `App.save`, and each repeat reads that document with `LoadedSchedule.parse_document`, opens it with `App.open` and records 400 ms of frames from the `App.open` call (`drawIn`, with the phase's p50, p95, missed frames and `encodeMs`). The open replaces the schedule, so it is the last phase. The frame cost of the draw-in is one copy of the dates (`status.slide.copyMs`) per open, and one write per row in the window per frame; no GPU-machine row has been taken yet. What the result holds (`schema` 1; the verdicts judge the phases pooled over the repeats, and `repeats` has each repeat's numbers):

| Field | Meaning |
|---|---|
| `zoom`, `pan`, `drag` | p50, p95 and missed frames of the requestAnimationFrame interval; a miss is an interval over 1.5 P; `encodeMs` is the CPU time of `App.frame()` in that phase; `totalMs` and `spanMs` are the sum of the intervals and the phase's elapsed time |
| `dragResponseMs` | from the pointer event's timestamp to the next requestAnimationFrame after its recompute, table update and draw |
| `recomputeMs` | the WASM recompute alone, one value per drag frame that changed the schedule |
| `encodeMs` | CPU encode and submit per frame, over the zoom and pan frames (they recompute nothing) |
| `wasm` | raw and gzip size of the `.wasm` as served (gzip by the browser) and the WASM memory at the end |
| `edit` | the edit phase (above); `null` when `editRepeats` is 0 |
| `linkEdit` | the link-edit phase (above); `null` when `editRepeats` is 0, and absent from a result written before gs#725 |
| `select`, `fit` | the select and Fit phase (above); `null` when `editRepeats` is 0, and absent from a result written before gs#309 |
| `drawIn` | the open draw-in phase (above); `null` when `editRepeats` is 0, and absent from a result written before gs#309 |
| `open` | only with `--open <file>`: the open-time phases (see "Open time" below) |
| `jsHeapBytes` | `performance.memory.usedJSHeapSize` where the browser has it, else `"unavailable"` |
| `zoomAnchor` | steps taken and the largest drift of the instant under the cursor, px |
| `environment` | machine, GPU (WebGL renderer and WebGPU adapter), browser version, backend, hardware acceleration, viewport, devicePixelRatio, refresh rate, generator seed, release build |

The thresholds were set before measuring, at the display's refresh period P: zoom and pan p95 frame interval at most 1.25 P with missed frames under 1%; drag p95 response at most 50 ms with missed frames under 5%; zoom anchor drift under 1 px per step. Each verdict is PASS or MISS; a MISS is a result, not a failure.

How the numbers are taken, where it matters:

- P is the 10th percentile of 90 idle frame intervals at the start (a slow frame is a whole number of periods above P); `refreshHz=<n>` overrides it. The browser does not report the display's refresh rate, so the GPU run passes `--param refreshHz=<display Hz>`; without it, an estimate that is not within 4% of 60, 75, 90, 120, 144, 165 or 240 Hz adds a warning to the result.
- The page draws only while something changes (`packages/gantt/src/loop.ts`): after the last change it draws for half a second and then asks for no frame, so `Status.frames` does not advance on an idle chart. A measured run, a drag and a slide keep drawing every frame, so none of the numbers below changes. The status read that a page makes through `window.gantt.status()`, or any other call into `window.gantt.app`, wakes the loop for that half second; to read the counter without moving it, call the prototype's method: `Object.getPrototypeOf(app).status.call(app)`.
- The drag response runs from the pointer event's own `timeStamp` to the `requestAnimationFrame` after the frame that applied the move (recompute, table update and draw), so a real pointer move includes the time before the browser delivered the event. The scripted drag has no real event: it calls the same input function as the DOM listener, and stamps each move with `performance.now()` read as the move is issued (the clock `event.timeStamp` uses), not with the frame's timestamp. A scripted response therefore leaves out input delivery and queueing, which a hand-driven run includes.
- A frame interval belongs to the phase the previous frame ran in. The interval after a phase's last frame is recorded before the script moves on, so a slow final frame counts. `totalMs` (the sum of a phase's intervals) equals `spanMs` (first frame to the frame after the last); the smoke checks that.
- `performance.now()` is coarse (0.1 ms) on a page that is not cross-origin isolated, so recompute and encode times below a few tenths of a millisecond are rounded.
- Hardware acceleration is inferred, and is `"on"`, `"off"` or `"unknown"`. The adapter is requested with `powerPreference: "high-performance"`, the preference the renderer asks for, so a machine with two GPUs reports the one that draws. A renderer or adapter that names SwiftShader, llvmpipe or a software path, or a fallback adapter, is `"off"`; a named one is `"on"`; no adapter, no name or no unmasked WebGL renderer string is `"unknown"`, never `"on"`. A result with `warnings` (software rendering, unknown acceleration, a debug build) is not a result.
- At seed 20261020 and 50,000 tasks the head task has about 267,600 minutes of float, so a 30-day drag moves few tasks and recomputes in well under a millisecond on hub. Raise `dragDays` past the float to make the cone, and the backward pass, the whole schedule.

### Measuring a file (gs#840)

`?measure=1&schedule=1` runs the same phases on the file the page loads as `schedule.dat` instead of on the stress fixture, and `node demos/50k/measure.mjs --schedule <file.xml or file.xer>` serves the file to the page itself (the page route is intercepted in the browser, so `dist/` is not touched). Everything else on this page applies: the options, the warm-up, the edit phases, the verdicts.

- **Drag target.** A file has no head task, so the script chooses by trial, as the edit phase does: it drags up to 16 leaf tasks, spread from the first row, half a sweep to the right, cancels each, and keeps the one that moved the most rows. The run stops with an error if no task moves any row. The stress fixture's drag is unchanged (its head task).
- **Result.** `environment.fixture` is `"file"` (it is `"stress"` otherwise), `environment.scheduleSha256` is the SHA-256 of the file's bytes as the page fetched them, and `environment.tasks` is the file's task count. Two results are comparable only when the hash is the same. The page hashes with `crypto.subtle`, which needs a secure context: `localhost` and `127.0.0.1` are one, a plain-http address on a network is not.
- **Not combined with `?stress`.** The page still refuses `?schedule` with `?stress`.
- **Numbers.** The thresholds are the stress fixture's, so a small file passes easily; read its numbers against the same file on another build, not against the 50,000-task rows. `packages/gantt/tests/measure.spec.ts` runs the 11-task `packages/gantt/tests/fixtures/measure-chain.xml` through the page in CI (software GL: a smoke run, not a result).

### A fresh machine (gs#39)

Results come from a machine with a real GPU: the Dell (Linux) or the MacBook Pro (macOS). A machine that has not built this repo needs the following, once. The versions are the ones the repo pins, so read them from the files if this page and the files ever disagree.

1. **Rust with the wasm target.** The workspace is edition 2024 and CI builds with the stable toolchain, so install a current stable one:

   ```sh
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
   rustup target add wasm32-unknown-unknown
   ```

2. **`~/.cargo/bin` on PATH, in the shell that runs `run.sh`.** `build-web.sh` calls `cargo` and `wasm-bindgen`; with the directory missing from PATH it stops with `command not found` or with `need wasm-bindgen-cli 0.2.129 (found 'none')`. The Dell needed the directory added to PATH (PR #40). Add `export PATH="$HOME/.cargo/bin:$PATH"` to the startup file that shell reads, then check with `command -v cargo wasm-bindgen`.

3. **`wasm-bindgen-cli` at the `wasm-bindgen` version in `Cargo.lock`**, 0.2.129:

   ```sh
   cargo install wasm-bindgen-cli --version 0.2.129 --locked
   wasm-bindgen --version   # wasm-bindgen 0.2.129
   ```

   `build-web.sh` reads the version from `Cargo.lock` and refuses any other, printing the command for the right one; when `Cargo.lock` moves, that message is the current truth.

4. **Node 22.13 or later and pnpm 11.25.0.** `packageManager` in `packages/gantt/package.json` pins pnpm 11.25.0, which needs Node 22.13 or later; CI uses Node 22. `npm install -g pnpm@11.25.0` installs it (on the Dell it was installed under mise's node, PR #40); `pnpm --version` should print `11.25.0`. `build-web.sh` then runs `pnpm install --frozen-lockfile` in `packages/gantt/`, which also installs the `@playwright/test` that `measure.mjs` loads. No Playwright browser download is needed for a headed run.

5. **A browser that drives the GPU.** `--channel chrome`, the default, drives the installed Google Chrome. The MacBook has Chrome 155 installed (gs#39). The Dell's runs used the system Chromium ("Results" below), which needs `--chrome <path>`, for example `--chrome "$(command -v chromium)"`.

6. **Run it headed, from the repo root, with `--measure` first.** A run without `--headless` opens a visible window; `--headless` is the smoke run on the software renderer, which is not a result. Leave the window alone until the script prints `overall`.

Users never set that flag, so no macOS WebGPU result may depend on it. On the Dell, Chromium 152 reported no WebGPU adapter without flags; the flags above are the ones that made the NVIDIA GPU draw (third bullet under "Results" below), each passed as its own `--chrome-arg <flag>`, and `__NV_PRIME_RENDER_OFFLOAD`, `__GLX_VENDOR_LIBRARY_NAME` and `__VK_LAYER_NV_optimus` are environment variables for that Dell's hybrid graphics. ### Open time (gs#87 PR 5)

How long a file takes to open, from the moment the page gets the file to the first frame of the new schedule. The page times eight phases on `performance.now()`, plus their `total`, and puts them on `window.gantt.opened.timings` (and in the status line and the hosted app's speed line, key `s`): `read` (the file into the page), `paint` (the wait that lets "Opening…" show, since the parse does not yield), `copy` (the bytes into linear memory, and building the result: the call minus its Rust phases, not clamped), `parse`, `build` and `compute` (Rust, from `LoadedSchedule.timings()`), `swap` (`App.open`) and `firstFrame` (the first frame submitted after the swap, not the display's vblank). Each starts where the one before ended, so they add up to `total`. The timings also carry `rustSpan`, which Rust measures with two clock reads outside the three Rust phases; it is a check, not a phase. `measure.mjs --open` rejects an open where `parse + build + compute` is more than 3 ms from `rustSpan` (a Rust phase that under-reports would otherwise be absorbed by `copy` and the sum would still balance; the 3 ms is the cost of the clock calls at the span's two ends, 0.7 ms warm and 2.3 ms cold in headless Chromium on hub), where any value is negative or not a number (the page keeps an invalid value as it is and never turns it into 0), or where the phases do not add up to `total`. The details are in `docs/ARCHITECTURE.md`, "Opening a file".

```sh
# a generator for the test files (not an XER exporter); not committed
cargo run --release -p xer --features synth --example synth -- --out /tmp/gantt-5k.xer --activities 5000
cargo run --release -p xer --features synth --example synth -- --out /tmp/gantt-50k.xer --activities 50000
cargo run --release -p xer --features synth --example synth -- --out /tmp/gantt-2x25k.xer --projects 2 --activities 25000

# on the machine with the GPU, after the scripted run, in the same page: 1 warm-up and 5 recorded opens
demos/50k/run.sh --measure --open /tmp/gantt-50k.xer --param refreshHz=<display Hz>
```

## Paired runs on a quiet box (gs#840)

`demos/dhtmlx-compare/pair.ts` runs one pair of bundles back to back: before each side it waits until nothing busy runs, load1 is under 4 (`--max-load`) and swap used did not grow since the poll before, so the first poll never counts as quiet (`wait.log`, with `max=` the cap, `swapKb=` and `busy=` naming what it waits on), serves the bundle, starts your command with `{url}` replaced by the page address, and samples load1, Chrome RSS and swap used every 3 s into `load.log` (`<unix s> <load1> <rss kB> <swap kB>`). `table.ts` prints each pair with the two runs' mean load1 and calls the pair matched when they differ by under 0.5. A cell needs 4 matched pairs among its first 8 attempts (by pair number), else the table says "unmatched"; later pairs are listed and not counted, and whoever calls `pair.ts` decides when to stop. `pair.ts` exits 1 when your command fails, 70 when it cannot start and 75 when the box never went quiet within `--wait-s` (default 3600). `table.ts` exits 1 with "no rows" on an empty results directory, 2 with "swap grew" when a run's swap used rose (that pair is not matched and none of its numbers count), and 3 when a driver result beside a `load.log` was refused or a cell's runs came from different environments (next section). This says nothing per frame. `pair.ts` runs on Linux and macOS and refuses any other platform. On Linux it reads `/proc/loadavg`, swap from `/proc/meminfo`, Chrome RSS from `/proc`, and counts a `gitlab-runner` build job as busy; it prints `/proc/loadavg` last. On macOS it reads load1 from `os.loadavg()`, swap used from `sysctl vm.swapusage`, Chrome RSS from `ps` (both run with `LC_ALL=C`; a swap figure that is not a whole dot-decimal number stops the run), and counts a running `cargo`, `rustc` or `xcodebuild` as busy (`BUSY_NAMES`, also when `ps` shows the kernel name in parentheses); it prints `os.loadavg()` last. `table.ts` prints the same load line last.

```sh
node demos/dhtmlx-compare/pair.ts --out results --cell open-50k --pair 1 --a gantt=<dir> --b dhtmlx=<dir> -- <measure command> {url}
node demos/dhtmlx-compare/table.ts results
node --test 'demos/dhtmlx-compare/*.test.ts'
```

### The benchmark schedule (gs#1197)

`demos/bench/dataset.ts` writes one schedule from a shape, a size and a seed: `dataset.json` and its SHA-256 in `dataset.json.sha256` (`sha256sum` format). Every side of the component benchmark loads that one file, and two runs compare only when the hash is equal. The bytes are a pure function of the three inputs, and the task count, summaries included, is the size. Sizes run from 1,000 to 100,000; anything else, an unknown shape, a seed that is not a u64, or an option missing, repeated, unknown or without its value exits 64 and writes nothing. The shapes:

- `chain` and `tree4`, the two shapes of the comparison harness (its `CONFIGURATION.md`, "The two dataset shapes"), rebuilt from that description: one summary over a single finish-to-start chain, and a four-level portfolio (projects of ten packages of ten tasks, leaves chained inside a project). Their summary, leaf and link counts match the harness's table at every size it lists. Neither uses the seed; the file still records it.
- `tree4seq` and `tree4long`, ours (#100): `tree4` with a host `key` on every task, so the open of a keyed schedule can be read against the open of the same schedule without keys (`tree4`). `tree4seq` gives the task of id `n` the key `t<n>`; `tree4long` gives it 54 characters, 48 of them the same for every task and the last six `n` padded with zeros, so the keys differ only in their last characters (the case `keys.rs` once searched slowly, #99). Only our side reads a `key` (`ours-adapt.ts` hands it to `mount`); the other sides' files are what `tree4` gives. Compare the open with `node demos/bench/profile.ts --cell tree4-50000 --holder <lock name> --runs 10`, then the same with `--cell tree4seq-50000` and `--cell tree4long-50000`: `profile.ts` reads the cell's shape from its name.
- `stress`, ours: the engine's stress fixture, `stress(seed, n)` in `crates/engine/src/generate.rs`, with the same tasks, task ids and links. Durations are in 8-hour days; calendars, lags and start-no-earlier-than dates are left out, so its tasks carry no start and the links place them from the project start.

The dataset's `start` is Monday 2026-03-02. Every leaf of `chain` and `tree4` carries a start date (08:00), worked out by a forward pass over the shape's own links (`demos/bench/plan.ts`) on the calendar every side uses, Monday to Friday, 08:00 to 16:00: the date our engine computes from the links, so a leaf's given start never moves it. A `chain` leaf starts two working days after the one before it, so a 1,000-task chain ends in October 2033 and longer chains run for centuries. `stress` tasks carry no start: some start mid-day, and the links alone place them. The records are the ones `demos/dhtmlx-compare/to-mspdi.ts` reads, so `node demos/dhtmlx-compare/to-mspdi.ts <dir>/dataset.json <out.xml>` turns one into a file the chart opens, with the dates kept: the dataset's `start` is the file's `StartDate`, and a leaf's start is a start-no-earlier-than constraint on that day at 08:00. A duration that is missing, negative, not a number or not whole minutes is refused, and a leaf of no duration is written as a milestone.


### Driving any Gantt the same way (gs#1199)

`demos/bench/drive.ts` drives one page with real input only (Playwright's mouse and wheel), the same steps on every side, and writes one JSON result. It knows a side only through a module whose default export holds four hooks, `ready(rows)`, `scrollTarget`, `leafBars` (every task bar the page draws, summaries left out, as boxes on the page, and the width of a day) and `dragState(target)`, and optionally `backend`, `debugBuild`, `build` (the build's name, which labels its table row), `rowsOnScreen`, `spotCheck`, `settled` and `datasetSha256` (`demos/bench/side.ts`; the last is the SHA-256 of the benchmark `dataset.json` the page's schedule was made from, as the side's adapter recorded it, and lands in the result's `datasetSha256`, null when the side does not say; ours: "Our side's dataset" below); each runs in the page. `--probe ours` is our own, read from `window.gantt` and the hosted page's `#timeline` (`demos/bench/sides/ours.ts`); another side passes the path of its module. `--rows` is required: a side is ready only when it holds exactly that many tasks (our hosted page first mounts its own small schedule).

Each run gets a fresh browser and profile, with smooth scrolling and Chrome's background networking off. The GPU (WebGL's unmasked vendor and renderer) and the display rate (the median frame gap over one idle second) are read on a blank page of their own before the side's page opens. Then the phases run in order, each input step followed by a wait for the page's next frame:

- **load**: from the navigation to the frame after the first one whose `ready(rows)` holds, both ends on the page's clock (the document's `performance.timeOrigin`, and that frame's `requestAnimationFrame` time). The check runs once per frame in the page for every side. The page must then stay the same document and ready for 1 s; a page that reloads itself (ours on a WebGPU failure) is waited for again, and load ends at the ready frame of the page the other phases drive. Load is split at two performance marks the page sets, the same names on every side: `libraryMs`, from the navigation to `library-ready` (the component's code loaded and able to run: ours right after the wasm instantiates, in `packages/gantt/src/index.ts`; a script library once its module has run), and `dataToReadyMs`, from `data-start` (the page starts fetching the schedule: ours as the hosted page opens a sample file, whose download may already be under way, so a built-in sample such as `demo-50k` has none) to the ready frame; each is null without its mark. A side with a `spotCheck` then has a sample of its dates checked against the schedule's: a failed check makes load a dnf (`"spot check: …"`), so a broken setup gives no number at all (`spotChecked` says whether one ran; the dnf's cause is `error`, which the table refuses). A side with `settled` (one whose ready frame can come before the work its load started is done, such as Bryntum drawing saved dates while its engine still computes) is waited for before the spot check and the input phases, so they absorb none of that work: `settledMs` is when it was done, from the navigation, and `dataToSettledMs` from `data-start`; both null for a side without the hook.
- **scroll-y**: wheel events over the side's scroll target, 50 heights of the driver's viewport (40,000 px at the default 800) down from where the rows start, and back. The distance is fixed, not the schedule's height, because a person scrolls a few dozen screens, not the whole of a 50,000-task schedule; the schedule's size still sets what is drawn each frame, and the phase's time no longer grows with it. Every side follows one rule: the target is the smaller of that fixed distance and the side's own scrollable range on the axis (`scrollTarget`'s `maxTop`, `maxLeft`, less where the view starts), so a schedule shorter than 50 heights (about 1,700 rows at 24 px) scrolls its whole range and no cell is skipped. The result records the target (`target`) and the distance the view went out (`scrolled`), and the table prints it (`scroll-y distance median px`), so a shorter range stays visible beside the frame columns, which are per-frame figures. Every event is the sweep's length over 120, one a frame, the same size and pace on every side, and after each one the driver reads the side's `scrollTarget`: it keeps wheeling until that reads the target (within the check's tolerance below) or past it, then wheels back until it reads the start (within 2 px) or past it. A side that follows the wheel's delta arrives in 120 events each way; one that moves a fixed step per event (DHTMLX) takes as many as it needs. A way stops short after twice the events the smallest step any side has shown needs (DHTMLX's 90 px down: 890 for scroll-y, 570 for scroll-x), and never fewer than 240 (twice the 120 events a side that follows the wheel's delta takes), so a short range does not cut a delta-following side's sweep short, or once the view has not moved for 120 events; the check below then fails and warns. The result records the events sent each way (`wheelEvents`: `out`, `back`) beside `stepPx`.
- **scroll-x**: the same along the time axis, wheeled until it reads the target, 20 widths of the driver's viewport (25,600 px at the default 1280) or the side's own range along the axis when that is less (DHTMLX's at `tree4` 50,000 is 18,707 px; ours has no end), out and back.
- **drag**: press on a task bar the driver picks from the side's `leafBars` by one rule for every side (`demos/bench/grab.ts`): the first bar fully inside the side's scroll target, in row order. When none is in view, the wheel brings the first bar reported into it; when the bar is narrower than 6 px, ctrl+wheel over its centre zooms in on it (one notch, -100, a step), up to 30 steps, none of them recorded. While it zooms, a listener on the window stops the browser's own page zoom, so a side that leaves ctrl+wheel unhandled is not zoomed as a page, and a zoom step that leaves the side's width of a day as it was ends the search. After any step the driver waits until the bars the side reports stay the same for 1 s (load's settle time) before it picks again and presses, so the re-layout a step set off is not in the drag's frames. The result records the dragged task's id in the benchmark dataset (`task`, from the bar's `datasetId`; null when the side cannot say), the width of a day (`pxPerDay`) and the steps taken (`zoomSteps`, `scrollSteps`). A tree4 schedule needs it: our first screen fits the portfolio's whole span, so its 2-day leaves are 3 to 5 px wide (gs#1242). A side with no bar in reach then has a drag dnf (`no bar on screen to drag`, cause `error`). Then move it 10 days later in 60 moves, release, then keep recording until the side's `dragState(target)` changes (the drag is committed) and 10 frames more, so a side that commits after the release is timed until it has: `commitMs` is the time from the release to the commit. A drag whose state has not changed `--drag-commit-s` (default 30) after the release is unverified and carries no frame numbers, so none is published.
- **memory**: read twice, and the table compares the first: `afterLoad`, made `--memory-at-s` (default 20) seconds after the navigation, the page idle and settled (the driver waits out what is left of that time after load; a page already older is read at once; the read's start is recorded as `readAtS`, and the table refuses a run whose read began over 2 s past it, a slow load no other side's 20 s read matches), and `afterScripts`, after the input phases, which is recorded only. Each is the memory of Chrome's processes by process type, summed: every process (`chromeBytes`, the number to compare), the renderers (`rendererBytes`) and the GPU process (`gpuProcessBytes`); and `jsHeapUsedBytes`, the page's JS heap after a garbage collection. The heap alone is never the memory number: it leaves out WebAssembly memory (where ours keeps its schedule). `kind` says what the byte counts are. On Linux it is `pss`, the proportional set size from `/proc/<pid>/smaps_rollup`: a page shared by several processes (the renderer and the GPU process share some) is split among them, so the sum counts it once. On macOS it is `footprint`, the physical footprint `vmmap --summary` prints. Summed RSS would count a shared page once per process that maps it, so a side could be skewed either way by how much it shares; on Linux and macOS a process still running whose number cannot be read (`vmmap` refused by a hardened runtime, say) makes the sample throw, so the memory phase is an `error` the table refuses; it never falls back to RSS there. Other platforms read RSS (`rss`, from `ps`). PSS and RSS leave out GPU memory that is not mapped into a process (VRAM), so a side that keeps its schedule on the GPU can read low. Whether the macOS physical footprint counts the GPU's (IOAccelerator) memory is not yet measured on a Mac, so that is unverified. The table prints the kind's caveat beside memory. Chrome does not say which renderer draws which page, so renderers are summed; each side runs alone in the same fresh browser, so the sums compare. The processes are the ones CDP's `SystemInfo.getProcessInfo` lists.

Each input phase checks that it did what it claims and says so in `verified` (with `why` when not): a scroll must reach its target and come back to where it started (within 0.5% of the sweep or 2 px out, and 2 px back), and a drag must change the side's `dragState` (ours: the schedule's revision; Bryntum: the dragged task's start date). A phase that failed its check is also a line in `warnings`. Each frame phase reports the `requestAnimationFrame` gaps while it ran: `frames`, `p50`, `p95`, `max` (ms), `longGaps` (gaps over 1.5 display periods at `--refresh-hz`, default 60) and `droppedFrames` (for each gap, its display periods rounded, less one).

`--dataset-sha256` is recorded in the result as `requestedDatasetSha256` before load. A phase that runs past `--dnf-s` (default 120 s), or throws, is written `{"dnf": true, "cause", "afterS", "why"}`. `cause` is `timeout` (past `--dnf-s`, or the page did not answer in that time), `error` (a hook or the driver threw, or there was no bar to drag), `not-ready` (load: the probe never saw the asked-for row count by the deadline, which a wrong probe or adapter gives as much as a slow side) or `not-run` (an earlier phase did not finish). Its input stops there (every step checks an abort signal), the page is closed, and every later phase is written as a dnf naming it (`"not run: scroll-y did not finish"`): no number is taken from a page an unfinished phase may still be driving. A load with no ready frame by then is a dnf the same way. The result always holds every phase; an error outside any phase writes a result with every phase a dnf that names it. `--phases` (default all five) picks which are written; all run, so each side gets the same sequence. The result's `options` are the driver options (viewport, device pixel ratio, refresh, `--dnf-s`, headless, phases). Its `environment` holds the Chrome version, the OS, the Node version, the GPU, the viewport (default 1280 by 800), the device pixel ratio (default 1), the refresh rate given and measured, what the side says it drew with (`sideBackend`), whether it is not its production build (`debugBuild`; ours: the Vite dev server's client script is on the page; Bryntum: the unminified trial), the build it names (`sideBuild`) and how many whole rows the view shows (`rowsOnScreen`: ours 24 px rows, Bryntum's default 45 px). `warnings` names a headless run, a software or unknown renderer, a measured rate more than 10% off `--refresh-hz`, a debug build and each unverified phase: a result with warnings is a smoke run, not a result.

The driver is headed by default: run it on the machine with the GPU and a display. Chrome is the one the `@playwright/test` of `apps/hosted` (else `packages/gantt`) installed, or `--chrome <path>` (or `$CHROME`). Exit 0 when a result was written, dnf phases included; 64 for bad options or a probe without its hooks; 70 when the browser did not start (a launch that fails with ETXTBSY, a Chromium binary still being written, is retried 3 times, 1 s apart, first; gantt#1642). `--network fast-4g|cable` (gs#1328) runs the page over a slow link instead of the box's own: the latency and speeds are set through CDP before the navigation (`demos/bench/network.ts`: `fast-4g` is Chrome DevTools' "Fast 4G", 9 Mbps down, 1.5 Mbps up, 165 ms added latency; `cable` is WebPageTest's Cable, 5 Mbps down, 1 Mbps up, 28 ms, since DevTools has no cable preset), and the driver starts a server in front of `--url`'s origin that sends text, script, JSON, wasm and SVG brotli-compressed at quality 11, the same headers for every side, because no bench server compresses and the raw 6 MB wasm would be timed instead of the size a real host sends. Each file is compressed once and kept, before the measured navigation: the driver first loads the page once in a throwaway browser with no throttle, so the server has every file the page asks for, then measures in a fresh browser; a file of over 64 KB asked for only afterwards is compressed during the run, and the result says so in `warnings`. An existing `Vary` keeps its tokens and gains `Accept-Encoding`. The profile and the quality are written into the result's `options` as `network` and `brotliQuality`, so runs on different links never share a table row. Without `--network` the driver is as it was: no proxy, no `network` key. The test checks the numbers and the fairness rules on a small fixture side (a stalled phase, a throwing hook, input that does nothing, a wrong row count), then serves `apps/hosted/dist` with `vite preview` (build it first, samples included), drives `?sample=demo-50k` headless and checks one JSON with all five phases, each verified, then drives a tree4 cell of 1,000 tasks adapted into a copy of the build and checks its drag is verified; the `hosted` CI job runs it after its build, on every tier but fast (a batch run, the nightly run, a manual run and a push to main), and never on a push to a pull request's branch, whatever the diff changes (the maintainers' CI decides this; gantt#1163). `node --test demos/bench/grab.test.ts` checks the rule that picks the bar, and that a scroll phase wheels a side moving a fixed step per event until it reaches the target, and stops a side that never does at the cap, and that `--network` is refused for an unknown profile or a non-http `--url`, that the chosen profile reaches the CDP call after `Network.enable`, and that the compressing server sends a script brotli-compressed and a picture as it is, and that a browser launch failing with ETXTBSY is retried 3 times and a launch failing any other way is not.

### One table over the pairs (gs#1202)

`demos/bench/run.ts` runs the matched pairs over a list of cells and prints the table. A cell is a shape and a size (`--cells tree4:10000,tree4:50000`, named `tree4-10000` in the results); the seed is `--seed` (default 20261020). The two sides are named in a JSON file, `--sides`: `[{"name", "bundle", "probe", "path"}, ...]`, where `bundle` is the directory `pair.ts` serves, `probe` what `drive.ts --probe` takes, and `path` the page in that bundle with `{shape}`, `{size}` and `{seed}` replaced. Turning the dataset into what each side loads is that side's adapter's work: `run.ts` does not touch the bundles.

For each cell it writes the schedule and its SHA-256 to `<out>/<cell>/dataset.json` and `dataset.json.sha256` (refusing, with exit 65, a cell that already holds another hash, so one cell never mixes two schedules), then runs pairs numbered on from the last one there. Each pair is `pair.ts`'s: the two sides back to back on a quiet box, the order flipped on every other pair, each side `drive.ts --url <page> --probe <probe> --rows <size> --dataset-sha256 <the cell's hash> --out <out>/<cell>/<pair>/<side>/result.json` with the same options after `--` for both. Beside each result it writes `side.json`, the side's build: its sides.json `probe` and `path`, `bundleSha256` (one SHA-256 over the bundle's files in sorted path order, a symlink by its target) and `harness` (this repository's commit, `-dirty` when `demos/` has uncommitted changes). The tests run `runCells` with a fixed reader, so whether a pair matches never depends on the CI box's load. A cell stops at 4 matched pairs or at `--pairs` attempts (default and most 8). `--max-load` (also a `pair.ts` option) is the quiet cap on load1, default 4, written on each line of `wait.log`; the tests raise it so a busy CI box still runs them, and a measured run leaves it alone. Then it prints the table and exits with its code; a side whose command fails stops the run with `pair.ts`'s code.

`table.ts` reads the `result.json` beside each `load.log` and refuses a run, so no number of it reaches the table, when its result has `warnings` (headless, a software or unknown renderer, a debug build, a display rate off, an input phase that did not do what it claims) or no `warnings` field (with one exception: a side's trial build, which says it is not its production build and names a trial build, as Bryntum's does; its debug-build warning refuses only the columns an unminified bundle affects, library median, the whole load and memory, which print `trial build`, and not the run), is unreadable, has no environment, does not report the dataset it loaded (`datasetSha256`) or reports another than the cell's `dataset.json.sha256` (after a load that timed out, when the side never could say, the dataset the run asked for, `requestedDatasetSha256`, is checked instead, so the timeout prints as one), has no `side.json` beside it, belongs to a pair whose two drags moved different tasks of the dataset or did not record which (`task`; both runs of the pair are refused, so drag numbers compare only on the same task), or has a phase whose cause is `error` or `not-ready` (with its `why`; `not-run` is refused too unless a phase before it timed out). A cell without a `dataset.json.sha256` refuses every run, so no number is ever printed beside "not recorded". A refused run's pair says `refused`, never counts as matched, a `refused:` line names the run and why, and the table exits 3. A pair whose swap grew says `swap grew` and is not matched either. A pair is matched only when its load1 means are within 0.5, neither run's swap grew and both results are accepted; `run.ts` reads the same rule, so it keeps running pairs past an unmatched one, up to the attempt cap.

A cell with results prints its dataset hash. With 4 matched pairs in its first 8, it then checks that every run in those pairs shares one environment: Chrome version, OS, Node version, GPU vendor and renderer, viewport, device pixel ratio, refresh rate, the driver's `options` and the harness version, and that every run of one side shares one build (its `bundleSha256`, `probe` and `path`, and the build it names, `sideBuild`). If not, it prints the differing environments and no numbers, and the table exits 3. Otherwise it prints one row per side over those pairs, the same on every side:

- the side's name and the build it names (`bryntum: Bryntum 7.3.8 trial build, dates given`);
- `pairs`, the side's runs, and `first`, how many of those pairs it ran first (by the earlier first `load.log` sample);
- `rows on screen`;
- `library median ms` and `data to ready median ms`, the two parts of load (`libraryMs` and `dataToReadyMs`), `-` for a side whose page sets no marks, and `data to settled median ms` (`dataToSettledMs`), `-` for a side without `settled`;
- `load median ms` and `load max ms` over the runs' load times;
- `scroll-y`, `scroll-x` and `drag`, each three columns (and `scroll-y` and `scroll-x` a fourth, `distance median px`, the median of the runs' distance scrolled out, which is the fixed distance or the side's shorter range): `p95 median ms`, the median of the runs' own p95 frame gap; `long frames median %`, the median of the runs' share of frames longer than 1.5 display periods (`longGaps` over `frames`), which shows how often the page missed a refresh when p95 sits at the display's period; and `longest frame max ms`, the longest single frame of any run (the maximum of the runs' `max`, so one slow frame in one run shows);
- `memory median`, the `afterLoad` read, with its kind; the note under the table says when it was read (from the runs' `memoryAtS`; runs from before it are labelled legacy), and an `input files` line gives the bytes of the file each side loaded (the side's `inputBytes` hook; each side loads its own file of the one dataset, whose hash is printed above the table).

A median of an even count is the mean of the middle two; with 4 runs the maximum is the worst run, not a percentile. No warm-up run is discarded (the plan's one discarded warm-up is not applied): every run is a fresh browser and profile, and the table says so. Only a `timeout` prints as `did not finish in <s> s (<n>/<runs>)`, and a phase not run after it as `not run (<n>/<runs>)`, never a number from the runs that did finish. An unmatched cell prints no numbers. Memory of two kinds in one cell is not compared (`memory not comparable`), and every kind shown gets a `memory:` line saying what it counts and what it leaves out.

**Setup.** `setup-harness.ts` clones the DHTMLX comparison harness at its pinned commit (`HARNESS_COMMIT`, the harness's commit, not ours) into the scratch directory, swaps the harness's trial package for the MIT Community one and installs it. Nothing of a vendor's goes into this repository: a scratch directory inside any git work tree is refused (exit 1, "refusing to put DHTMLX code"), so pick one outside every repo (default `$TMPDIR/dhtmlx-harness-<sha7>`), and one that already exists is refused too (exit 1), so a rerun never builds on top of an old install. Any other option exits 64.

**Run.** `run.ts` takes the two sides in `sides.json` (`[{"name", "bundle", "probe", "path"}, ...]`, "One table over the pairs") and the cells as `shape:size`. It writes each cell's schedule and its SHA-256, then runs pairs on a quiet box until a cell has 4 matched pairs or `--pairs` attempts (at most 8). What it refuses:

- a cell directory that already holds another dataset's hash (exit 65): one cell never mixes two schedules, so use another `--out`;
- options it does not know, a missing `--sides`, `--cells` or `--out`, or a `sides.json` that does not name exactly two sides with different names (exit 64);
- a box that never goes quiet within `--wait-s` (exit 75 from `pair.ts`): a build job running, load1 at or over `--max-load` (4; raise it only for a smoke run), or swap used still growing;
- a side whose driver fails (`pair.ts`'s code: 1, or 70 when it cannot start).

**Table.** `table.ts` prints the table from the results directory: each pair with its two runs' mean load1 and its verdict (`matched`, `not matched`, `refused`, `swap grew`), each cell's matched count, its dataset hash and its rows, then a `refused:` line per refused run with why. Exit 0 is a table; 1 is "no rows" (an empty table is a failure, not a result); 2 is "swap grew" (that pair is not matched and none of its numbers count: the box was paging); 3 is a refused run or a cell whose runs differ. A cell with fewer than 4 matched pairs in its first 8 prints `no numbers` for both sides and, with nothing refused, still exits 0. A run is refused, and none of its numbers print, when its result:

- has `warnings`: headless, a software or unknown renderer, a debug build, a display rate more than 10% off `--refresh-hz`, or an input phase that did not do what it claims. A result with warnings is a smoke run, not a result. The one exception is a side's trial build ("Bryntum's load" below): its debug-build warning refuses only some of its columns, not the run;
- has no `warnings` field (not a driver result), cannot be read, or has no environment (the run broke outside any phase);
- does not report the dataset it loaded, or reports another than the cell's `dataset.json.sha256` (a cell without that file refuses every run);
- has no `side.json` (the side's build) beside it;
- has a phase that threw (`error`), whose probe never saw the row count (`not-ready`), or that was `not-run` with no timed-out phase before it.

A refused run makes its whole pair `refused`, so the pair is not matched and counts for neither side: one side's refusal costs both sides that pair. A cell's numbers print only when every run in its matched pairs shares one environment (Chrome version, OS, Node version, GPU, viewport, device pixel ratio, refresh rate, the driver's options, and `harness`: this repository's commit that ran the pairs, with `-dirty` when `demos/` has uncommitted changes, from `harnessVersion` in `demos/bench/build.ts`), and every run of one side one build (`bundleSha256`, `probe`, `path` and the build the side names, `sideBuild`); otherwise the table prints the differing environments and no numbers.

**The statistics.** Each side's row, over the cell's matched pairs, labelled with the side's name and the build it names (`bryntum-dates: Bryntum 7.3.8 trial build, dates given`): `pairs`, its runs, and `first`, how many of those pairs it ran first; `rows on screen`; `library median ms` (navigation to the page's `library-ready` mark) and `data to ready median ms` (its `data-start` mark to the ready frame; "Driving any Gantt the same way", **load**), `-` for a side whose page sets no marks; `data to settled median ms` (`data-start` to when the side's own load work is done), for a side whose ready frame can come first, `-` for the others; load as the true median and the maximum of the runs' load times (a median of an even count is the mean of the middle two; with 4 runs the maximum is the worst run, not a percentile); scroll-y, scroll-x and drag as the median of each run's own p95 frame gap, the median of each run's share of frames over 1.5 display periods and the longest frame of any run; memory as the median of the read 20 s after the page opened. No warm-up run is dropped: every run is a fresh browser and profile. A phase stopped at `--dnf-s` prints "did not finish in <s> s", and a phase not run after it "not run", never a number from the runs that did finish.

**Memory and the GPU.** The memory column is Chrome's processes summed, by kind: `pss` on Linux (a shared page counted once), `footprint` on macOS (`vmmap`'s physical footprint), `rss` elsewhere (a shared page counted once per process). The table prints a `memory:` line with each shown kind's caveat. PSS and RSS leave out GPU memory that is not mapped into a process (VRAM), so a side that keeps its schedule on the GPU can read low; whether the macOS footprint counts the GPU's (IOAccelerator) memory is not yet measured on a Mac, so its GPU share is unverified. A cell whose runs read two kinds prints `memory not comparable`, no memory numbers and no caveat line for those kinds. The JS heap is recorded but is never the memory number: it leaves out WebAssembly memory, where ours keeps its schedule.

**The dated results file.** `results-file.ts` writes `demos/bench/results/YYYY-MM-DD.json` (a second run on the same day: `YYYY-MM-DD-run2.json`), from the run directories. The one line of `demos/bench/results/current` names the file `scripts/bench-table.ts` reads and the page shows; change it to publish a new run: `node demos/bench/results-file.ts --runs results --head <commit> --date <YYYY-MM-DD> --notes notes.json --out demos/bench/results/<date>.json`. The cells (dataset hash, pairs run, pairs matched, a note for each pair not matched), the box's load1 samples and the medians come from `<cell>/<pair>/<side>/{result.json,side.json,load.log,wait.log}` and `<cell>/dataset.json.sha256`, over the same matched pairs `table.ts` counts; `longestFrameMaxMs` is the longest frame of any matched run in the scroll and drag phases. `notes.json` holds the prose no run directory says: `story`, `machine`, `command`, `driverOptions`, `method`, `tree`, and `box` with `quietCap` and `wallClock`. It refuses, exit 1 and nothing written, when any `side.json` under the runs directory (every pair, counted or not) has a harness that is `unknown`, ends in `-dirty` or is not `--head`, or when `--head` is not a 40-digit commit; it exits 2 when the notes are incomplete or a side directory's `side.json`, `result.json`, `load.log` or `wait.log` cannot be read, and 64 on a usage error. It also refuses (exit 1, naming the cell, side and figure) when a matched run has no figure for a median the page reads, because a phase timed out or did not run: `null` in the file would read as zero on the page. ### The Bryntum side (gs#1203)

`demos/bench/sides/bryntum.ts` is the Bryntum Gantt side of the driver: its hooks read the trial's Gantt through its public API (`window.gantt`) and the page's own elements. `ready(rows)` holds once the task store holds `rows` tasks, a row is on the page, and the first task bar in the time axis is drawn where its task's start date puts it (its left edge within 1 px of `getCoordinateFromDate(startDate)`); without dates given, also once the project's initial commit has fired `dataReady` (Bryntum draws before its engine has placed the tasks, and its `isEngineReady` already holds before that first calculation starts). `settled` is when that first calculation was done, so with dates given the input phases wait for it. The scroll target is the time axis column clipped to the body that scrolls it; the drag target is a task bar fully on screen, with its task id and one calendar day's width; the drag state is that task's start date as of the last time Bryntum's engine was idle (the record takes its new date at the drop, before the engine has rescheduled what follows it); the backend is `DOM`; `datasetSha256` is the hash the adapter wrote into the cell's file; `debugBuild` is true, because the trial is not Bryntum's production build (its README: "Trial bundles are not minified"), and `build` names it ("Bryntum 7.3.8 trial build", and ", dates given" for that variant), so the table prints its row with data to ready (and to settled) and the input phases, and "trial build" for library, the whole load and memory.

Nothing of Bryntum's is in this repository. The reader installs the trial for their own evaluation with `demos/bench/sides/bryntum-setup.ts --trial <scratch-dir>`: without `--trial` (the reader's statement that they start a Bryntum trial under Bryntum's EULA, whose trial grant is for internal evaluation only) it exits 64 and installs nothing, and a directory inside a git work tree or one that is not empty is refused (exit 1). It installs `@bryntum/gantt-trial` at the pinned version (`TRIAL`, 7.3.8, the npm `latest` on 2026-11-02) from the public npm registry, as Bryntum's install guide says: aliased to `@bryntum/gantt`, exact version, its own install script run. Then it writes the page beside it: `index.html` (the build's label, Bryntum's icon font, `gantt.css` and the Svalbard light theme, as its examples load them) and `page.js` (`bryntum-page.js`, our code). The scratch directory is the side's bundle for `run.ts`, and its hash covers every file in it, the cells' files included: write every cell's files (`bryntum-dates.ts`) before the first run, or a side's runs from before and after differ in build and the table will not combine them.

The page is set up per Bryntum's own large-data guidance. As its big data set example does (https://bryntum.com/products/gantt/examples/bigdataset/): the Gantt is made first, with three columns (name, start date, duration) and no column lines, and the schedule then goes in as one new `ProjectModel` from the whole data at once, with `useRawData` on the task and dependency stores (the example's approach A); everything else is Bryntum's default, so the time axis spans the project. `?cell=<shape>-<size>-<seed>` names the schedule, `cells/<cell>/` of the scratch directory. As its console advises above 1,000 tasks ("Consider providing both `startDate` and `endDate` for all tasks"), there are two variants: without `dates` the page loads `bryntum.json` (constraints and links only; Bryntum's engine places every task on load, as ours does), and with `&dates` it loads `bryntum-dated.json`, the same tasks with the start and end dates Bryntum's own engine wrote back on a first pass, as a real app loads a saved project; that variant is ready once its bars are drawn at those dates, and its input phases start once the engine has finished. In sides.json they are two sides, with the paths `?cell={shape}-{size}-{seed}` and `?cell={shape}-{size}-{seed}&dates`. Bryntum's performance guide ("Performance optimization" in https://bryntum.com/products/gantt/docs/guide/Gantt/build-production) adds minified and thin bundles; the trial ships neither, which is why its library load and whole load are not compared.

The two load marks sit where ours are. `library-ready` is set once the library has run (ours: once the wasm has instantiated). `data-start` is set once the component is made and before the schedule's fetch: ours starts the file's download while the engine loads, mounts the chart (canvas, GPU and a small schedule of its own) and, once it is made, opens the file, so the mark is set at the open and the part of the download that ran beside the engine is not in data to ready (it is in the whole load); the Bryntum page makes its empty Gantt and then fetches the file and builds the project. Data to ready then starts at the same point on both sides and ends at the first frame that shows the schedule. Without dates given that span holds the fetch, the parse, the schedule computed and drawn, on both sides; with dates given Bryntum draws the saved dates first, so its data to ready leaves the engine's first pass out, and its data to settled, from the same mark to the end of that pass, holds it.

`demos/bench/sides/bryntum-adapt.ts <dataset.json> <scratch-dir>` writes the schedule the page fetches, `cells/<shape>-<size>-<seed>/bryntum.json` and its SHA-256, with the dataset's own SHA-256 inside (`datasetSha256`, which the page takes out before Bryntum sees the data and the side reports, so the table checks it against the cell's), and refuses a dataset its `dataset.json.sha256` does not name. It is the same schedule as ours, not only the same records: a project calendar of Monday to Friday, 08:00 to 16:00 and nothing else (8 hours a day, 5 days a week), leaf durations in hours (the dataset's days times 8), a leaf's start as a start-no-earlier-than constraint at 08:00 of that day, every link with its type and no lag, the project start at 08:00 of the dataset's `start`. Summaries are expanded, so every task is a row. The community edition has no working-time calendars: its readme's "Community vs PRO" table marks "Working-time calendars (setWorkTime, custom work calendars)" PRO only, and in 10.0.3 `setWorkTime` returns true and changes nothing (Saturday and 22:00 read as work time, `getWorkHours` is `[0, 24]`, and `calculateEndDate` from a Friday 15:00 by 120 minutes is 17:00 that day). The sweep's distance is fixed ("Driving any Gantt the same way", **scroll-y**), so DHTMLX needs at most about 445 events down and 285 along, not the 4,000 and up it needed to cross the whole schedule, and the default `--dnf-s` of 120 s is enough. Headless runs of all five phases on 2026-11-03, seed 20261020, at `tree4` 50,000, `stress` 2,000 and `chain` 1,000 (a smoke run: its numbers are not results): load ready with the spot check passed, the dataset hash reported, the drag verified, both scroll phases unverified as above (before the driver wheeled to the target), and no request off the box.

### Handing the schedule to each side (gs#1198)

Each side has its own adapter beside it in `demos/bench/sides/`: ours is `ours-adapt.ts` (the plain tasks and links `mount` takes, dated as DHTMLX's are), Bryntum's `bryntum-adapt.ts`, SVAR's `svar-adapt.ts` ("The SVAR side"), and DHTMLX's `dhtmlx-adapt.ts <dataset.json> <out-dir>`, which writes what the DHTMLX community side loads (its `<out-dir>` is the cell's directory in the side's scratch directory, `<scratch-dir>/cells/<shape>-<size>-<seed>`). A dataset with no `start` starts on `to-mspdi.ts`'s `DEFAULT_START` in ours, DHTMLX's and Bryntum's.
