# Importing a schedule

What the P6 XER and MS Project XML readers map, what they leave out, and how to open a file. The XER mapping itself is described in [ARCHITECTURE.md](ARCHITECTURE.md); the J1 chapter of the book ([../book/src/open-a-schedule.md](../book/src/open-a-schedule.md)) has the steps by hand.

The parser is `import::parse_mspdi` in `crates/import`; it depends only on `engine` and `quick-xml`.
It maps task names, outline levels and parents, working-time durations, elapsed durations (a task whose duration unit is elapsed minutes, hours, days, weeks or months runs in a 24-hour, seven-day calendar, so it spans nights, weekends and holidays; gs#690), milestones, task constraints (`ConstraintType` 1 to 7, see below), task calendars, the project start and the status date.
The project's `StatusDate` is the data date (gs#563): the app draws the data-date line at that date and time, as written in the file, so a late-evening time with a zone offset still shows the same day. A file with no `StatusDate` has no data-date line. A `StatusDate` that is not a date, or that falls before the Monday on or before the project start, is ignored and listed in `Imported.unsupported`, as the XER reader does for a bad data date (`crates/import/tests/mspdi_status_date.rs`). The file's data date, from an MS Project `StatusDate` or a P6 `last_recalc_date`, applies at open: unfinished work starts no earlier than it from the first schedule, before anyone edits (gs#736).
It maps FS, SS, FF and SF links with lag (a lag in an elapsed unit counts in all minutes, so a 2-day elapsed lag runs across a weekend; gs#703), plus calendar weekdays, working times, and exceptions: a non-working exception is a holiday and a working exception replaces the day's periods. Both readers hold the engine's ranges (`crates/engine/src/model/range.rs`) and never fail on a value outside one: a duration over 100 years of 366 days (`MAX_DURATION`) is set to it, a lag of more than that size either way reads 0, and a date more than 1,000 years either side of the schedule start (`MAX_DATE`), a remaining duration over `MAX_DURATION` and a data date outside the range are left out. Each kind earns one counted note with the number of tasks and the first five (`crates/import/src/range.rs`). A negative P6 duration, or a P6 duration or lag that is infinite or not a number in the floating-point sense, still fails the import; a P6 duration or lag cell that holds text is skipped with a warning (a lag reads as 0, a duration as none). An MS Project `Duration` or `LinkLag` that is not a number still fails the import. A negative lag is a lead and is read.
A work week (a date range with its own weekdays, such as one that works Saturdays) sets the weekdays it lists on every date in its range, up to 3660 days, and an exception on a date beats it. A derived calendar's work week keeps its base calendar's holidays: a base-calendar holiday inside the range stays a holiday unless the derived calendar has its own exception on that date. A weekday it does not list keeps the calendar's own week (or its base calendar's), as in MS Project; a listed weekday that is not worked stays off. A work week with no valid date range is left out and noted.
A recurring exception is expanded into its dates between `FromDate` and `ToDate`: daily every N days, weekly on the days in `DaysOfWeek` every N weeks (weeks start on Sunday), monthly on a day of the month and yearly on a month and day (the last day of a shorter month). The meanings of `Type`, `DaysOfWeek` (Sunday is 1) and `Month` (January is 0) follow the MPXJ reader; they are not checked against MS Project itself. A recurrence on a weekday of a month ("the second Friday") and a recurring exception missing a field it needs are left out and noted.
`Imported.unsupported` lists a constraint with no date, percent lags, resources, a deadline that is not a date, inactive tasks, recurring exceptions on a weekday of a month and missing calendars instead of silently dropping them. Each MS Project line is a sentence in a scheduler's words: it names the task or calendar, says what the reader did not read, and says whether a date can change ("Task 2: a link lag has a fraction ..."), with no file-format name standing in for the sentence (gs#881). The tasks that are inactive, scheduled manually, carry a leveling delay or have a deadline that is not a date are counted, one line per kind, ending with the count and the UIDs of the first five ("Tasks with a leveling delay: the delay was not read, so their dates can differ from the file's: 600 (first: 1, 2, 3, 4, 5)"), and those lines list before the sentences. The P6 lines are sentences too (gs#976), and each line about activities ends with how many activities it covers and the IDs of the first five, for example "Activities with the unrecognised (CS_XYZ) constraint: the constraint was not read and they are scheduled without it, so their dates can differ from the file's: 2 (first: A1010, A1020)". The importer keeps no list of the rest, so a counted note names at most its first five IDs and its count is the only complete figure.
A task with a non-empty `Notes` element adds one line, "Task notes were not read; no dates are affected.", however many tasks have notes; the text is not carried (`crates/import/tests/mspdi_task_notes.rs`, gs#703). Resource assignments add one line, "600 tasks have resource assignments; only the resource names were read, and no dates are affected." (the count is the number of tasks with a real resource; "1 task has" for one), not one line per task (`many_assigned_tasks_give_one_resource_note` in `crates/import/tests/mspdi_mapping.rs`). The reader keeps the name of each resource assigned to a task, once each and in the order of the assignments, on `ImportedTask.resource_names`; a resource with no name or none listed adds nothing, and no date follows from them (`crates/import/tests/mspdi_resource_names.rs`). Opening the file keeps them as the session's `Loaded::resources` (`Session::resources`, display only: an edit never changes them, a saved schedule document does not carry them), and the hover card lists them on a "Resources" row, the first three then `+N`; a task with none has no row. Task costs add one line the same way, "3 tasks state a cost; costs were not read, and no dates are affected." ("1 task states" for one): the count is the tasks, summaries excluded because their cost rolls up their children's, with a nonzero `Cost`, `FixedCost` or `ActualCost` (`a_file_with_task_costs_gets_one_cost_note`); a file whose costs are all zero gets no line.
A link whose predecessor is not a task in the file (a link to another project) is dropped, the file still opens, and the list names the successor task and the missing predecessor task.
A summary task becomes a zero-duration engine task with no constraint, and the importer adds no note for it (the app rolls summaries up, so the panel does not say they are "scheduled later"); the app then builds the outline from the parents and draws each summary bar spanning its children, rolled up from their dates (`Session::with_outline`, `crates/app/src/outline.rs`; gs#47, PR #70, #73). Load a file with `demos/50k/run.sh --schedule <file.xml>`: it builds the app, copies the file to `packages/gantt/dist/schedule.dat` under that fixed name, and serves `http://127.0.0.1:4173/?schedule=1`. The page fetches the bytes and the wasm module parses them with `import::parse_mspdi`. The outline forbids a dependency on a summary task (gs#47 ruling 5), so every dependency with a summary task at either end is dropped and added to the `unsupported` list as one line naming the link and the summary task (`load_bytes` in `crates/app/src/load.rs` writes it; the importer adds none). The page shows that list's count and up to 500 lines in a panel you can close, then a last line `and N more` (the title keeps the full count). A malformed or missing file shows the error text and draws no chart.

**Open a file from the page.** Press "Open…" in the toolbar (or Ctrl+O while focus is in the chart) and choose a P6 XER, an MS Project XML or a .gantt file, or drop one on the chart; a dashed outline and the words "Drop to open" show while a file is over it, and a file dropped beside the chart is refused without the page leaving for it, unless a drop zone of the host page's own or another chart takes it. The file is read in your browser and handed to the WebAssembly module as bytes: nothing is uploaded, and the page makes no network request for it (the specs in `packages/gantt/tests/open.spec.ts` assert that). The new schedule replaces the one on the page in place: the selection, search, filter, collapsed rows and undo history of the old one are gone, and the view is fitted to the new one. A file that cannot be opened (truncated, neither format, empty, or over 256 MiB, which is never read) shows its reason on a red line under the toolbar (for a file that cannot be parsed, the line ends with a sentence that names the product and the formats it opens: P6 XER, MS Project XML and .gantt files) and leaves the schedule on the page as it was. If several files are dropped, the first opens and the toolbar says how many were ignored. The status line (`s`) shows where the open time went: read, paint, copy, parse, build, compute, swap and first frame (see "Open time" in [MEASURING.md](MEASURING.md)).

To start the page with a file already loaded instead, pass it on the command line: `demos/50k/run.sh --schedule <file.xml or file.xer>`.
An XER activity lists under its WBS node by the start the Start column shows, the engine's computed start with the actuals and data date applied, then by activity code with digit runs compared as numbers (`A1-2` before `A1-10`). The file's own early start does not set the order, so dates never run backwards down a work package. Sibling WBS nodes keep the file's `seq_num` order, and the MS Project reader keeps file order (gs#865).
The app tells the two formats apart by content, not by file name: a file whose first line starts with `ERMHDR` (after an optional UTF-8 byte order mark) is XER and goes to `import::parse_xer`; a file that starts with the OLE2 signature (`D0 CF 11 E0 A1 B1 1A E1`) is an MS Project binary file (.mpp) and is refused with a line that says to choose File > Save As in MS Project and pick the XML format; any other file is read as MS Project XML.
A file that starts with `%PDF` (a PDF) or `PK\x03\x04` (a ZIP archive, such as an `.xlsx` file), or XML whose root is not `Project`, is refused with `ImportError::NotASchedule`: "this is a PDF file, not a schedule; open a P6 XER file or an MS Project XML file", with "a ZIP archive (...)" or "an XML file whose root is <name>" (cut at 40 characters) in place of "a PDF file" (`crates/import/tests/bytes_not_a_schedule.rs`).
A P6 XER file with several projects first shows a project list (gs#87; gs#81 ruling 4): one button per project with its id, short name and activity count, and a last button that opens all of them, each as a top-level summary. Esc or Cancel closes the list and leaves the schedule on the page as it was.
A task with an `ActualStart` and no `ActualFinish` is in progress. When the `Start` or `Finish` the file states for it falls on a different calendar day than the engine computed, the panel counts the task in the in-progress line, as for an XER activity (gs#691). Both readers apply actuals (gs#860, below), so the dates differ only where the file's own `Start` and `Finish` disagree with the engine's. A task whose actual start or finish is after the data date is kept as the file states it and counted in one line in both readers, `tasks with an actual date after the data date, kept as the file states them: <count> (first: <the first five activity IDs or UIDs>)`, like the other counted lines above; the app refuses to type such a date (the progress cells and the task dialog), but an import is not refused.

The MS Project reader keeps each task's saved baseline: the `Start` and `Finish` of its `Baseline` element numbered 0 (`ImportedTask::baseline_start` and `baseline_finish`, instants from the schedule origin, negative when the baseline falls before it). MS Project can save either date without the other, so each is read on its own; a task with no baseline 0, or one that states only a cost or duration, has neither, and an unreadable date is left out. Baselines 1 to 10 are not read. The P6 reader has no baseline yet. Opening a file keeps them as the session's baseline (`Loaded::baseline`): a task with both dates has an entry, and the baseline's project finish is the latest baseline finish. A file states no float, so those entries hold none, and the status line counts such a task as slipped but never as joining or leaving the critical path. A task with one date, or none, has no entry and counts as added. Opening it is no edit, so the history stays empty, and a later Export writes the `Baseline` element back; one that states only a cost or one date is listed in `left_out`.

The MS Project reader also keeps each task's `Deadline` (`ImportedTask::deadline`, an instant from the schedule origin, negative when it falls before it; `None` when the file states none or one that is not a date). The session keeps it for display (`Loaded::deadlines`, `Session::deadline`); no date, float or link moves for it, an edit never changes it, and the hover card shows it with how many days the task misses it by (`App.task_deadline_text`), so a deadline that is a date has no line in `Imported.unsupported`; one that is not a date is counted in "Tasks with a deadline that is not a date: the deadline was not read; no dates are affected: 1 (first: 1)". The P6 reader has no deadline. A saved schedule document does not carry it, so a reopened one has none.

The reader is best effort and the unsupported panel lists what it left out: constraints it cannot apply, and any unknown code value. The MS Project reader applies a task's `ConstraintType` as the engine's limits (`engine::Limit`, `constraint` in `crates/import/src/tasks.rs`; gantt#1875): 1 is as late as possible, which needs no date, 2 is a start pin, 3 a finish pin, 4 start-no-earlier-than, 5 start-no-later-than, 6 finish-no-earlier-than and 7 finish-no-later-than, each from the task's `ConstraintDate`. A task has one constraint, so there is no second pin to leave out. Type 0 (as soon as possible) is the default and needs nothing. A summary takes none. A type 2, 3, 5, 6 or 7 with no `ConstraintDate` and an unknown type are listed in `Imported.unsupported` ("Task 3: the finish no later than constraint (type 7) has no date and was not read; ..."). Writing an MS Project file carries one constraint per task, in the same types and from the same limits (see the export section below). The XER reader applies both of an activity's date rules, the primary (`cstr_type`, `cstr_date`) and the secondary (`cstr_type2`, `cstr_date2`), as the engine's limits (`engine::Limit`, `crates/import/src/xer_activities/constraints.rs`): `CS_MSOA` is start-no-earlier-than, `CS_MSOB` start-no-later-than, `CS_MEOA` finish-no-earlier-than, `CS_MEOB` finish-no-later-than, `CS_MSO` and `CS_MANDSTART` a start pin, `CS_MEO` and `CS_MANDFIN` a finish pin, and `CS_ALAP` as late as possible, which needs no date. When both rules set the same bound the stricter one holds; a second pin that differs from the first is left out. A dated type with no date, an unrecognised code and that second pin are listed in `Imported.unsupported` ("Activities with the secondary mandatory finish constraint: ..."). Writing an XER file carries a task's date rules as its primary and secondary constraints (see the export section below). Both readers also hold each task at its project's start as a floor, and an earlier constraint is overridden by it: a task starts no earlier than the later of its project's start and its own constraint date, whatever links it has (`crates/import/src/floor.rs`, ruling devteam-1-64), and a task whose project has no start date keeps its own constraint, if any. An XER activity's actuals are applied at open (gs#703, decision 0008): an Active or Complete activity keeps its `act_start_date`, a Complete one is fixed at its `act_end_date`, and a started one finishes its `remain_drtn_hr_cnt` after the data date; the in-progress dates line counts only the activities whose dates in the file still differ from the engine's. An MS Project task's actuals are applied the same way (gs#860): a task with an `ActualStart` keeps it, one with an `ActualFinish` too is fixed at its actual dates, and a started task finishes its `RemainingDuration` after the `StatusDate`. A summary takes none, a `RemainingDuration` with no `ActualStart` is not taken, and `PercentComplete` is shown but moves no date. A started task's `Resume` is kept as `Limit::resume`, so its remaining work starts no earlier; the writers write neither `Resume` nor `Stop`, so a round trip drops them. What the reader leaves out of a task it lists, one line each: an `ActualStart` or `ActualFinish` that is not a date, an `ActualFinish` with no usable `ActualStart`, a `Resume` that is not a date or sits on a task with no actual start or a finished one, a `Stop` date, and an `ActualDuration` on a task with no actual dates ("Task N: the actual duration was not read because the task has no actual dates; no dates are affected."). A summary lists none, and a `RemainingDuration` alone is not listed, because MS Project writes one on every task. The XER import counts a link's lag in the calendar the file's lag calendar setting names; a file that does not state it gets Predecessor, with a note (gs#148). The XER mapping is described in `docs/ARCHITECTURE.md`.
An XER file's activity code tables (`ACTVTYPE`, `ACTVCODE`, `TASKACTV`) are read by `xer::read` into typed rows, so the "tables not read" line no longer lists them, and the import maps them onto tasks (gs#714): each activity's `TaskMeta` lists its codes as (code type name, value) pairs in the order `TASKACTV` gives them, the value being the code's short name, or its full name when the file gives no short name. An activity with no `TASKACTV` row has none, and so does a WBS summary. An assignment that names a code or code type the file lacks, or a code with neither a short name nor a name, is dropped and counted in the notes ("activity code ignored"); a file with `TASKACTV` rows but no `ACTVTYPE` rows or no `ACTVCODE` rows at all is dropped without a note. The Filters panel has an Activity code type and value filter that uses them (gs#771).
Each task keeps a WBS code (`ImportedTask::wbs_code`, gs#703). For an XER task it is the `wbs_short_name` of each WBS node from the project's real root down to the task's own node (a WBS summary's own node, an activity's node), joined with a dot (`HAND.1.2`); a node with no short name adds no segment, a project with no real WBS root has no root segment, and an activity on an unknown node takes the root's code. For an MS Project task it is the text of the `WBS` element, trimmed; an empty or missing element gives none. The table shows a WBS column only when the file gives at least one code.
An XER calendar takes the holidays it lists itself and none from its base calendar. Whenever a calendar above it on the base chain lists holidays, the notes list says "Calendar N: holidays listed on its base calendar are not applied to it; working days can differ from the file's", whether the calendar states its own week or takes the base week. Whether P6 already copies a base calendar's holidays into the calendar based on it when it writes the file is not verified on a real P6 export, so the import keeps the dates the file states and says so (gs#126). A calendar of type CA_Rsrc above it on the base chain counts like any other: its holidays raise the note and its week can be taken as the base week (gs#599).
The notes list names a calendar only when the opened projects use it: a project's calendar, the calendar of one of its activities, or a calendar on their base chains. A calendar that no opened project uses adds no note, even when the reader found a problem in its data, and it changes no date; a file whose calendars are all used lists the same notes as before (gs#590).
To see where the time goes at 50,000 activities, run `cargo test --release -p app --test it -- --ignored --nocapture xer::timing`. It builds a generated file with `xer::synth` (a test input writer, not an XER exporter) and prints the parse, map and solve phases and the whole `load_schedule` call; it asserts no timing. On the hub (release build, a 34 MB generated file, 50,201 tasks) one run measured parse 112 ms, map 50 ms, solve 10 ms and 231 ms for the whole `load_schedule` call. A real P6 file has more tables and wider rows than the generated one, so its figures differ.
The MS Project reader has the same kind of timing test, next to the P6 one: `cargo test --release -p app --test it -- --ignored --nocapture mspdi_timing::`. It writes a 50,000-activity MS Project file with the writer in `crates/app/tests/common/mspdi_synth.rs` (18.1 MB: one root, 200 summaries, 50,000 tasks, 57,141 links, and one in-progress dates line in the unsupported list, since the actuals are applied) and a 50,000-activity XER file of the same shape, then calls `load_bytes` on each three times in turn, printing the milliseconds and the machine load beside every call; it asserts no timing. A 5,000-activity case of the same file runs in the normal test run and asserts the task count and that no link is dropped. On a quiet MacBook Pro (Apple M3 Pro, 12 cores, release build, load average 1.44 before the run) `load_bytes` took 126.4, 127.9 and 127.2 ms for the MS Project file and 94.8, 96.8 and 95.1 ms for the XER file: the MS Project open takes about 1.3 times as long as the P6 one. A run on a busy Dell laptop (load average 9.7 on 20 cores, a release build) read 212 to 267 ms for MS Project and 154 to 173 ms for XER; that is not a quiet-machine figure. A real MS Project file has more elements per task than the generated one, so its figures differ.
An external LGPL MPXJ checkout is never committed here; run its corpus with `MPXJ_DATA=<checkout>/junit/data cargo test -p import --test mpxj_corpus -- --nocapture`.

## Writing an MS Project XML file

`import::export_mspdi(&Imported)` writes the project the reader returned as an MS Project XML file and returns the bytes with `left_out`, a list of strings (`crates/import/src/export/mspdi.rs`, gs#703). The Export dialog's MS Project XML button calls it through `Gantt.exportMspdi` (`FORMATS` in `apps/chrome/src/export.ts`): `crates/app/src/export.rs` wraps it for a session and `crates/app/tests/export_mspdi.rs` tests it.
It writes the inverse of what the reader maps: the project `StartDate` (kept in `Imported::project_start`, because the origin is only the Monday on or before it) and the `StatusDate` when the project has a data date; every calendar with its weekdays, working times and exception days, each as a base calendar with no parent; and for each live task its `UID`, `ID`, `Name`, `OutlineLevel`, `Summary`, `Duration`, `Milestone`, its constraint (`ConstraintType` and `ConstraintDate`, below), `Deadline` (the session's, `Session::deadline`), `CalendarUID`, `WBS`, `PercentComplete`, the file's own `Start` and `Finish`, for a started task its `ActualStart` and `RemainingDuration` and for a finished one its `ActualFinish` (the reader takes the last two only with a start), its baseline 0 and one `PredecessorLink` for each link with its type and lag. Durations and lags are written in hours (`DurationFormat` and `LagFormat` 5), or elapsed hours (6) for a lag counted in all minutes; an elapsed task is written on its all-minutes calendar, which the reader reads as an ordinary calendar. A task with sub-tasks and no work of its own is a summary; one that has its own duration or calendar is written as a task. The project start is `StartDate`, not a constraint on every task, so a task gets a `ConstraintType` 4 only when its own date is later. A task's limits are written as the types the reader maps them from (`constraint` in `crates/import/src/export/mspdi/constraint.rs`; gantt#1875): 1 as late as possible, 2 a start pin, 3 a finish pin, 5 start-no-later-than, 6 finish-no-earlier-than and 7 finish-no-later-than, each with its `ConstraintDate` (1 has none). The file holds one constraint per task, so a task with several writes the first of: a pin, start-no-earlier-than, finish-no-earlier-than, start-no-later-than, finish-no-later-than, as late as possible. A P6 soft Start On or Finish On is such a pair, and the file writes its no-earlier-than half (4 or 6).
Reading the written file gives the same schedule, tasks, links, calendars and dates (`crates/import/tests/mspdi_export.rs`: read, write, read over `links.xml`, `summary.xml`, `constraints.xml` and the other fixtures), and the same project writes the same bytes.
`left_out` names each thing the project holds that the file does not carry: a source with no `StartDate` (written from the origin), deleted tasks and removed links, host keys on tasks, links and calendars, P6 activity ids and activity codes, a task in progress or finished with no actual start (the file cannot state one), a summary's own start constraint, a start-no-earlier-than earlier than the project start (the reader raises it to the start), the constraints of a task that has more than one (one line per task naming the ones not written: "task 2: its start no later than constraint is not written (the file carries one constraint per task, the start no earlier than), so it reads back without it"), a parent task written as a task (it has its own duration, calendar or dates), a link lag counted in another calendar than the successor's, repeated task UIDs (the file renumbers them) and characters XML cannot hold in a name. It also repeats every line of `Imported.unsupported`, because the reader had already left those out (a constraint with no date, resources and the rest; the readable constraints are written, or listed by the writer above, not here), so the file cannot carry them. Which links, calendars and tasks the file holds is tested; that MS Project opens the file is not: no copy of MS Project is available to the tests, so a person who has one has to check it, including the order of the elements. For a session, `export_mspdi` and `export_xer` in `crates/app/src/export.rs` add one more line, `host keys on N task(s) are not written`, when a live task carries the opaque `key` a host gave it (neither file has a place for it).

## Writing a P6 XER file

`import::export_xer(&Imported, &XerOptions)` writes the project as an XER file and returns the bytes in an `Exported` (`crates/import/src/export/xer.rs`, gs#703). The Export window's "P6 XER" button calls it (`apps/chrome/src/export.ts`): it downloads `<name>.xer`, names the version `19.12` in its result line and lists `left_out` under it.
Today it writes the `ERMHDR` line (version `19.12`, the export time from `XerOptions::exported_at` in minutes since 1970-01-01, never the clock, so the same inputs give the same bytes), one `PROJECT` row whose `proj_short_name` is `XerOptions::name` and whose `clndr_id` is the first task's calendar, and the `CALENDAR` table with every calendar's week and exception days. `XerOptions::layout` has two values: `XerLayout::One` writes one project, named from the options, holding every task, and `XerLayout::FromXer` is for a project that came from an XER, where each level-1 summary is a project.
It also writes the `PROJWBS` rows and each task's `TASK` row: its identity (its id, project, WBS node, calendar, activity ID and name; gs#803, gs#809), `status_code` (`TK_NotStart`, `TK_Active` for a started task and `TK_Complete` for one with an actual finish), `target_drtn_hr_cnt` and `remain_drtn_hr_cnt` (hours, so the reader's round to the minute gives the minutes back: the duration for both, except that a started task's remaining is its remaining work and a finished task's is 0), `act_start_date` and `act_end_date` (only when the task has them), `phys_complete_pct`, and up to two constraints, the primary (`cstr_type`, `cstr_date`) and the secondary (`cstr_type2`, `cstr_date2`), from the task's start-no-earlier-than (only when it is above its project's start) and its limits, in this order: the pin (`CS_MANDSTART` or `CS_MANDFIN`), start-no-later-than (`CS_MSOB`), finish-no-later-than (`CS_MEOB`), as late as possible (`CS_ALAP`), start-no-earlier-than (`CS_MSOA`) and finish-no-earlier-than (`CS_MEOA`), so the spellings the second slot refuses come first and a task with at most one of them keeps both rules (`crates/import/src/export/xer/constraint.rs`). A project's `plan_start_date` is `Imported::project_start` when given, else the earliest constraint among its tasks, else the origin; a session's one-project export (`export_xer` in `crates/app/src/export.rs`) gives the earlier of the earliest start of its tasks and the data date, so every task reads back on the date it has and the data date is kept; its `last_recalc_date` is the data date. A started task reads back started, with its actual start, its actual finish and its remaining work (`crates/import/tests/xer_export_values.rs`); whether P6 accepts the file is not tested. A re-opened export lists each WBS node's rows by the Start column, the engine's computed start with the actuals and data date applied, so a started task comes first; the file carries no early dates, and the dates, links and durations are unchanged (`crates/app/tests/export_xer.rs`). It also writes each link between two live activities as a `TASKPRED` row (`pred_type` `PR_FS`, `PR_SS`, `PR_FF` or `PR_SF`, and `lag_hr_cnt` in hours) and one `SCHEDOPTIONS` row per project holding the lag calendar; a link with a deleted end or a summary end has no row, and a summary end is listed in `left_out` (`crates/import/tests/xer_export_links.rs`, `xer_export.rs`). A baseline or a deadline on a task it writes has no XER row, so each is counted in `left_out` ("the baseline on 2 tasks was not written", "the deadline on 1 task was not written"; `xer_export.rs`). A rule that has no slot is not written and is counted the same way ("the constraint on 1 task was not written"; `an_export_lists_the_limits_it_does_not_write` in `xer_constraints.rs`): a third rule, and a second one other than `CS_MSOA` or `CS_MEOA` (two of start-no-later-than, finish-no-later-than and as late as possible, or a pin with one of them), the only second-slot spellings a P6 probe file shows accepted. A finish pin and a second limit read back as the same limit (`xer_export_values.rs`). Reading the written file gives back the project name, the export time, the calendars, and each task's duration, constraint and percent complete (`crates/import/tests/xer_export_project.rs`, `xer_export_calendars.rs`, `xer_export_values.rs`).

## Opening a schedule document

Open, Ctrl+O and a dropped file also read a `.gantt` file, the document that Ctrl+S saves (decision 0010): a gzip file whose JSON says `"format":"gantt"`, which the page gunzips (`packages/gantt/src/document.ts`) and `LoadedSchedule.parse_document` reads. The file's content decides, never its name. The schedule comes back as it was saved: its edits, names and outline, the baseline, the summaries that were collapsed, and the original P6 or MS Project file it came from, with an empty undo history. A document from a newer version of the app, or one that is damaged, is refused with the reader's message (`this document is version 2; this app reads version 1`) and the open schedule stays as it was.
