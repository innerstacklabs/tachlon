# Changelog

What changed in each npm release, newest first. Each entry says what you must change in your own code, then what is new. The decision records in `docs/decisions/` hold the reasons.

## Unreleased

### Breaking changes

- **Under `dateForm: "day"`, `update`, `hostEdit` and `setData` refuse a date with a time of day as `badValue`.** They took either form whatever `dateForm` was; send `YYYY-MM-DD`, the form the chart wrote to you, which is read on the task's calendar (a start is its first working minute, a finish the end of its last).

### New

- `App.table_rows` rows carry one more member, at position 9: the task's free float as working-day text (`1d`), `null` for a summary, a group header and a finished task, and for every row until `App.set_free_float_shown(true)` (the column is hidden at the start, and a hidden column works nothing out). A host that reads the tuples by position sees a tenth member; positions 0 to 8 are unchanged.
- The package's `describe methods` prints the chart's own methods, each with its whole doc comment, and `describe refusals` prints the `reason` of each refusal with the fix where there is one (`describe methods` and `describe commands` end with a line that names it). The `hostEdit` comment now says that `hasActuals` is any `progress` or any change to a task with actual dates, and that `update` is the call for it and for `notAllowed`.
- The time-scale header no longer draws the name of a period the right edge cuts too short to hold it, and the progress view's Task column leaves room for the Predecessors or Resources column, so the last column is whole at the end of a sideways scroll.
- Under `keys: "server"`, a restored row (the undo of a delete, the redo of a create) may be answered with another key, and the chart takes it; a different key was put back with `reason: "result"` before. A member of the change set that names a restored row is now `{ ref }`, as for a new row, so a `save` function puts the `key` of each create that has one in its ref map before it reads the creates that name it.

## 0.4.0

Read "Breaking changes" first. A page that reads neither the `edit` event nor the `beforeEdit` payload, never calls `chart.save()` and does not set `structure`, `kinds` or `perTask` in `capabilities`, sets no `notAllowed` text, and puts no date limit on a task whose calendar ends before midnight, needs none of them except the type changes in the last entry, for TypeScript code. The new `save` option, which stores what the person edits, is under "New".

### Breaking changes

- **A change in the `edit` event and in the `beforeEdit` payload is one change per record, with `set` and `was`.** It was one change per field, with `field`, `old` and `new` (and `fields` on a create). A change is now `{ record, op, key, set, was }` (and `task` or `link`, the session slot): an update's `set` holds the members that changed with their new values and `was` the same members as they were, a create's `set` is the whole record, and a delete's `was` is the whole record it removed. A link delete that follows from a task delete in the same commit has `cascade: true`. This reaches `Gantt.on("edit")`, React `onEdit`, Vue `@edit`, Angular `(chartEdit)` and `beforeEdit`. To update, read `set` and `was` where you read `field`, `old` and `new`, and delete the code that gathered fields back into a record. Decision 0022, section 2.

- **A duration or lag in the `edit` event, a `save` change set and the `beforeEdit` payload is in the `durationUnit` the chart mounted with.** It was days of the task's calendar (of the link's lag calendar for a lag) whatever the unit, so a chart mounted with `durationUnit: "hours"` took hours in and gave days out. A chart with the default `"days"` is unchanged. A new `dateForm: "day"` option gives every date in those three as `YYYY-MM-DD` (a finish as the last day worked); `"minute"`, the default, keeps `YYYY-MM-DDTHH:mm`. It is a prop of the React and Vue components and an input of the Angular one.

- **A task's date limit in the `edit` event, a `save` change set and the `beforeEdit` payload is one member, `constraint: { type, date }` or `null`: `constraintForm` now defaults to `"typed"`.** It was the six members `snet`, `snlt`, `fnet`, `fnlt`, `mso` and `mfo`; `type` is one of the eight names in the next entry and `date` is in the form `dateForm` gives. A task the engine holds with several bounds reads as the first of `mso`, `mfo`, `so`, `fo`, `snlt`, `fnlt`, `snet` and `fnet`. To keep the six members, mount with `constraintForm: "separate"` (a prop of the React and Vue components and an input of the Angular one): a host that reads the separate limit fields writes that one line and changes nothing else. Decision 0022, section 9.

- **`constraint.type` has two more values, `so` (start on) and `fo` (finish on).** `so` is `snet` and `snlt` on one date and `fo` is `fnet` and `fnlt` on one date: the bar is not moved, and float goes negative when logic pushes past the date, where `mso` and `mfo` pin the bar to the date. The reading order is `mso`, `mfo`, `so`, `fo`, `snlt`, `fnlt`, `snet`, `fnet`. A typed host gets `so` and `fo` only when `capabilities.kinds` is left out or lists them. To keep the old reading, list the kinds without them: a task whose floor and ceiling sit on one date then reads as `snlt` (or `fnlt`), as it did before the pair had a name; with `constraintForm: "separate"` a host never sees them. A `switch` over `ConstraintType` with no `default` needs both cases. A host whose own type names are Primavera P6's "Start On" and "Finish On" maps them to `so` and `fo` in its own code, and "Mandatory Start" and "Mandatory Finish" to `mso` and `mfo`; nothing changes what `mso` and `mfo` mean. Decision 0022, section 9.

- **A date alone on a date limit is read on the task's calendar: on a finish limit (`fnet`, `fnlt`, `mfo`, `fo`) it is the end of that day's last working minute, and on a start limit (`snet`, `snlt`, `mso`, `so`) its first working minute.** A finish limit was the end of the day (00:00 of the next day) and a start limit was 00:00, so on a calendar that does not run to midnight (08:00 to 16:00, say) a finish limit by date fell a working day late and the late start of `snlt` fell early. The dates of a schedule on a 24-hour calendar are unchanged, and so are those of `snet` and `mso`, whose bar starts at the next working minute anyway. This holds in the separate members and the typed `constraint`, in `mount`, `update` and `setData`, and in the limit editor. A host that wants the old reading writes the time: `YYYY-MM-DDT00:00` for a start limit and, for a finish limit, the next day's `T00:00`. A host that stores dates with no time of day (`dateForm: "day"`, or `dates: "day"` in `capabilities`) cannot keep it. Decision 0017, rule 6.

- **`capabilities.kinds`, left out, now means nine kinds, not seven.** It was `snet`, `snlt`, `fnet`, `fnlt`, `mso`, `mfo` and `alap`; `so` and `fo` are added, and a task whose floor and ceiling sit on one date counts as one kind, not two, against `perTask`. A host with `perTask` and no `kinds` that must keep the old count lists `kinds` without `so` and `fo`.

- **`Gantt.save()` is now `Gantt.download()`.** It downloads the open schedule as a `.gantt` file, as before; `save` is now the name of the option that stores each edit (see "New"). To update, rename each call.

- **`editable.structure` in the host profile (`mount`'s `capabilities`, `setCapabilities`) is now three members, `rows` (insert and delete), `outline` (indent, outdent and move) and `paste`.** A host that set `structure: false` must set the ones it needs; `structure` is refused as an unknown key.

- **The `texts` key `notAllowed`, shipped in 0.3.1, is removed: each refusal for what `capabilities` turns off has a key of its own.** The keys are `notAllowedBarMove`, `notAllowedResize`, `notAllowedLink`, `notAllowedRows`, `notAllowedOutline`, `notAllowedPaste`, `notAllowedNames`, `notAllowedDates`, `notAllowedLinks`, `notAllowedProgress` and `notAllowedBaseline`, each with a default sentence that does not say "the host" (`notAllowedBarMove` is "Moving a bar is not allowed."). `mount` drops a `texts` key the chart does not know, with no error, so a host that set `notAllowed` now gets the default sentence for every refusal until it sets the new keys it wants worded. The `"notAllowed"` reason in an answer is unchanged, and so is the `member` that says which group was refused. `notStored`'s default is now "Saving allows {what}." (it began "The host stores {what}.").

- **A `switch` over a type with no `default` needs the new cases.** `CommitSource` gains `"rollback"` and `"host"`, `ErrorSource` gains `"save"` and `EditRefusal` gains `"rowsChanged"`, `"finishBeforeStart"`, `"hasActuals"` and `"badToken"`. The `error` event's payload is now also a `SaveError`. `Gantt` gains `hostEdit`, `pushHostEntry`, `clearHistory` and `setData`, and `Commands` gains `setOverlay` and `ViewState` gains `customFields` and `unsavedCommits`; a test double or a copy of the type needs them. A change's `key` is `string | null`, where it could be left out.

### New

- `mount({ save })` stores each edit a person makes (a prop or input of the same name in React, Vue and Angular, which read the latest value when a change set is sent and never mount the chart again for a new one). `save` is a function that gets one change set per undo step, `{ id, seq, source, changes }`, one call at a time in the order the person made them, and resolves when your server has it. A change is `{ record, op, key, set, was, once }` in your names, `once` is its idempotency key, and `id` is a UUID that is the same on every call of that change set. To refuse a change, throw `new SaveRefused({ message, key, field })` (an export of the package's main entry): the chart puts that edit and every edit after it back, shows the message and fires `error` once with `source: "save"` and a `SaveError`, which holds `reason` (`"refused"` or `"result"`), `calls`, `key`, `field`, `seq`, `undone` (how many commits it put back) and `reload` (read your data again: the chart could not put itself back). With `save`, every task and link needs a `key` no other of its kind holds, and `mount` refuses a row that breaks that. Without `save` the chart stores nothing and you read the `edit` event, as before.
- `save` also takes an object with one handler for each kind of change, for a host that already has an API client: `createTask(row, c)`, `updateTask(key, set, c)`, `deleteTask(key, c)`, `createLink`, `updateLink`, `deleteLink` and `updateSchedule(set, c)`, with `row`, `set` and `was` in your names. The chart calls them in the order the person made the changes, each after the one before has resolved. The last argument, `c`, holds `once`, `signal` (aborted 10 seconds after the call; the chart still waits for the handler to settle), `was` (the old values of an update or a delete) and `changeSet`. A handler that rejects, or resolves with a `Response` whose status is not 2xx, ends the call, and a `SaveRefused` it throws puts the edit back as above. A handler that resolves with an object that has `error`, `errors` or `userErrors` is read as saved, and the console warns once.
- `mount({ keys, newKey })` say who makes the key of a row the person creates when `save` is set. `keys: "chart"` (the default) makes it before the change set is written, with `newKey()` or `crypto.randomUUID()`, and the create carries it, so you store it as the row's id. With `keys: "server"` the create carries `key: null` and a `ref`, and every change in the change set that names the row holds `{ ref }`: answer with the key the server made. A handler resolves with the key, an object that has it under your name for `key`, or a 2xx `Response` whose JSON body is the row; a `save` function resolves with `{ keys: [{ ref, key }] }`, one for each create that has a `ref`. A result the chart cannot use (a missing, repeated or taken key) puts the edit back, and `error` fires with `reason: "result"`. The undo of a delete and the redo of a create bring a row back under the key it had: answer with that key.
- `mount({ fields })` maps your own field names to the chart's once (a prop or input of the same name, read when the chart mounts): `{ tasks: { key: "id", name: "title", start: "plannedStart" }, links: { key: "id", from: "source", to: "target" } }`. A field with no entry keeps its name, and a name that is not a chart field does not compile. `tasks`, `links`, `update`, `hostEdit` and `setData` then take your own rows, and the chart writes your names in the `set` and `was` of every change it tells you of (an `edit` event, a `save` change set, a `beforeEdit` call), so you write no rename function. It renames members and converts no value; `durationUnit` and `dateForm` do that.
- `chart.hostEdit(records)` gives the chart the changes your page made to tasks outside it (the records `update` takes) as one undo step on the person's own list: one Undo takes back all of them, the next Undo takes back the person's edit before them. It answers as `update` does, and refuses a record that sets `progress` or changes a task with actual dates as `"hasActuals"`, and one that changes a group of fields the host profile turned off as `"notAllowed"`. An `edit` event fires with the commit source `"host"`, which your `save` never gets because you made the change; `beforeEdit` is not asked.
- The React, Vue and Angular components take `records`, a new array of `chart.update` records, and apply it to the chart that is mounted, in place (`onUpdate` in React, `@update` in Vue and `(update)` in Angular get the answer, a refusal too). The scroll position, the selection and the undo list stay. The first array, and one that arrives with a new `tasks`, is not applied: put those values in `tasks`.
- The records `chart.update` takes also carry `snlt`, `fnet` and `fnlt` (a date, or `null` for none), and `start: null` clears the start. A record may carry `hostStart` and `hostFinish`, the early start and finish your own code computed: they set nothing, and the answer holds `differs`, one `{ record, key, member, host, chart }` for each date that is not the chart's.
- `chart.commands.setBaseline(records)` takes `[{ key, start, finish }]` and makes those dates, by task key, the baseline, in place of every task's dates as they are now; with no argument it works as before. `chart.commands.setOverlay(records)` draws such records as a second thin bar under each keyed task's comparison bar, for dates of your own such as a leveled schedule's; `null` removes it. The overlay is not saved and not an edit.
- The task dialog has a Predecessors field, for a schedule whose tasks have `id`s. A person types a list such as `3, 5SS+1d` and the links into that task change as one undo step, as in the task list's Predecessors column (the column has been in the package since 0.3.1; that release's list left it out).
- A task takes `constraint: { type, date }` or `null` in `tasks`, `update` and `setData`, and `fields` maps `constraint` to one member of yours, or `{ type: "limitType", date: "limitDate" }` to two that are both `null` for none, so a host that stores one typed limit writes no code that spreads it over six members. The `type` is one of `snet`, `snlt`, `fnet`, `fnlt`, `mso`, `mfo`, `so` or `fo`. A record that gives `constraint` and one of `snet`, `snlt`, `fnet`, `fnlt`, `mso` or `mfo` is refused; a row in `tasks` that has a `constraint` takes no floor from its `start`, which may then be left out; in `update`, `constraint` replaces every other bound and `null` clears them.
- A task in plain data with no duration takes `milestone: "start"` or `"finish"`, which puts it at the start of a working period or at the end of one; the saved copy and `snapshot()` write it back, and an undo that brings a deleted task back keeps it. Any other value is refused by `validate`.
- After `chart.update(records)`, each cell in view whose shown value changed (the values the host sent and the ones the new plan moved) is highlighted for 1.5 seconds, with no fade under `prefers-reduced-motion: reduce`, and a row marked with `setPending` that the call wrote stops being dimmed.
- `chart.setData({ tasks, links })` gives the chart the rows your page holds now and sets in place only the `name`, `start`, `snet`, `constraint`, `duration` and `progress` of each task (by `key`) that differ from the rows it was last given, keeping the selection, the scroll position and the undo list. It compares each task's `key`, `id`, `parent` and place in the list and every link, and answers `"rowsChanged"` and changes nothing when any of them differs; every other member (`color`, `label`, `end`, `calendar`, `milestone`, the limits `snlt`, `fnet`, `fnlt`, `mso`, `mfo` and `alap`, the actuals, your own members) is ignored.
- `chart.pushHostEntry(token)` puts an entry for an action your page took outside the chart on the undo list: an Undo that reaches it fires `edit` with a commit whose `host` is the token (`source` `"undo"`, `"redo"` for a Redo) and changes no value. `chart.clearHistory()` empties the undo and redo lists, the unsaved commits and any what-if.
- A member of a row that the chart has no field for (`status`, `owner`) is kept with the row by its `key` and comes back unchanged in a create's `set` and a delete's `was`, so the create that undoes a delete restores your own columns; `chart.state().customFields` lists the names seen. It is no longer counted in `leftOut`, so a misspelled member is kept, not reported.
- The React, Vue and Angular components take `capabilities` as a prop or input, as `mount` takes it as an option. A new value is set on the chart that is mounted with `setCapabilities` and does not mount it again; a chart that mounts again starts on the latest value.
- The host profile (`mount`'s `capabilities`, `setCapabilities`) says what the host stores: `kinds` (nine kinds when left out: the eight date limits and `alap`) and `perTask` for date limits, `durationStep` and `lagStep` in `"minutes"`, `"hours"` or `"days"`, and `dates` as `"minute"` or `"day"`. A typed, dialog, keyboard or paste change outside them is refused with `"notAllowed"` and a sentence that says what the host stores; a bar drag that would make one is refused.
- The chart reads the outcome of a host's answer from its status, so a host whose client throws an error with a status number, or whose `save` resolves with a `Response`, needs no code of its own. A thrown `SaveRefused` is a refusal. For any other throw, a handlers object's `classify(error)` is asked next (a number from 100 to 599, or `"refused"`, `"stopped"` or `"failed"`; `undefined` leaves it to the table), then the status decides: 2xx is saved when resolved and a failure when thrown, 401 stops the queue, 408, 429 and 5xx are a failure that stops it, and any other status (a 403 included) is a refusal that puts the edit back with the error's message or the response's JSON `message`. No status is a failure. A refusal that names a `key` selects that row, and one that names a `field` (your name for it) shows its message in a note under that cell until the person's next edit or until you give the chart new `tasks`. A handler's non-2xx `Response` is returned, not thrown, and is judged as a resolved answer.
- Rows whose edit is waiting to be saved are dimmed until the call settles. The dimming is the chart's own set, merged with the marks `chart.setPending` made, so a host's marks stay.
- Each refusal for what `capabilities` turns off has its own `texts` key and default sentence (the eleven keys in "Breaking changes"), and six more sentences the chart wrote itself are replaceable through `texts`: the chart's name for a screen reader (`gantt-chart`), the task dialog's title (`edit-task`), the hint of a Start cell in the table (`start-no-earlier-hint`) and in its editor (`start-no-earlier-clear`), and a summary's disclosure labels (`collapse`, `expand`). `App.default_texts` returns 155 keys. A refusal's key reaches the chart only when `mount` also gets `locale`, as for the other `texts`.
- `chart.state().unsavedCommits` is the number of commits your `save` has not saved yet, and the `change` event fires when it moves, so a host never counts commits itself. The save queue owns the number: it is 0 again after a commit is saved, put back (with every commit behind it), dropped because it was made below a put-back, or dropped when the chart stops its queue (`destroy()` and the switch to WebGL2 send none of those commits), and 0 with no `save`. A `save` whose answer is neither a success nor a refusal (a 401, a failure by the status table above, or a throw with no status) stops the queue: no later call is made, the held commits stay counted until `destroy()`, and `error` fires once with `reason: "stopped"`, the thrown `message` and `held`; a host tells the person and mounts again (retry and discard come later). `unsaved` keeps its meaning, the file mark.

### Fixed

- The Float cell of a finished task (one with an actual finish) is empty; it read `0d`. The engine's float for it is unchanged.
- A typed percent complete of `0` (in the percent cell, the task dialog and the by-key update's `progress`) leaves a task that has not started with no actual start and no remaining work; it used to give it its early start. A typed percent that would put an actual start or finish after the data date is refused with `actualAfterDataDate`, as the actual date cells and the by-key update already refuse it.
- `setData` sets a changed `snlt`, `fnet` or `fnlt` on its task by key, as `update` does; before, it compared only `name`, `start`, `snet`, `duration` and `progress` and dropped a changed limit.
- `update` and `setData` take an `mso` or `mfo` that equals the pin the task holds (a date alone is read as for `snlt` and `fnet`: the first working minute for `mso`, the last for `mfo`), or `null` when it holds none of that kind, and change nothing for it. Before, every `mso` and `mfo` was `notUpdatable`, so after a host saved and reread its rows every later `setData` was refused (issue #144). A different `mso` or `mfo` is still `notUpdatable`, and a date that does not parse is `badValue`.
- `validate` and `fromTasks` take `parent: null` as no parent, as leaving `parent` out is, and a task that other tasks name as `parent` needs no `start`. A leaf still needs a `start` unless it has a `constraint`. `plain.schema.json` takes `parent: null` and no longer requires `start` or `constraint` on every task: `validate` holds that rule, because a schema cannot see the other rows (issue #145).

## 0.3.1

A page that runs on 0.3.0 behaves the same apart from the fix below. TypeScript code that handles every `EditRefusal` reason or every `error` source with no default case (an exhaustive `switch`, or a `Record` keyed by the type) needs the new cases the entries under "New" name.

### Fixed

- A link that one undo step both adds and deletes, because the step also removes the task at its end, is listed in the `edit` event's commits as neither created nor deleted.

### New

- The package's command line gains `describe`, which answers what the installed package offers, from the package in `node_modules`, so the answer matches the version you installed. `describe options`, `events`, `commands`, `tokens` and `errors` list each name with its type, what it does and its default when it has one; `--json` prints the same as data for a coding assistant. `describe fit` prints the steps that make the chart fit your product: its look, then its behavior.
- `mount({ beforeEdit })` (a prop or input of the same name in React, Vue and Angular, which ask the latest function without mounting the chart again) gives the chart a function it asks before each change a person makes. The function sees the action and the changes it would make with their old and new values (the README's "Control editing" says which actions carry values), and answers a string to refuse the change with that reason, which the chart shows. A refusal changes nothing and carries the new `EditRefusal` reason `"refused"`; a throw or a promise refuses the change, fires `error` with the source `beforeEdit` and carries the new reason `"beforeEditFailed"`. A `switch` over the reasons with no `default` needs both new cases.
- `mount({ capabilities })` and `chart.setCapabilities(profile)` (not yet a prop or input in React, Vue and Angular) tell the chart which gestures (`barMove`, `resize`, `link`) and groups of fields (`structure`, `names`, `dates`, `links`, `progress`, `baseline`) the host's database can take. A change a host turned off is refused on every path, undo included, with `"notAllowed"` and a sentence that says the host does not allow it.
- The by-key update (`App.update_tasks` and `Session::update_tasks`, which `chart.update` below calls) also takes `name` and `progress` in a record. A name is checked as a typed rename is, and a progress (a whole percent from 0 to 100) as a typed percent is, and is refused if it sets an actual after the data date. A progress is taken against the dates the record's `duration`, `start` and `snet` leave, so the chart works the plan out twice when a call mixes them, and once otherwise.
- `chart.update(records)` gives the chart new names, starts, durations, start-no-earlier-than dates and progress for many tasks by `key`, in place, so a host that recalculates elsewhere hands back the result with no new `mount`. The selection, the scroll position and the undo list stay as they were, and the call is not an edit (no `edit` event, no undo step). A duration counts `mount`'s `durationUnit`; the answer is `{ ok: true, updated }` or a refusal that changed nothing (`Refusal` now also carries `record` and `member`, and `EditRefusal` the reasons of `update`).
- The app can put the chart back to before a change the host failed to save (`App.rollback_to` and `Session::rollback_to`, with `App.acknowledge` for a saved change; no JavaScript call yet). It takes away the changes made after it too, as one commit with the source `rollback`, and refuses with `rollbackGone` when it can no longer go back that far, so the host loads its own copy.

## 0.3.0

Read "Breaking changes" first if you use 0.2.0. A page that mounts the chart with `schedule` and listens only to `select`, `edit` and `open` needs none of them.

### Breaking changes

**Events**

- **The `move` event's `start` is a date text, not minutes.** It was minutes from the origin Monday; it is now `YYYY-MM-DDTHH:mm`, and the event also carries `key`. This reaches `Gantt.on("move")`, React `onMove`, Vue `@move` and Angular `(chartMove)`. To update, delete the code that turned minutes into a date and read the text. Decision 0017.

**Plain data** (`fromTasks`, `mount({ tasks, links })`, `openHeadless`)

- **Names that 0.2.0 ignored are now read.** A task member `key`, `calendar`, `snet`, `snlt`, `fnet`, `fnlt`, `mso`, `mfo`, `alap`, `actualStart`, `actualFinish`, `remaining` or `resume`, a link member `key`, and the top-level `dataDate`, `mustFinishBy`, `options`, `calendars`, `durationUnit` and `lagCalendar` now mean something and are checked. If your objects carry a field of your own under one of these names, rename it before you pass the data in. Decisions 0016 to 0018.
- **`key` must be text.** A number is refused: send `String(id)`. `snet` is read in place of `start` when you give it. `mso` and `mfo` do not go together. `actualFinish` and `resume` need an `actualStart`, as does `remaining` unless `options.unstartedRemaining` is `"on"`, and `remaining` is not given with `progress`. An unknown member or value inside `options` is refused. `validate` lists each one. In TypeScript, `PlainTask` and `PlainLink` now type these members, so a field of yours with another type fails to compile.

**Document format** (`toDocument()`, `.gantt` files)

- **A document from 0.2.0 opens unchanged. A document that 0.3.0 saves with a host key (task, link or calendar), with `options` or with a `must_finish_by` date is refused by 0.2.0.** The version stays 1, and a schedule with no keys, default options and no date saves the same text as before. To update, move every reader to 0.3.0 before you save keys. Decisions 0010, 0016 and 0018.
- **`ScheduleDocument` types are wider.** `data_date`, and a task's `actual_start`, `actual_finish` and `remaining`, are `number | null` where they were `null`. Add a check where your code assumed `null`. The document may also hold a task `key`, a limit `resume` and a top-level `options` and `must_finish_by`.
- **A value outside the engine's range no longer opens.** A duration or remaining time over about 100 years, a lag beyond the same, or a date more than 1,000 years from the origin is refused by the document reader, and by an edit. Nothing a person types in good faith reaches it. Decision 0020.

**Types you build or switch over**

- **`EditRefusal` has six more reasons:** `readOnly`, `emptyKey`, `hasKey`, `keyTaken`, `unknownTask` and `unknownLink`. A `switch` over the reasons with no `default` needs the new cases.
- **`ProposeResult` has four more reasons:** `finishBeforeStart`, `actualAfterDataDate`, `duration` and `badPercent`. `ProposedChange` and `ProposedKey` have a `progress` kind. A `switch` over the reasons or the kinds with no `default` needs the new cases.
- **Interfaces gained members.** `ViewState.groupBy`, `Commands.setGroupBy`, `Commands.assignKey`, `Gantt.snapshot`, `Gantt.setPending`, `Gantt.setReadOnly`, `Gantt.readOnly`, `HeadlessSchedule.leftOut` and `HeadlessSchedule.results` are required, and so are the event payload members: `key` on `select` and `move`, and `commits`, `seq` and `snapshot` on `edit`. Code that only calls or listens is unaffected; a test double or a copy of the type needs them.

**Behavior with no type change**

- **Negative float is no longer cut off at the project start.** A late start can now fall before the project start, so a task that cannot meet a late limit reports its true float: a two-day task that must finish by the first Monday at 17:00 reads -1 working day, where it read 0, in the chart's Float column, in `explain` and in `results`. The count of late tasks in the Checks grows with it. Change any threshold that read float.
- **A length beyond the range is refused where it was answered.** `whatIfLonger` for a task that would run longer than about 100 years refuses with reason `other`. An imported P6 file with a lag or duration over about 100 years used to fail to open, and an MS Project file with one was held to 100 years of 365 days. Both open with a counted note now: a lag past the range reads 0 and a duration reads the largest length.
- **A command-line flag that takes no value refuses one.** `--skill=false` and `--dry-run=false` used to read as on; the flags `--dry-run`, `--json`, `--no-install`, `--plain`, `--skill`, `--help` and `--version` now exit 2 with `<flag> takes no value`. To turn a flag off, leave it out.
- **`mount` with no `schedule`, `document` or `tasks` opens an empty chart.** It rejected before. Code that used the rejection to detect "no data" checks the task count instead.
- **A typed actual start or finish after the data date is refused** in the cell and the task dialog. A file whose actual dates are after the data date opens with one counted note.
- **Exported files change.** For a schedule that did not come from an XER file, the XER export writes the project start as the earlier of the earliest task start and the data date, so the file reads back with its dates. It also keeps both date rules of a task that has two when at most one of them is a pin, a start-no-later-than, a finish-no-later-than or as-late-as-possible, where it dropped one; `leftOut` still names a task that loses a rule. Both exports add a `leftOut` line when a task has a host key or the schedule has a must-finish-by date, which the formats cannot carry.

### New

**Mounting and options**

- `mount({ document })` starts the chart on a saved document in one call, instead of an empty start and `load`. React, Vue and Angular take a `document` prop or input. A `schedule` wins over a `document`, and a `document` over `tasks`.
- `mount({ dataDate })` and `mount({ options })` (with the same props and inputs) set the day the data is as of and the schedule options. `options.startedLateStart` is `"p6"` (default) or `"project"`: the late start a started task shows is the late start of its remaining work, or its actual start. `options.unstartedRemaining` is `"off"` (default) or `"on"`: a task that has not started and has a remaining duration is scheduled with that length. The defaults give the 0.2.0 answers.
- `mount({ mustFinishBy })` (a prop or input of the same name in React, Vue and Angular) gives plain `tasks` the date the project must finish by, as `YYYY-MM-DD[THH:mm]`; a date alone is the end of that day. It is read with `tasks`, as `dataDate` is.
- `Gantt.load({ document, unsaved: true })` shows the loaded schedule as unsaved, for a copy of work no save holds, so opening another file asks first. A chart that switches to WebGL2 and loses edits keeps its unsaved mark.
- `mount({ assistant: { send, into } })` writes a chat panel into your element. Each message calls your `send` with the conversation, so the page sends nothing anywhere else, and a change the model proposes waits for the person to accept or reject it.
- `mount({ readOnly })`, `Gantt.setReadOnly(on)` and `Gantt.readOnly()` switch the chart read-only for the person using it, at any time and without a restart. The cell editor and the task dialog do not open, every other edit is refused with `"readOnly"`, and a click still selects a row. The React and Vue `readOnly` prop and the Angular `readOnly` input do the same and never mount the chart again.
- `Gantt.setPending(keys)` dims the rows that wait for your own recalculation and tells a screen reader they are busy.
- `Commands.setGroupBy(codeType)` groups the rows under one header per activity code value; `null` ungroups. `ViewState.groupBy` reports it. A group opens and closes with a click or `Alt+Left` and `Alt+Right`.

**Editing and events**

- A task keeps the `key` your host gave it through edits, saves and loads. Links and calendars carry one too. `select` and `move` events carry `key` (`null` when there is none).
- `Commands.assignKey({ task } | { link }, key)` gives a key to a task or link made in the chart after your host saved it. It is not an edit: no undo step, no revision.
- `Commands.select(task)` and `Commands.scrollTo({ task })` take a task's key as text as well as the chart's own task number, so a page that lists tasks by its own id selects one and brings it into view without row numbers. A key no live task holds, a deleted task's included, answers `false` and changes nothing. `ScrollTarget` is `{ task: number | string } | { date: string }`.
- `Commands.propose({ kind: "progress", task, actualStart | actualFinish | remaining | progress })` holds a task's reported progress as a pending change, so a host field app can post progress for a scheduler to approve. The chart draws it as a dashed bar, changes nothing until a person accepts it, and Accept applies it as one undo step. `acceptProposed` and `rejectProposed` take `kind: "progress"`, and the `propose` tool of `mount({ assistant })` takes it too.
- The `edit` event carries `commits`, one per undo step, each with its `source` (`typed`, `drag`, `dialog`, `paste`, `proposal`, `undo`, `redo`) and its changes with old and new values; `seq` counts them, and `snapshot: true` says commits were lost, so save `snapshot()` instead. Moving a task in the outline (indent, outdent or a move) records `parent` and `after` for the task and for each sibling that changes place with it. Types `Change`, `Commit` and `CommitSource`. Decision 0019.
- The Rust host API's before-edit function (`Session::set_before_edit`, no JavaScript call yet) is shown the old and new values for a drag, the task dialog, a paste, a link drag, and an undo or redo of a task-field step, as it is for a plain edit and a group; it can refuse by value, each dialog field as planned against the chart. A paste carries the name of each task it creates and a link drag the finish-to-start link it makes with no lag, and no other field of either. A delete, restore, outline move, link edit or data-date edit carries the records its commit writes; an insert carries only the place and name the edit names, and a baseline edit the `baseline` field, although its commit writes no change. A plan of two or more of these (a group, a multi-step undo or redo) carries its task-field values and no structural ones. An undo or redo of a data-date edit and `discardWhatIf` carry no values, only their kind and every task they touch, both ends of a link included. An outline move names the moved task only, not the siblings it adopts or releases.
- A program that keeps its own copy of the schedule can send new durations and start-no-earlier-than dates for many tasks at once, each task named by its key (`App.update_tasks` and `Session::update_tasks`, no JavaScript call yet; a duration is a whole number of working minutes, and `start` is read as `snet`). A record takes `key`, `duration`, `start` and `snet` and no other member, a summary task is refused, and one refused record refuses the whole call and changes nothing. The chart works the plan out again once and keeps what the person had selected; their undo list is left as it was, and no `edit` event fires.
- A started task takes a `resume` date, the day its remaining work picks up again. The MS Project reader keeps it.
- A typed list of predecessors (`3, 5SS+1d`: Activity IDs with an optional link type and lag) makes, changes and removes the links into a task as one undo step, and its `edit` event commit lists each link change. The wasm `App` takes it (`set_predecessors_text`, read back by `predecessors_text`); the chart's cells and `Commands` do not call it yet.

**Plain data and the headless solve**

- `Gantt.snapshot()` and `toPlain` return the whole schedule as plain `tasks` and `links`, with `dataDate`, `options` and `leftOut` (one line for each thing plain data cannot carry). `fromTasks` reads the result back.
- A must-finish-by date goes in plain data as `mustFinishBy` (`fromTasks`, `openHeadless`, `validate`, `schema.json`; `snapshot()` and `toPlain` return it) and in a document as `must_finish_by`, in minutes from `origin`, written only when set; a value out of range, or given twice, is refused. Float is measured against the earlier of the date and the computed finish: a date the plan cannot meet gives negative float, in the chart and in `results`, and a date it beats changes nothing. Decisions 0010 and 0017.
- Plain data carries a task's limits (`snet`, `snlt`, `fnet`, `fnlt`, `mso`, `mfo`, `alap`), its actuals (`actualStart`, `actualFinish`, `remaining`, `resume`), `key`, and the schedule's `dataDate` and `options`. `schema.json` lists them.
- Plain data carries working calendars: `calendars` (each a `key` with `workDays` and `hoursPerDay`, or a `week`, and `exceptions` of holidays or extra working days), a task's `calendar` by key (the first calendar is every other task's), `durationUnit` (`"days"`, the default, `"hours"` or `"minutes"`, for every duration, remaining time and lag) and `lagCalendar` (`"successor"`, the default, `"predecessor"`, `"24h"` or `{ calendar }`). `mount`, `openHeadless` and the React, Vue and Angular components take them beside `tasks`; with none of them the schedule is planned as in 0.2.0, on one Monday to Friday calendar. An exception before the schedule's first Monday is left out and named in `leftOut`. `snapshot()` and `toPlain` do not return calendars: `leftOut` says so for a schedule that has one.
- `openHeadless` takes plain `{ tasks, links, dataDate, options }` or `{ document }` as well as file bytes, and throws a `PlainDataError` that lists every problem. The schedule it returns has `leftOut` and `results()`: each task's early and late start and finish, total and free float, `critical` and `finished`, with its `key`.

**Import and export**

- A P6 or MS Project file with a value out of range opens with one counted note per kind, naming the first five tasks.
- A P6 file saved from a schedule your host built keeps the project start, and a task with two date limits keeps both.

**The task list**

- A schedule whose tasks name resources shows a Resources column at the right end of the list: each task's names joined by commas, cut with an ellipsis when they do not fit, and the whole list in the tooltip; a summary row and every row mid-drag leave it empty. A schedule with no resource names looks as it did. The list only: print, copy and export do not carry it. `--gantt-res-col` sets its width.
